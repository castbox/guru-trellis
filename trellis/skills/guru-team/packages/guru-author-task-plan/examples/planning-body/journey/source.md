# 连续编辑教学来源

本文件是去敏教学情境，内容是为讲解方法设定的事实与要求。它不是当前业务需求、用户答复或实际工具记录。配套 [process](process.md) 展示如何推导与审核；两份文件都不作为无答案提示的实际 Agent 验收材料。

## 1. 已确认要求

一个编辑页可添加文本、图片或视频。用户通过文本区域的长按菜单粘贴。媒体选择完成后返回编辑页，用户可继续输入。媒体处理在后台执行，处理中仍可重新打开编辑器调整内容。局部“确认”将本轮选择放回主表单；主表单的“保存”才最终提交。普通退出时，存在未保存内容须提示。已确认保留的编辑稿应能重新打开。

## 2. 调查得到的实现事实

- 编辑器、表单与后台处理分别持有媒体来源。清理逻辑在没有持有者时删除临时来源。
- 初稿确认案例中的本地选择已就绪，确认前只有编辑器持有该来源的唯一引用；表单尚未接收，后台任务不持有该来源。确认顺序是：清空编辑器引用，关闭编辑器，再把结果交给表单。
- 另一个处理中案例中，后台上传任务已存在，重新确认会复用原 Future。原回调只清理旧候选；新候选是否继续接收处理状态尚未说明。
- 服务适配器会把返回记录反序列化为新对象，并可能刷新媒体地址。内存替身直接返回之前的同一实例。
- 预览组件可先得到 URL，稍后才完成图像解码；本地缓存可能已有旧帧。
- 当前测试直接调用 paste 和 confirm 方法。媒体样本只有 H264 视频与 AAC 音频的 MOV。交付构建使用裁剪后的原生媒体依赖，其 HEVC/PCM 能力尚未核实。

## 3. 真实未决产品选择

用户在局部确认前关闭编辑器时，未确认的编辑是丢弃，还是保留到下次打开？第1节没有回答。现有代码行为也不能代替这一产品决定。

## 4. 简单任务对照

另一独立需求只要求一个纯函数去除字符串两端空白，保留中间内容。调用方直接传入并取得字符串；不涉及 UI、后台任务或持久化。它不继承前述编辑页的验收场景。
