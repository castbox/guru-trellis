# 需求歧义探索与分级确认

Identity：`RDT-REQ-DECISIONS`；定义 R-DEC-01..04 / BEH-DEC。来源为本地 Task `requirement-decision-exploration` 的已接受整体需求；适用基线 a4feadd99683e006580ef16b078c44e3ad3648a7。候选晋升前是 accepted target，不是已实现证明。前驱与继续适用的责任见 [Task/Delivery](task-delivery-lifecycle.md)、[局部修复 Intake](local-fix-intake.md) 和 [知识维护](knowledge-maintenance.md)。

## R-DEC-01 / BEH-DEC-DISCOVERY：事实与需求选择

原 owner 先调查当前来源、代码、测试、合同与适用历史，复用仍有效的已定事项。用本次改变和保持的行为、正常具体例子及适用关键边界识别两种合理解释的差异。不是等待用户提供完整需求，也不在实现中静默补齐。无歧义时不制造提问；不为探索扩张无关压力或对抗场景。

凡影响目标、可观察行为、范围、兼容性或验收的未明确需求选择，均须用户确认。轻度、可逆或符合惯例不能免除确认。当前代码建立基线，不自动代表用户的新意图。外部系统的实际行为是事实，应通过证据查证；用户可以决定产品如何应对事实，不能以偏好替代事实。

纯 UI 变更未要求改变业务时，保留适用旧承诺；设计稿没画某状态不等于允许删除恢复或业务能力。存在真实来源冲突时由原 Clarify 处理。

## R-DEC-02 / BEH-DEC-QUESTION：低成本确认与重大取舍

轻度需求歧义提供明确参考行为、推荐及必要影响，用户可接受或修正。同阶段且互不依赖的轻度问题可组成简短清单，一次明确接受或逐项修正；不能将相互依赖问题或重大选择混入模糊整体确认。

多个合理选项无法由已确认要求及约束决定，且影响行为、数据、兼容、架构、风险或成本时，研究可行方案并说明推荐、结果及代价，再由用户选择。不要求用户设计函数、字段或代码；既有约束内不暗含需求选择的常规实现由 AI 自主完成。

按钮可在平台支持且允许时使用；普通清晰肯定答复具有相同效果。不以固定按钮、词句或强制问题数量代替语义判断。

## R-DEC-03 / BEH-DEC-ANSWER：逐项承接与新问题

推荐不是默认决定，未答不是接受。轻度清单只是组合呈现，每项仍有独立问题和回答范围。部分回答仅解决实际回答项；不将未答记为拒绝、延期或完成，不用 atomic_group 包装独立条目。未决选择暂停依赖行为，独立调查可以继续。

实际选择写回所属需求、设计及验收；前任务阶段保留在对话。否定推荐后采用用户实际选择，不能保留原推荐为已确认规则。已定内容仍适用时恢复不重问；Author 展开方案后发现新需求歧义仍回原 Clarify，不用旧 clear 判断覆盖新问题。

需求确认不代替整体规划激活或 Git/GitHub、资源创建、发布等独立边界。授权只存在当前对话，不进入问题结果、任务、规范、runtime 或评测证据。

## R-DEC-04 / BEH-DEC-EVIDENCE：复用与效果边界

复用当前 owner、公共 schema 与生命周期。脚本只核验事实及既定机器条件，不发现需求含义或按关键词决定是否询问。canonical 经原受管机制分发；源通过不代表业务项目已经采用。

测试分开证明逐项记录、规则引用/分发和实际 Agent 对话行为。多轮测试后续用户答复不能提前提供给被测 Agent；实际事件及退出码不能由预写 transcript 替代。方法试验不等于完整 Guru 正式入口、生命周期或全部平台效果。历史 UI 回归根因与修复仍需各自证据。
