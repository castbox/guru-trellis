# Review Sufficiency

## Ownership and loading

This is the common semantic rule for the sufficiency of one current review.
Each original review owner reads this complete body before reviewing its own
object. It retains its entry, scope, read order, independence, qualification,
stage-specific pass conditions, repair actions, recorder, recovery and typed
exits. This specification creates no Skill, gate or lifecycle transition.

Resolve framework rules from the complete Guru provider that supplies the
calling Skill. In source, this body is
`trellis/presets/guru-team/spec/workflow/review-sufficiency.md`; after
installation it is `.trellis/spec/workflow/review-sufficiency.md` in that
provider. Package methods and their framework references use the same provider.
Read target-project authority separately. A target repository need not install
Trellis merely to receive a review from an external provider. A missing or mixed
provider returns through the original installation or authority owner; recovery
does not supply a semantic pass.

The applicable Guru owners are Issue Clarify, change-request readiness, contract
wording, Planning Approval, independent change review, Check, Branch Review,
Delivery Review, Completion, Architecture, Requirements/Design/Test maintenance,
and extension-installation evidence review. Apply these rules to each owner's
actual review responsibility. A wording review remains a wording review; an
installation review does not become a business-code review. External specialist
Skills retain their own independently maintained contracts.

## Three distinct conclusions

Keep these conclusions distinct:

1. **Review completed:** the selected object and scope have been sufficiently
   examined, and the owner can report the established findings and coverage.
2. **Object passed:** the object meets its original stage's pass conditions.
3. **Repair or acceptance completed:** the original repair, verification and
   delivery owners have established their required results.

Unfixed findings and failed tests can coexist with a completed independent
read-only review. A failure can be evidence for a finding. Execute targeted
verification only when needed for the current judgment and permitted by the
request; state which conclusions unavailable verification leaves unsupported.
Original prerequisite stops and formal pass, repair, independence and publication
conditions remain in force. Review completion does not authorize repairs or
advance a Task or Delivery.

## Form and cross-check coverage

Identify the current object, purpose and version under the original entry.
Derive check units from effective source commitments, supported entries,
necessary consumers and applicable specialist standards. Cross-check that set
against the source and relationships to find omissions in the coverage itself.
Implementation and tests agreeing cannot establish complete requirements.
Reading every file, complete chapter headings or filled dimension fields cannot
replace behavior and relationship coverage.

Within the original owner's read order and isolation, first derive the key
behavior and relationship questions from its applicable authority, then compare
those questions with the candidate and implementer's explanation. For a
multi-stage path, consider the supported continuous actions and necessary
handoff conditions, not only isolated final states. The dispatch must not seed
the independent reviewer with defect answers or a passing narrative. This does
not move Authority-first Architecture behind requirements/acceptance reading,
create another reviewer or round, or invalidate still-applicable evidence.
Keep only the conclusions needed in the original review or planning body.

Tailor units to the actual object and complexity. No universal table, coverage
percentage, reading quota or unsupported input enumeration is required. Necessary
unchanged consumers are evidence within the selected review, not automatic
expansion of accepted scope. Examine identifiable necessary relationships; do
not claim proof that all unknown defects are absent.

Read applicable complete authority and its conditions under the original read
order. Use [Semantic Retrieval](semantic-retrieval.md) for retrieval sufficiency,
[Specialist Review Standards](quality-guidelines.md#specialist-review-standards)
for selecting professional methods, and
[Test And Validation Value](quality-guidelines.md#test-and-validation-value)
for test effectiveness and proof boundaries. Apply
[Causal Completion Semantics](causal-completion-semantics.md) when judging causal
claims. These sources retain their topic rules; this file does not copy them.

## Investigate the remaining coverage

Work through the remaining check units. Batches and progress reports are
permitted. Finding a few issues, reaching an output count or reaching report
length cannot silently end the review. Continue the unexamined scope within the
original responsibility, carrying necessary coverage context across execution
or context limits. Preserve every established finding in the final report.

When a conversion, state transition or contract problem is found, investigate
applicable entries and consumers in the current scope that share the actual
mechanism. Follow evidenced relationships; a general possibility of more bugs
does not justify unlimited expansion, new features or unsupported defensive
scenarios. When grouping one root cause, preserve each established trigger and
impact.

Finish the investigation needed to judge each discovered candidate: verify its
evidence, applicability and impact under the original qualification contract.
Report all established findings. Explain rejected candidates only when needed
to resolve an important dispute or explain a conclusion's limits, unless the
original owner requires a specific record. This adds no candidate-history store.

## End and report honestly

End when the selected scope and applicable questions have enough coverage to
support the current conclusions. Report the findings, coverage basis and any
unresolved evidence that affects those conclusions. Finding counts, zero results,
Agent agreement and command or scan success cannot replace that judgment.

If access, authority or execution gaps prevent sufficient review, state the
covered portion, remaining portion, concrete blocker and its effect. Do not
claim complete review. Follow the original owner's continuation or declared
exit, including any required prerequisite stop; a factual statement of partial
completion creates no new `partial` exit.

Once coverage is sufficient and there is no new evidence or impact, finish the
current review. Do not rescan merely because another issue might exist. No fixed
round count, consecutive zero-finding rounds, different reviewer, repaired
findings, completed acceptance or a test suite with every check passing is a common completion
condition. The original stage still decides whether its object can pass.

## Review a later candidate

When the original workflow or a new request starts another review, judge which
previous coverage and evidence remain applicable. Review the entire actual
candidate delta and affected paths, including necessary unchanged consumers.
A changed reviewer or session alone does not invalidate verifiable coverage.
Retain valid coverage and supplement missing or invalidated coverage. If the
combined impact cannot be bounded, perform the complete review needed for the
current conclusion. Neither checking only the repair point nor unconditionally
starting from zero is sufficient policy.

This rule governs how a later review works. It does not require the current
invocation to wait for repair or schedule a repair–review–Delivery loop.
Formal fixed ranges, public-result sources, predecessor and finding ancestry,
closure and alignment constraints remain in
[Candidate Applicability And Coverage](workflow-contract.md#candidate-applicability-and-coverage)
and the original stage contracts. That contract also owns engineering-fact
adoption and the distinction between execution facts, semantic judgment and
Git/PR facts; this file does not redefine those rules.

Coverage progress stays in the current conversation or the original necessary
result. Add no long-term review ledger, scorer, digest chain, authorization
record or public field. AI judges coverage and conclusions. Scripts execute
queries and checks, record permitted results and validate objective facts.
