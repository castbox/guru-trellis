## 2. 背景与问题

模型过强的防御与安全偏好是本次重点纠偏的行为成因假设。典型问题是先设想攻击、并发或失败，再默认增加保护义务。既有设计和测试可能据此自证；进入基线后，后继任务继续沿用。研究案例支持治理这种行为，不能证明模型训练层面的因果。

当前 Architecture contract 已拒绝把旧实现当先例，也要求必要性，但其适用入口仍突出新增能力和单项原则。Protection 已要求真实损害与当前层必要性，提出方的缺口、收益和整体代价责任仍需补清。知识合同已管理文档迁移和旧 reader，尚需明确被纠正决策的存量实现及 Task 完成义务。

## 3. 目标与非目标

本任务在原 owners 中形成可实际应用的机制审核方法，覆盖新决策晋升与既有机制采用。纠正错误决策时，影响分析覆盖同一决策的旧采用者，并由原范围与交付合同承接必要收敛。

范围包含公共 canonical 规则、必要调用入口、项目映射、既有分发投影、针对性机械验证与少量真实 Agent 行为对照。规则完成、分发完成和行为观察分别验收。

不实施后端安装升级、游标去密钥、共享仲裁业务修复、生产迁移或线上资源清理。不引入原则排名、Ponytail 固定六步、代码行数目标、新 workflow 阶段、审批链、永久审核/迁移台账或无直接 consumer 的公共字段。完整发布矩阵和发布本身属于原发布职责。

## 4. 真实调用方、场景与流程

| 场景 | 调用方与前置条件 | 触发与处理 | 可观察结果 |
| --- | --- | --- | --- |
| SC1 新增保护 | Author 或 reviewer 正形成候选 | 拟加签名、加密、锁、队列、重试或台账；说明真实约束、现有缺口、机制作用和整体代价 | 无依据的候选不升级为要求、测试或 finding；真实保护仍可成立 |
| SC2 复用机制 | 新入口采用旧机制，旧文件可能无 diff | 核原理由、范围、运行条件与当前消费者；覆盖充分时简短承接，变化或缺证时补判断 | 不因历史通过免审，也不对所有 helper 逐项重审 |
| SC3 纠正决策 | 受审候选改变旧技术选择 | 保持真实业务约束，比较移除、缩小、替换或继续采用；分析旧采用者 | 受审旧规则不自行否决替代；存量处置明确 |
| SC4 晋升与完成 | 候选已实施，原 owner 执行晋升或 Completion | 分别核新边界、旧实现共存、迁移和环境事实 | 不用 CURRENT 晋升或单次 Delivery 证明整项迁完 |
| SC5 分发与行为验证 | canonical 规则候选已就绪 | 经原 preset 分发；用可比事实执行真实 Agent 审查 | 机械结果与实际判断分别报告，未知收益不夸大 |

## 5. 行为要求

- **R1 审核对象。** 审本次新增、修改、复用或扩大使用的机制及其直接消费者。将数据 authority、职责、协调、失败或生命周期约束带入当前路径的采用，即使原实现无 diff 也进入适用性判断。普通 helper 和无关依赖不逐个建单元；无架构影响走原轻量路径。
- **R2 保护举证。** 新增或强化保护的提出方包含作者、reviewer 与模板要求。其说明真实要求或可信事实、现有保障缺口、候选补齐方式、收益和整体运行/维护代价。“没有签名/锁/重试”不独立成立 finding。实际职责偏离无需等待功能失败；真实保密或权限要求无需等待事故。
- **R3 判断方法。** 找到设计依据后，独立判断必要性、适用性和代价。按完整宪法审实际命中的取舍；关注职责与作用范围、状态/协调成本、可行替代和风险匹配证据。五项聚焦问题不转成评分表或固定填报。性能比较以真实约束为准，不要求全局最优。
- **R4 取证与选择。** RDT 和 Architecture 足够时从文档回答；实际行为、全部相关调用者、性能或文档冲突有缺口时定向查实现。审查某项技术选择时，不以该旧选择本身排除替代。保留真实外部合同，沿原受审变更合同实施，再按原阶段晋升。借鉴必要性追问和能力复用，不建设无 consumer 的抽象、包装、转换、配置或未来预留。
- **R5 依据不足。** 新保护补证、修订或撤回，不先成为强制义务。旧保护缺证时不直接删除，也不默认复用通过；只暂停依赖该结论的采用或晋升，无关工作继续。已覆盖的旧论证和工程事实可承接；阶段或版本变化本身不要求重做全部工作。
- **R6 存量分析与处置。** 纠正旧决策时识别实际采用者、共享状态、数据、接口、配置和运行依赖。共存会破坏同一约束或使纠正失效的，承接必要适配与退出。可独立保留的，说明约束如何保持、剩余采用者、真实保留依据、owner、可执行后继交付或可观察触发条件和退出证据。旧场景仍有依据的明确范围后保留。“下次碰到再改”或仅有 owner/链接不代表已安排。新消费者不继续进入已判错模式。
- **R7 晋升与完成。** 分别表达目标生效、新需求交付、旧实现迁完和环境切换。Task scope 内迁移拆到后继 Delivery 仍未完成；范围外有充分共存依据的存量不自动阻塞当前 Task。分析范围可大于实现范围，不自动创建跨仓任务。退出真实支持窗口且无消费者后才按原合同删除旧能力及配置。兼容不自动产生通用双轨框架。
- **R8 公共规则与验证。** 原 owners 保有语义判断；脚本仅验证分发、引用和既定机械条件。canonical、dogfood 和声明平台完整投影一致，既有安装沿原更新/冲突处理路径采用。真实 Agent 用相同事实和可比上下文先判断，再与预期对照；预期不注入受测输入。保留具体执行条件与证据边界，不以删 key 数、代码量或更少 finding 证明改进。

## 6. 约束与依赖

本次沿 Guru 标准 Task/Delivery 生命周期。Planning 由唯一 Author 写，Architecture 独立评估，Wording 和 Approval 分别履行原职责。原安全、权限、敏感数据保护、诚实协作与副作用边界继续成立。不得将业务后端规则直接提升为公共 workflow 需求。

实施依赖当前完整 Guru preset、项目设计宪法、Architecture/change contract 和现有 package/eval 分发设施。当前来源与目标均可读取，没有需要用户补充的范围选择。实际行为验证受可用 Agent 执行入口约束；若不可执行，只能报告缺失并保留本任务该项未完成，不能以静态样例替代。无业务 API、数据库或运行服务变更，因此本任务不要求业务部署证明。

## 7. 可观察验收与验证方式

| 验收 | 要求/场景 | 输入与入口 | 预期观察与证据边界 |
| --- | --- | --- | --- |
| AC1 | R1/R3；SC2 | 新入口复用旧加密/协调机制，原实现无 diff；另给已论证同类消费者对照 | 前者核当前必要性；后者简短承接；不递归重审普通依赖 |
| AC2 | R2/R4/R5；SC1 | reviewer 仅以未签名提 finding；另给真实保密/全局约束的对照 | 无依据要求不成立；必要保护保留；不把复杂度转到新台账 |
| AC3 | R4/R5；SC3 | 旧基线指定 AES，正在审其必要性；另给缺证且删后合同未核清的旧保护 | 可比较去该选择的候选；缺证时补证与限制依赖结论，不擅删或全局停工 |
| AC4 | R6/R7；SC3/SC4 | 新旧 writer 共享状态；独立可迁移入口；场景差异保留；scope 内后继 Delivery | 分别承接必要同步适配、可执行分期、范围保留和 Task 未完成责任；不把晋升当迁完 |
| AC5 | R3/R8；SC5 | 实际候选的规则与调用入口、preset reapply 和投影检查 | 无新原则排名、阶段、ledger 或无 consumer 字段；机械检查仅证明其实际范围 |
| AC6 | R8；SC5 | 同来源事实、可比上下文下的原方法/新方法真实 Agent 执行 | 保存实际输入、输出、规则版本与语义核对；不泄露答案；缺旧行为证据则不宣称改善幅度 |

AC1至AC4用少量组合正反案例覆盖，具体组合由 Delivery 规划确定；不要求把研究全部案例变成每次业务任务的固定矩阵。全 Task 完成须同时满足规则、分发、当前测试和实际行为证据要求。

## 8. 实际未决项

没有阻塞整体范围编写的未决问题。Delivery 规划仍须确定最小规则落点、必要调用方与 SSOT 回写、具体验证入口及行为案例组合；它们属于原 Author/Architecture 的技术细化，尚不代表方案审核或实施完成。
