## 5. 完整行为、条件与约束

本批完整承接以下全部行为。已约定来源设计及约束的实际落点只在本批 design 第3节维护；这里不另建处置矩阵。草稿、初始文件和 PRD-only 均可作为正常 Planning 中间状态。原 `requirements_ready` 只检查当时需求阶段的必要内容；当前 `plan_ready` 则要求 design 和 implement 完成适用内容。

### R1. 先调查并验证实际差额

盘点当前 Issue／草稿写作入口、Clarify 的正文与评论操作、Wording 和 Readiness 的审核职责、必要的下游读取及现有示例。

通过受支持的正常入口观察实际编写结果，区分合同缺口、指引不足、普通执行遗漏和读取不足。已有机制满足要求时复用原机制；仅对证据支持的差额修改，不预先认定需要新能力或新流程。

### R2. 由原 Clarify 整理完整正文

用户要求创建或完善 Issue 时，`guru-clarify-requirements` 先读取完整当前请求、Issue 正文、相关评论及必要仓库事实，区分已确认要求、约定设计、建议、历史事实和未决问题。

仓库可以回答的问题先调查；影响需求成立的真实选择按原澄清流程处理。不得猜测缺失事实或编造用户回答。必要问题尚未解决时，保留具体缺口并阻塞依赖结论，不宣称正文已完善。

形成最终草稿或修订正文时，须保留此前仍有效的已确认需求，并整合本轮明确的变更。要求发生替换、撤回或范围调整时，由原 Clarify 按既有规则处理，不能仅因要求未在本轮重述就将其删除。评论可保留讨论及历史，但不能仅因要求已出现在评论或当前会话，就省略最终正文中的必要内容。简短完整的原正文可保留，不为符合形式重写。

正文须让读者理解本 Issue 承担的需求。共享定义或详细接口规格可以通过准确引用承接；本 Issue 的行为、条件、约束和验收仍须写清，不能只给出链接或笼统的“见讨论”。

已有 Issue 的正文修改继续使用原操作、确认、写入后回读和上下文刷新路径。新 Issue 仍从经原审核的草稿进入 `guru-create-issue`；本 Issue 不新增创建入口或修改 Task 创建职责。

### R3. 创建与修订共同遵守唯一内容 SSOT

由现有 Clarify 步骤负责维护唯一的 Issue 内容编写规范，源文件放在其规范包内，并通过既有受管分发安装。实施时按现有结构确定文件路径。创建和修订必须引用同一份规范；模板、示例和入口不得复制并维护另一套内容标准。

规范明确适用内容、必要深度、裁剪条件、来源保留和审核要求。Issue 创建与修订均必须满足同一质量基线；不能以已有 Issue、局部修改或独立操作为由跳过适用规范。

语言规则唯一引用 `.trellis/spec/workflow/clear-technical-writing.md`。本文将其称为“采用 STE 部分原则的项目中文清晰写作规范”。它是项目规则，不是 ASD-STE100 的中文版，也不表示中文符合 ASD-STE100 或已取得认证。

创建、修订及原审核责任方在生成或审核实质文本前，必须完整读取该文件，并在各自职责内执行适用规则。规范缺失或读取失败时，暂停依赖它的实质文本，只报告具体缺口；恢复并完整读取后继续原请求，不新增审批。

适用的强制规则必须落实，包括保留完整语义、明确执行者和条件、保持术语一致，以及区分要求、建议、事实和未验证结论。短句、常用词和主动语态属于建议，不能以句长、词数或个人表达偏好单独阻塞。同样清楚且准确的表达可以保留。

创建时检查最终标题和正文。修订时，语言检查覆盖本次新写或修改的文本及理解它所需的上下文；R4 的内容完整性检查仍覆盖修改后的完整标题和正文。保留精确命令、路径、标识符、接口消息、用户指定原文和必要引用。原始证据保持原样，呈现时遵守脱敏规则。

来源保留原则与 #154 已落地规则保持一致，不复制另一套公共规则。

正文按实际需求清楚组织下列内容：

- 背景、当前问题及影响；
- 目标、承担范围与非目标；
- 真实用户或调用方、前置条件、触发动作、期望行为和可观察结果；
- 已确认的行为要求，以及适用的条件、例外、失败结果和执行顺序；
- 影响交付的约束、依赖及必要来源；
- 可观察的验收与验证方式；
- 实际存在的未决项及其影响。

简单 Issue 可以简写、合并章节。裁剪不得丢失适用内容，不要求空章节、无关的 N/A、统一用户故事、Given/When/Then 或优先级格式。Bug 以现象、期望和正常复现场景为主；工程变更使用真实调用方及“触发条件 → 行为 → 可观察结果”；存在真实业务角色和价值时可使用用户故事。

不要求提交者提前完成技术设计。来源已经明确的接口、机制、职责、顺序和兼容约束，须按其实际角色保留；不得以“后续 Planning 再设计”为由删除已确认承诺。尚未确定的实现机制继续由原规划责任方处理。

### R4. 原责任方读取同一规范并审核结果

下列责任方必须在现有入口合同中显式引用同一 Issue 内容 SSOT 和项目中文清晰写作规范。执行时必须实际读取，并按原职责使用。须能核对入口、安装文件与实际使用步骤；仅在 README 声明不构成完成。

- `guru-clarify-requirements`：负责草稿编写、已有正文修订及自检，对照同一 SSOT 核对需求、来源、范围和正文完整性。
- `guru-review-contract-wording`：在原职责内检查表述清楚、术语一致，以及重排和改写是否保持完整语义。
- `guru-review-change-request`：在原职责内检查需求完整性、范围、独立交付单位和可观察验收。
- `guru-create-issue`：保留创建职责，在原创建语义门禁中，确认最终草稿满足共同规范，前序审核结果仍适用，待写入内容与经审核草稿一致。发现遗漏时返回原责任方，不另定义内容标准或接管前序职责。创建后按原路径回读，确认实际标题、正文与经审核内容一致。

创建审核面向最终草稿；修订审核面向修改后的完整标题、正文及必要来源上下文，不能仅审新增段落。两者遵循同一 SSOT，但保留各自的写入、确认、写入后回读、状态时效校验和恢复路径。修订不调用创建动作，不生成重复 Issue。

局部修订须判断改动对完整正文的影响，无关历史段落不因语言偏好被强制重写。如果发现授权范围外的既有缺口，须说明缺口及其对本轮结论的影响。不得静默扩大修改范围；如果缺口影响本轮完整性判断，须保留该判断的阻塞，不得宣称正文完整合规。需要真实范围选择时，由原 Clarify 处理。

发现正常遗漏时返回原受影响责任方修订，并按既有重新进入审核的规则执行。技术细化未定不自动成为产品需求缺口。章节齐全、关键词覆盖、文件存在，以及记录器或校验器通过，都不能单独证明内容充分。

不要求把所有简略 Issue 先改写成完整 Issue 才能进入 Planning；本 Issue 的正文整理要求适用于用户实际请求的创建或完善操作。#154 对简略来源进行调查、澄清并形成完整 PRD 的能力保持。



## 6. 本批验收、验证方式与未决项

### 6.1 实际行为与安装验证


至少在一个当前支持、具备实际 Agent 执行能力的平台，通过正常入口观察以下场景：

| 场景 | 可观察结果 |
| --- | --- |
| V1：简略自然语言请求 | Agent 调查事实并完成必要澄清，形成清楚完整的草稿；未猜测事实或编造回答。 |
| V2：已有详细技术 Issue | 修订正文保留适用的条件、例外、义务强度、约束和验收；不因模板或简写丢失来源承诺。 |
| V3：正文与评论分散 | 在用户要求完善 Issue 时，将已确认必要内容整合进正文；建议和历史没有被升级为要求。 |
| V4：正常写作遗漏及修订 | 原审核实际指出缺失内容，返回原责任方修订并重新审核；最终正文补齐对应要求。 |
| V5：只读审核与已有完整正文 | 只读请求不自动写入；完整正文不因形式要求被无意义重写。 |
| V6：创建与修订的一致性 | 对语义等价的已确认需求，分别经新 Issue 草稿和已有 Issue 修订入口执行。两者实际加载同一内容 SSOT 及同一语言规范，按相同质量基线编写、审核，保留相同需求语义。章节组织可依输入裁剪。 |
| V7：局部修订及完整正文审核 | 修改后的完整标题、正文及必要上下文得到检查。原审核发现并推动修订正常产生的跨段不一致或遗漏。语言检查按 R3 执行，无关内容不被自动扩写，范围外缺口按 R4 处置。 |

样例合计覆盖功能变更、缺陷修复和工程变更；不要求逐场景新建安装、Task 或 GitHub Issue。草稿可用于不需要 GitHub 写入的场景；创建和正文修改两条路径均须在明确选定的可写验证对象上取得实际写入及写入后回读证据，并遵守原确认边界。草稿验证只证明写作与审核，不能代替实际创建结果。可复用创建所得 Issue 验证后续修订，不要求逐场景创建资源。

提供去敏示例，展示输入、实际调查或澄清得到的必要事实、最终正文及审核修订关系。不能只提供空模板或宿主预写的理想成品，再用脚本封装入口或 schema 校验通过冒充 Agent 编写成功。

按实际改动范围，检查规范源文件、本仓库安装副本、目标安装及声明平台投影，并核对规范加载、引用、重复应用、漂移和冲突旁文件。仅当改动确需干净安装证明时，最多使用一个代表性干净临时仓库。分别报告实际 Agent 行为、确定性检查和安装结果。明确列出未验证的平台，以及由专门 Issue 承担的完整多平台升级／Release 矩阵。

### 6.2 整体验收责任
