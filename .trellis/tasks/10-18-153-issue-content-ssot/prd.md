SSOT 指单一事实来源。Issue 内容 SSOT 定义创建和修订共同适用的内容质量；它不是新的范围权威。Task PRD 承载本 Task 整体要求；Delivery design 承载本批具体实现方案。Wording 指原表述审核，Readiness 指原需求完整性及独立交付审核。正文完整性与语言检查的范围不同：前者检查修改后的完整标题、正文及必要来源上下文；后者在修订时检查本轮新写或修改文本及理解它所需的上下文。

## 2. 背景与问题

Guru Team 已有事实调查、Clarify 需求澄清与草稿或正文修订、Wording、Readiness、Create Issue 及写入后回读能力。#154 已完善后续 Task 与 Delivery 规划正文。本 Task 解决 Issue 创建与修订的共同内容规范及最终正文整理问题。

当前需验证的差额是：用户要求创建或完善 Issue 时，已确认需求是否仍散落在评论或会话，最终正文是否完整说明问题、行为、范围与验收，以及原审核能否识别普通遗漏并推动修订。不得从已有能力清单推定每次正文都完整，也不得先认定执行脚本会丢失正文。

前置调查已定位原 Clarify 的正文/评论写入、Wording 固定完整 title/body 范围、Readiness 十维度审核和 Create Issue 回读机制。调查仅证明这些合同和共同正文规范的显式差额；已运行的 scan 不是语义通过、真实创建或修订证据。实际修改前仍须通过正常入口观察写作结果，将合同缺口、指引不足、普通执行遗漏和读取不足区分开。已有能力正常工作的部分直接复用。

## 3. 目标与非目标

用户要求创建或完善 Issue 时，原责任方完成调查、必要澄清、正文编写或修订及审核，使最终草稿或 Issue 正文完整承接所有仍有效的已确认需求，包括此前内容和本轮明确变更。创建与修订共同使用 Clarify package 唯一维护、通过原受管分发安装的 Issue 内容规范，并共同采用现有项目中文清晰写作规范。

本 Task 承担 R1–R4、V1–V7 与 AC1–AC10 全部责任。源码或模板完成不等于整体完成；Completion 还须核对实际 Agent 写作及审核、创建与正文修改的真实写入和回读、定向工程及安装证据。普通状态查询、只读审核、需求讨论及过程评论不自动触发正文写入。Issue 完善不隐含授权创建 Task、branch 或 worktree。

来源明确的非目标如下：

- 不新增 GitHub Issue Forms、chooser 配置、repository-assets 安装面或相应 manifest 扩展，不修改业务仓库的模板和标签策略。
- 不新增 Skill、审批阶段、通用需求数据库、额外 gate artifact 或无人消费的 DTO；不静默改变 public API。
- 不修改 Trellis upstream、全局 npm、`node_modules` 或 hook 来实现编写流程。
- 不自动重写历史 Issue，不执行本 Issue 范围外的发布或资源创建；实际验证副作用沿原边界单独处理。
- 不扩展恶意篡改、攻击、压力及非常规故障场景，只覆盖正常输入、普通遗漏、stale／mismatch 和既有恢复。
- #154 已完成 Task／Delivery 规划正文改进。本 Issue 聚焦 GitHub Issue 的编写及正文整理，复用其适用规则，不建立第二份 Planning 权威。

## 4. 真实调用方、场景与流程

这是工程 workflow 变更。实际调用方是请求创建、完善或审核 Issue 的用户及执行原步骤的 Agent，不编造业务终端用户故事。

| 场景 | 调用方及前置条件 | 触发动作 | 处理行为 | 可观察结果 |
| --- | --- | --- | --- | --- |
| S1 创建 | 用户提出简略或详细的创建请求；原 Intake 正常入口可用 | 请求创建 Issue | 原 Discovery 调查；Clarify 读取完整来源、必要澄清并按共同 SSOT 写草稿；原 Wording/Readiness 审核；Create Issue 在原门禁内核对最终草稿，执行创建并回读 | 草稿完整且语义保持；仅创建所选对象；回读实际标题、正文与审核内容一致 |
| S2 完善既有 Issue | 既有正文、相关评论及当前请求可读 | 请求完善或修订正文 | Clarify 保留仍有效承诺并整合本轮明确变更；按原正文修改路径写入、回读、刷新；原审核检查完整修改后正文 | 必要内容进入最终正文；建议和历史保持原角色；不调用创建动作或重复建 Issue |
| S3 普通遗漏 | 原写作产生或原入口支持的未完成正文 | 进入原审核 | 原 owner 指出具体遗漏并回到最早受影响 owner；修订后按既有规则重入审核 | 有实际缺口、修订及重新审核结果；机械通过不替代语义判断 |
| S4 只读/完整正文 | 用户仅查询、讨论或只读审核，或已有正文已完整 | 读取或审核 | 保持只读边界；可以给修订建议；完整正文不为形式重写 | 不发生自动正文写入；仍保留原权限与确认边界 |
| S5 局部修订 | 当前授权范围明确，必要来源和完整 title/body 可读 | 修改局部文本 | 语言审核检查本轮文本与必要上下文；完整性审核检查完整正文及跨段影响；范围外缺口说明影响并交原 Clarify 处理真实范围选择 | 本轮未重述的有效要求保留；正常跨段遗漏被修订；无关历史不自动扩写；影响完整性判断的范围外缺口仍阻塞该判断 |
| S6 规范暂缺 | 创建、修订或原审核依赖的语言规范缺失或读取失败 | 开始实质文本 | 只报告具体缺口并暂停依赖正文；恢复后完整读取并继续同一请求 | 不作未验证声明，不新增审批，不改变原步骤职责 |

S1 与 S2 对语义等价的需求使用同一内容质量基线，章节组织允许按输入裁剪。创建与修订各自保留原写入、确认、freshness 和恢复路径。必要问题未解决时停止依赖结论；技术机制未定由原规划 owner 细化，不自动当作产品需求缺口。

## 5. 行为要求

以下 R1–R4 保留 Direct Source 的全部要求。来源已约定的 owner、共同规范归属、语言 SSOT 和受管分发约束由选定 Delivery design 第3节提供唯一来源设计处置及实际落点；本 PRD 不另建处置矩阵。

### R1. 先调查并验证实际差额

盘点当前 Issue／草稿写作入口、Clarify 的正文与评论操作、Wording 和 Readiness 的审核职责、必要的下游读取及现有示例。

通过受支持的正常入口观察实际编写结果，区分合同缺口、指引不足、普通执行遗漏和读取不足。已有机制满足要求时复用原机制；仅对证据支持的差额修改，不预先认定需要新能力或新流程。

### R2. 由原 Clarify 整理完整正文

用户要求创建或完善 Issue 时，`guru-clarify-requirements` 先读取完整当前请求、Issue 正文、相关评论及必要仓库事实，区分已确认要求、约定设计、建议、历史事实和未决问题。

仓库可以回答的问题先调查；影响需求成立的真实选择按原澄清流程处理。不得猜测缺失事实或编造用户回答。必要问题尚未解决时，保留具体缺口并阻塞依赖结论，不宣称正文已完善。

形成最终草稿或修订正文时，须保留此前仍有效的已确认需求，并整合本轮明确的变更。要求发生替换、撤回或范围调整时，由原 Clarify 按既有规则处理，不能仅因要求未在本轮重述就将其删除。评论可保留讨论及历史，但不能仅因要求已出现在评论或当前会话，就省略最终正文中的必要内容。简短完整的原正文可保留，不为符合形式重写。

正文须让读者理解本 Issue 承担的需求。共享定义或详细接口规格可以通过准确引用承接；本 Issue 的行为、条件、约束和验收仍须写清，不能只给出链接或笼统的“见讨论”。

已有 Issue 的正文修改继续使用原操作、确认、写入后回读和上下文刷新路径。新 Issue 仍从经原审核的草稿进入 `guru-create-issue`；本 Issue 不新增创建入口或修改 Task 创建职责。

### R3. 创建与修订共同遵守唯一内容 SSOT

由现有 Clarify 步骤负责维护唯一的 Issue 内容编写规范，源文件放在其规范包内，并通过既有受管分发安装。实施时按现有结构确定文件路径。创建和修订必须引用同一份规范；模板、示例和入口不得复制并维护另一套内容标准。

规范明确适用内容、必要深度、裁剪条件、来源保留和审核要求。Issue 创建与修订均必须满足同一质量基线；不能以已有 Issue、局部修改或独立操作为由跳过适用规范。

语言规则唯一引用 `.trellis/spec/workflow/clear-technical-writing.md`。本文将其称为“采用 STE 部分原则的项目中文清晰写作规范”。它是项目规则，不是 ASD-STE100 的中文版，也不表示中文符合 ASD-STE100 或已取得认证。

创建、修订及原审核责任方在生成或审核实质文本前，必须完整读取该文件，并在各自职责内执行适用规则。规范缺失或读取失败时，暂停依赖它的实质文本，只报告具体缺口；恢复并完整读取后继续原请求，不新增审批。

适用的强制规则必须落实，包括保留完整语义、明确执行者和条件、保持术语一致，以及区分要求、建议、事实和未验证结论。短句、常用词和主动语态属于建议，不能以句长、词数或个人表达偏好单独阻塞。同样清楚且准确的表达可以保留。

创建时检查最终标题和正文。修订时，语言检查覆盖本次新写或修改的文本及理解它所需的上下文；R4 的内容完整性检查仍覆盖修改后的完整标题和正文。保留精确命令、路径、标识符、接口消息、用户指定原文和必要引用。原始证据保持原样，呈现时遵守脱敏规则。

来源保留原则与 #154 已落地规则保持一致，不复制另一套公共规则。

正文按实际需求清楚组织下列内容：

- 背景、当前问题及影响；
- 目标、承担范围与非目标；
- 真实用户或调用方、前置条件、触发动作、期望行为和可观察结果；
- 已确认的行为要求，以及适用的条件、例外、失败结果和执行顺序；
- 影响交付的约束、依赖及必要来源；
- 可观察的验收与验证方式；
- 实际存在的未决项及其影响。

简单 Issue 可以简写、合并章节。裁剪不得丢失适用内容，不要求空章节、无关的 N/A、统一用户故事、Given/When/Then 或优先级格式。Bug 以现象、期望和正常复现场景为主；工程变更使用真实调用方及“触发条件 → 行为 → 可观察结果”；存在真实业务角色和价值时可使用用户故事。

不要求提交者提前完成技术设计。来源已经明确的接口、机制、职责、顺序和兼容约束，须按其实际角色保留；不得以“后续 Planning 再设计”为由删除已确认承诺。尚未确定的实现机制继续由原规划责任方处理。

### R4. 原责任方读取同一规范并审核结果

下列责任方必须在现有入口合同中显式引用同一 Issue 内容 SSOT 和项目中文清晰写作规范。执行时必须实际读取，并按原职责使用。须能核对入口、安装文件与实际使用步骤；仅在 README 声明不构成完成。

- `guru-clarify-requirements`：负责草稿编写、已有正文修订及自检，对照同一 SSOT 核对需求、来源、范围和正文完整性。
- `guru-review-contract-wording`：在原职责内检查表述清楚、术语一致，以及重排和改写是否保持完整语义。
- `guru-review-change-request`：在原职责内检查需求完整性、范围、独立交付单位和可观察验收。
- `guru-create-issue`：保留创建职责，在原创建语义门禁中，确认最终草稿满足共同规范，前序审核结果仍适用，待写入内容与经审核草稿一致。发现遗漏时返回原责任方，不另定义内容标准或接管前序职责。创建后按原路径回读，确认实际标题、正文与经审核内容一致。

创建审核面向最终草稿；修订审核面向修改后的完整标题、正文及必要来源上下文，不能仅审新增段落。两者遵循同一 SSOT，但保留各自的写入、确认、写入后回读、状态时效校验和恢复路径。修订不调用创建动作，不生成重复 Issue。

局部修订须判断改动对完整正文的影响，无关历史段落不因语言偏好被强制重写。如果发现授权范围外的既有缺口，须说明缺口及其对本轮结论的影响。不得静默扩大修改范围；如果缺口影响本轮完整性判断，须保留该判断的阻塞，不得宣称正文完整合规。需要真实范围选择时，由原 Clarify 处理。

发现正常遗漏时返回原受影响责任方修订，并按既有重新进入审核的规则执行。技术细化未定不自动成为产品需求缺口。章节齐全、关键词覆盖、文件存在，以及记录器或校验器通过，都不能单独证明内容充分。

不要求把所有简略 Issue 先改写成完整 Issue 才能进入 Planning；本 Issue 的正文整理要求适用于用户实际请求的创建或完善操作。#154 对简略来源进行调查、澄清并形成完整 PRD 的能力保持。

## 6. 约束与依赖

- 唯一 Issue 内容规范位于原 Clarify package，实施时按当前结构选具体文件路径。四个原 owners 必须显式定位同一安装正文并实际读取。模板、示例、入口不得维护另一套内容标准。
- 语言规范只引用既有 `clear-technical-writing.md`；来源保留复用 #154 已落地适用规则。既有规范可明确引用，但本 Issue 行为、条件、约束和验收仍须在正文中说明。
- 原 Clarify 拥有意图、来源角色、范围与真实选择；Discovery 提供可查事实。Wording、Readiness 与 Create Issue 各保留原判断，记录器和校验器仅执行确定性事实，不替代内容充分性判断。
- 不新增公开 API、DTO、gate artifact、Skill 或审核阶段。只有实际验证证明确定性缺陷时，才在 accepted scope 内处理；当前尚无改变 scanner scope/schema 或 mutation executor 的需求依据。
- canonical、dogfood 和安装投影须沿原受管分发同步，并处理 reapply、drift、sidecar 和用户自有内容保留。不能修改上游、全局 npm、`node_modules` 或 hook 实现流程。
- GitHub 实际验证依赖明确选定的可写对象、正常原入口及写入后回读。可复用创建所得 Issue 做修订，不要求每场景创建资源；不能以草稿或机械封装代替真实写入结果。
- 本 Task 不涉及数据库、服务 API 或数据格式迁移，因此不定义数据迁移方案。规范性来源中已有接口、职责、执行顺序与兼容边界继续保留。实现机制由 Delivery Author/Architecture 细化，不将技术未定升级为用户前置义务。
- 完整多平台升级与 Release 矩阵由专门 Issue 承担。本 Task 的代表平台行为不能推定其余平台的真实 Agent 行为。

## 7. 可观察验收与验证方式

### 7.1 实际行为与安装验证

至少在一个当前支持、具备实际 Agent 执行能力的平台，通过正常入口观察以下场景：

| 场景 | 可观察结果 |
| --- | --- |
| V1：简略自然语言请求 | Agent 调查事实并完成必要澄清，形成清楚完整的草稿；未猜测事实或编造回答。 |
| V2：已有详细技术 Issue | 修订正文保留适用的条件、例外、义务强度、约束和验收；不因模板或简写丢失来源承诺。 |
| V3：正文与评论分散 | 在用户要求完善 Issue 时，将已确认必要内容整合进正文；建议和历史没有被升级为要求。 |
| V4：正常写作遗漏及修订 | 原审核实际指出缺失内容，返回原责任方修订并重新审核；最终正文补齐对应要求。 |
| V5：只读审核与已有完整正文 | 只读请求不自动写入；完整正文不因形式要求被无意义重写。 |
| V6：创建与修订的一致性 | 对语义等价的已确认需求，分别经新 Issue 草稿和已有 Issue 修订入口执行。两者实际加载同一内容 SSOT 及同一语言规范，按相同质量基线编写、审核，保留相同需求语义。章节组织可依输入裁剪。 |
| V7：局部修订及完整正文审核 | 修改后的完整标题、正文及必要上下文得到检查。原审核发现并推动修订正常产生的跨段不一致或遗漏。语言检查按 R3 执行，无关内容不被自动扩写，范围外缺口按 R4 处置。 |

样例合计覆盖功能变更、缺陷修复和工程变更；不要求逐场景新建安装、Task 或 GitHub Issue。草稿可用于不需要 GitHub 写入的场景；创建和正文修改两条路径均须在明确选定的可写验证对象上取得实际写入及写入后回读证据，并遵守原确认边界。草稿验证只证明写作与审核，不能代替实际创建结果。可复用创建所得 Issue 验证后续修订，不要求逐场景创建资源。

提供去敏示例，展示输入、实际调查或澄清得到的必要事实、最终正文及审核修订关系。不能只提供空模板或宿主预写的理想成品，再用脚本封装入口或 schema 校验通过冒充 Agent 编写成功。

按实际改动范围，检查规范源文件、本仓库安装副本、目标安装及声明平台投影，并核对规范加载、引用、重复应用、漂移和冲突旁文件。仅当改动确需干净安装证明时，最多使用一个代表性干净临时仓库。分别报告实际 Agent 行为、确定性检查和安装结果。明确列出未验证的平台，以及由专门 Issue 承担的完整多平台升级／Release 矩阵。

### 7.2 整体验收责任

以下 AC1–AC10 与 Direct Source 编号一致。R1 对应 AC1，R2 对应 AC2/AC4/AC7/AC10，R3 对应 AC2/AC3/AC4/AC9，R4 对应 AC2/AC5/AC6/AC7/AC10。S1–S6 与 V1–V7 的入口及观察由第7.1节规定；最终证据必须同时说明适用输入、实际执行 owner、正文、修订和可观察结果。

- [ ] AC1：已盘点现有能力并实际验证差额；修改范围有具体证据，已满足要求的能力直接复用。
- [ ] AC2：存在唯一、受管分发的 Issue 内容 SSOT。Clarify 的创建／修订写作入口，以及 R4 所列审核和创建步骤的适用语义门禁，均显式读取同一规范并按原职责执行。创建与修订没有两套内容标准。最终正文完整承接全部仍有效的已确认需求，包括此前内容和本轮明确的变更。必要内容不只留在评论或当前会话。
- [ ] AC3：共同规范支持按真实需求裁剪，覆盖适用的背景、范围、场景、行为、约束及验收，不强制无关格式或空章节。
- [ ] AC4：详细来源的条件、例外、义务强度和已确认技术约束完整保留；建议、历史与未知事实保持原角色。
- [ ] AC5：原 Wording、Readiness 在原职责内识别正常遗漏并返回修订，V4 有实际发现、修订及重新审核结果。
- [ ] AC6：V1–V7 的适用行为有实际 Agent 证据，样例覆盖三类需求；V6 证明创建与修订实际消费同一 SSOT，并遵循相同内容质量基线。创建和修订均有真实写入及写入后回读证据，未用脚本通过替代实际行为。
- [ ] AC7：只读请求、已有完整正文、Issue 创建与 Task 创建边界保持；既有责任分工、typed exits、确认和恢复合同未被另建流程替代。
- [ ] AC8：受影响的分发、加载及定向验证通过；实际行为、机械验证、安装结果和未验证边界分别说明。
- [ ] AC9：创建、修订和原审核责任方实际完整读取同一 `clear-technical-writing.md`，执行采用 STE 部分原则的项目中文清晰写作规范。适用强制规则得到落实，建议未被升级为独立阻塞条件；语义、条件、术语及事实状态准确。规范缺失时按 R3 暂停并恢复，不宣称中文符合 ASD-STE100 或已取得认证。
- [ ] AC10：修订审核覆盖修改后的完整标题、正文及必要来源上下文；V7 证明正常遗漏得到处置，此前仍有效的需求没有因本轮未重述而丢失，同时保持局部修改的授权范围。

### 7.3 证据边界

实际 Agent 写作与审核、确定性 package/runtime 检查、安装和受影响平台投影分别报告。已有研究和扫描只作为基线；不得算作 V1–V7 完成。章节、关键词、文件非空、schema、recorder/checker pass 不证明语义充分性。创建与正文修改必须各有实际写入及回读，不用草稿替代。任何缺失的适用行为证据保留为验收缺口。
