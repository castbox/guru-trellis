“最小充分”指完成原始目标和实际受支持场景所需的要求与验收足够明确；不以减少篇幅替代正确性。四原 owner 指 Clarify、Wording、Readiness、Create Issue，各自保留既有职责。

## 2. 背景与问题

现行共享内容规范已要求完整读取来源、保留有效承诺、裁剪适用内容，并由四原 owner 在其职责内使用。仍需明确限制模型因防御性推断、风险厌恶、完整性偏好或未来想象新增要求；还需避免配套约束压过主目标、完整规则分散及验收复述功能条目。

本项把适用于 Issue 的通用方法写入 Guru 自身的共享合同。外仓仅用于实施前研究，交付后的公共扩展能够独立使用。

## 3. 目标与非目标

让 Issue 创建、修订和审核先判断要求是否必要，再检查表达是否充分。正文突出核心行为与结果，验收精简且足以判定目标完成，同时保留真实必要保护和受影响入口适配。

范围是共享内容规范、四原 owner 的必要引用、受影响 canonical/dogfood/声明平台投影及定向验证。Task 对 #818 整体负责，不把分发成功当作 Agent 行为验证完成。

不新增 Skill、审核轮次、评分、逐项证明表、资格账本、评测平台或脚本语义门禁。不追改无关历史 Issue，不把 #747/#736 整项纳入或设为前置；#819 的审核评论复用及 Intake 分流另项承担。不关联发布 Issue 或版本，不执行完整安装或发布矩阵。

## 4. 真实调用方、场景与流程

- **S1 创建或修订：**原 Clarify 在读取原始需求、当前 Issue 和必要仓库事实后组织正文。新增要求先对应实际场景、消费者及当前结果；删除无依据的扩张与派生验收。最终正文连续说明触发条件、执行者、行为、结果，再展开必要例外和技术约束。
- **S2 原审核：**Wording、Readiness 和 Create Issue 在各自原入口读取完整当前正文及必要来源。审核者先独立还原完整规则，再核对来源、真实入口和验收；同时发现多余要求与必要遗漏。原 Gate、修订、刷新及回读路径保持。
- **S3 受管采用：**原安装 owner 同步受影响共享正文和入口投影。验证分别观察实际 Agent 输出和安装分发事实；未执行项如实报告。

## 5. 行为要求

**R1 最小充分与必要性（S1/S2）：**共享规范统一定义方法，四原 owner 在原职责内执行。新增要求、机制和验证义务须服务原始需求、受支持入口、实际消费者及当前结果。必要性说明回答：省去该项后，哪个受支持场景中的哪项原始需求无法完成。业务结果必要不代表整套机制必要；文档、实现、测试或审核记录不能自行取得需求权威。

**R2 扩张及其派生义务（S1/S2）：**禁止从未来想象或防御性推断扩张职责、字段、状态、控制机制与验收。无依据或已排除内容不转成确认问题、测试、Finding、依赖、后续任务或放行条件。发现扩张后收敛要求及完整派生义务，不只改名或搬到其他阶段。保留原始需求明确要求的安全、权限、敏感数据保护和真实兼容责任。

**R3 核心规则与完整审核（S1/S2）：**正文先连续说明触发条件、执行者、核心行为和可观察结果，再展开必要例外与技术约束。同一规则保持一个完整定义；新增摘要不能掩盖正文分散。审核同时识别多余项和必要遗漏。发现既有入口不自动新增交付项；完成原目标所需的真实适配不能以精简为由省略。审核者不依赖作者会话解释才能理解基本行为。

**R4 主目标优先的验收（S1/S2/S3）：**验收先证明主目标，再覆盖按实际后果确定的必要保护。不逐项复述功能规则，不凭完整性追加固定样本数、设备数、测试方法或完整矩阵。验收深度与本项成果一致，不将后续实施或发布准备提前变成需求发布条件。

**AC1（R1–R4、S1/S2）：**复用已有例子与执行能力，经现有 Issue 撰写和审核入口观察真实输出。输入包含无原始需求依据的扩张及派生验收，并保留同一来源明确要求的保护和真实受影响入口。预期输出删除扩张及派生义务、突出主要结果，必要保护和适配仍完整。分别说明实际覆盖的写作、审核行为和未验证范围；不新建评测平台或证明账本。
