# 正常完成路径与协调成本：整体需求

## 1. 来源与术语

本 Task 为 `no_issue` 来源，承担三层规范方案的 Guru 通用方法部分。

| 来源 | 章节 | 角色与用途 |
| --- | --- | --- |
| `/tmp/codex-architecture-three-layers-20261108/proposal.md` | §1、§3、§7、§8 | 本次要求、最小源修改、验证与交付边界 |
| `trellis/skills/guru-team/packages/guru-maintain-architecture-baseline/references/contract.md` | Adopted-mechanism review | 既有唯一通用方法，保留原 owner、适用性与路由 |
| `trellis/skills/guru-team/packages/guru-qualify-root-cause/references/contract.md` | Protection | 既有保护资格职责；必要用途不替代 Architecture 取舍 |
| `trellis/skills/guru-team/packages/guru-author-task-plan/references/authoring.md` | Requirements and candidate before substantive solution writing | 原方案形成消费点 |

“正常完成”是受支持调用方取得承诺的可观察结果；提前返回受理状态不自动等于完成。“额外协调”指新增共享写、串行依赖、等待阶段或独立维护状态，不按锁或队列名称分类。

## 2. 背景与问题

现有方法已要求正常路径优先、用途和总体成本判断以及删除/收窄/替换比较，但未明确默认不准入额外协调、独立审核主动淘汰机制和最终完成成本的责任。用途解释或旧实现测试可能被误当成保留机制的充分理由。

业务仓库的共享写、持锁慢调用、整批等待和恢复空窗用于校准本次方法。本 Task 不据个案声明全部同名机制有害，也不承担业务代码修复或生产根因闭环。

## 3. 目标与非目标

以一个完整规范修改单元增强原方法及必要消费点，使设计先推导最直接完成路径，再决定是否保留额外协调。保留必要权限、资金、幂等与恢复约束。

不新增 Skill、阶段、审批角色、公共 DTO、schema、生命周期字段、评分器、扫描器或固定问卷。不改 runtime/installer、业务代码、生产数据和 go-guru 依赖。backend 技术基线和业务投影另仓承接，公共 Guru 不复制其正文。当前本地工作不提交、推送或更新已安装项目，不以源码修改证明采用或生产改善。

## 4. 真实调用方、场景与流程

| 场景 | 调用方与前置条件 | 行为与结果 |
| --- | --- | --- |
| NC-S1 | Author 根据已接受行为形成候选 | 先建立直接完成路径；额外协调经过删除、收窄或已有能力比较 |
| NC-S2 | Architecture/独立审核检查实际机制及无 helper diff 的复用 | 独立尝试更简单方案并判断可行性，不只接受用途解释、旧测试或 CURRENT 自证 |
| NC-S3 | 保护资格已成立，候选仍增加等待或共享写 | Architecture 继续判断最小范围及完成成本，资格不自动成为方案批准 |
| NC-S4 | 审查已有机制必要性与成本 | 区分必要、已证缺陷和证据不足，沿原 owner 局部收敛；不危险删除或把未知当成功复用 |

使用原阶段及 typed exits。原方案已最小时说明依据，不虚构可行替代。

## 5. 行为要求

- **NC-R1 正常完成优先**：从可观察结果及必要业务、数据、权限和外部约束推导直接可行路径。异步方案覆盖最终结果可消费的完整路径，不能只比较受理响应。
- **NC-R2 默认不准入**：新增、修改、扩用及复用的额外协调，先证明更简单方案不能满足已接受要求。用途、泛称可靠性、名称、现有实现或技术测试均非充分依据。
- **NC-R3 主动淘汰**：Author 先尝试删除、缩小一致性范围、已有原子能力或更直接责任边界。独立审核自行判断替代，不只审核论证自洽；无可行替代或原方案已最小时说明依据。
- **NC-R4 正确性与成本共同成立**：核实际增加的 I/O、共享写竞争、串行阶段、队列等待及恢复前提，包含跨用户、资源和实例作用域。功能断言通过不豁免可避免成本；验证匹配真实不确定性，不普遍要求基准测试。
- **NC-R5 存量处置**：区分必要性已证、缺陷已证和证据不足。已证缺陷由原 scope/Architecture owner 承接有界整改与消费者适配；证据不足不授权危险删除，不作成功复用，也不扩大机制。
- **NC-R6 单一正文**：增强原 Adopted-mechanism review；Root Cause 与 Author 仅承接必要消费。其他现有引用有效时不复制条款，不建立第二准入层。
- **NC-R7 验证分层**：以命中案例检查拒绝可避免成本及保留必要机制。源码、定向验证、分发、安装采用和业务效果分别报告，不新增全平台或业务性能矩阵。

## 6. 约束与依赖

保留原 Guru owner、正常场景/机制/根因资格职责、独立架构读取顺序及公共合同。方案必要性不由关键词或名称扫描器决定。原 RDT/Architecture owner 按真实影响维护所属完整单元，候选与共享 current 晋升边界保持。

没有 API、持久化字段或运行单元变化，因此没有业务迁移或部署步骤。安装采用与业务修复不作为本地源码修改前置，也不标记已完成。

## 7. 可观察验收与验证方式

| 验收 | 要求/场景 | 入口、输入及预期结果 |
| --- | --- | --- |
| NC-AC1 | R1—R4；S1—S3 | 通过当前 Author/Architecture 方法审查共享写、持锁慢调用及整批等待案例：判断完整正常路径，拒绝无依据额外成本，保护资格不替代取舍 |
| NC-AC2 | R3、R5；S2、S4 | 检查原方案已最小、必要短事务及证据不足案例：不虚构可行替代，不按名称禁用，不直接删除或批准未知机制 |

验证消费现有 Test And Validation Value 和本仓验证职责。案例用于当前语义判断，不新增永久矩阵，不以文字自比较证明方法有效。
