# 准备 Guru Trellis v0.7.0-guru.12 正式发布

## 1. 来源与术语

| 来源 | 角色 | 用途 |
| --- | --- | --- |
| [#924](https://github.com/castbox/guru-trellis/issues/924) 的「发布目标」「准备与候选」「验收」 | 要求 | 定义版本、范围、候选和本地安装条件 |
| `.agents/skills/release-guru-trellis-version/references/contract.md` 的 Two-Stage Lifecycle | 设计约束 | 定义准备源码、安装采用、正式发布与关闭的顺序 |
| `v0.7.0-guru.11` 与准备起点 `6825949699d342eba1ad018ee04a8f9396f11619` | 事实 | 分别定位正式前驱与准备基线 |

扩展版本标识 Guru Team 分发内容。Trellis CLI 版本和 source lock 标识其依赖的 Trellis 构建。

## 2. 背景与问题

当前已发布 `v0.7.0-guru.11`。远端 `main` 已有后续变更，扩展的 canonical 版本仍为 `0.7.0-guru.11`。正式发布需要先完成 .12 的版本准备与实际安装采用。

## 3. 目标与非目标

本 Task 将可分发源码及实际 dogfood 安装交付到 `main`，完成准备任务的收尾归档。后续发布由 #924 和私有发布合同承接，包括最终候选、tag、冒烟验证、Release、本地安装收敛与 Issue 关闭。其他 Issue 的完成、合并、关闭或归档不构成本次准备的前置条件。

## 4. 真实调用方、场景与流程

- S1：维护者从已核实的远端 `main` 开始准备，交付 .12 canonical 版本、公开说明及可安装的源码，供安装采用读取。
- S2：维护者在 S1 实际交付后，使用完整且干净的已交付源码运行 `guru-upgrade-tools`。准备仓库保留实际安装结果，供合并后正式发布候选验证。
- S3：全部准备交付完成并合并，维护者完成整体审核及归档。发布负责人之后重新获取远端 `main` 并冻结候选。

## 5. 行为要求

- R1：核实目标 tag、前驱、扩展版本、CLI 版本和 source lock。准备公开安装说明和受管源码，并验证源码可分发、可安装。
- R2：采用完整且干净的实际交付源码，验证目标的扩展版本、实际来源、CLI、受管内容以及保留边界。工具采用失败时由原 owner 恢复，准备工作仍未完成。
- R3：准备 Task 以 `reference_only` 关联 #924，准备 PR 使用 `Refs`。准备验收后通过原 Task Completion 与 Finish 完成归档。正式发布以归档合并后重新获取的远端 `main` 为准。

## 6. 约束与依赖

遵循现有两阶段发布合同与标准 Guru Team 生命周期。源码交付先于实际安装采用。只有在候选版本与 source lock 一致时，既有固定 Trellis CLI 才能继续使用。准备验证采用与发布范围匹配的验证项。

## 7. 可观察验收与验证方式

- AC01（R1、S1）：对实际可分发源码执行 source 检查、平台投影核对及定向安装。版本、公开说明、source lock 和已安装结果一致后，源码交付合并至 `main`。
- AC02（R2、S2）：以 AC01 实际交付的干净源码执行 `source_locked` 工具采用。读回准备仓库中的真实受管内容、扩展版本、来源和 CLI；验证通过后将应跟踪的安装结果交付至 `main`。
- AC03（R3、S3）：原 Completion 核对 AC01、AC02 及真实交付结果，Finish 将终态归档合并到 `main`。此时 #924 仍开放，可以进入正式候选阶段。

## 8. 实际未决项

整体要求没有待决项。最终发布 commit 和 tree 在准备工作归档合并后取得。
