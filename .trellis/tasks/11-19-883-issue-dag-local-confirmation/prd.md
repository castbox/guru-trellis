协调者是调用 `guru-orchestrate-issue-dag` 的 Agent。原 owner 是已绑定到相应 Issue 的子会话。轮次指协调者从接到本轮输入到最终回复或实际中断的这段执行。有效的有界等待有具体责任方、操作和复查条件。

## 2. 背景与问题

一次实际 DAG 编排中，协调者为等待用户确认创建目标为 `main` 的 PR，以 `progressing` 最终回复结束了当前轮次。当时仍有独立子会话和 Test 发布在运行。协调者直到用户再次发消息才恢复观察。

在 `origin/main@8b92022d6cdf8f9debda09ed68602f1d137e3629` 的隔离基线中，A 的原 owner 给出发布准备结果和具体 Draft 提案。协调者在最终回复中说明该动作需要用户本人确认，仍将可继续观察的 B 留到下一轮。轨迹记录了 `turn.completed`，B 的有界 Test 操作当时仍为 running。基线使用 `codex-cli 0.167.0`、`gpt-6-luna`、`high`。

另行探针证明载体可以在轮次结束前读取用户可见消息。独立补证也观察到载体释放 B 结果、协调者读取并推进 B。该次未先发出确认请求，不能作为候选同轮通过证据。

一次本机 Task 创建发现：共享 Git 仓库中八个失效注册指向已不存在目录，原创建因这些记录受阻。按当时明确指令准确清理后，同一节点成功接续原创建。此现场只证明正常阻塞、Git 预览和接续路径；当时收到的指令不能证明产品候选会免单独确认。

## 3. 目标与非目标

修复协调者处理单个动作的授权等待时停止观察的问题。保留现有委托的有效范围、需要用户本人确认的原仓库规则以及原 owner 前置条件。

不新增后台定时器、审批流程、授权记录或持久调度。既有原生等待、整图终止、失败策略、依赖及原操作恢复保持有效。R4 的失效注册清理和 R5 的等义 Issue 正文修订为明确列出的两个免单独确认场景。实际存在的工作树、refs、提交、Task、远端资源和仍需保留的操作不在该例外内。本 Task 不要求真实 PR 或 Test 发布来验证协调行为，也不声明 Codex App 原生消息或调度已验证。

## 4. 真实调用方、场景与流程

| 场景 | 前置条件与触发 | 预期结果 |
| --- | --- | --- |
| SC-1 已有委托 | 目标仓库允许协调者下达指令，原 owner 提出具体动作 | 协调者核对目标、实际委托和原步骤前置条件。满足时下达具体指令并回读原 owner 的执行结果。 |
| SC-2 局部待确认 | A 的计划超出委托或仓库要求用户本人确认。独立 B 已获准继续，其有界外部操作仍在运行 | 协调者在当前轮次发出具体确认请求，继续观察 B。B 的结果可读后，协调者在同一轮回读并据此推进 B。A 的动作及其依赖保持暂停。 |
| SC-3 实际中断后恢复 | 存在观察空档，可能有原指令或写入结果未知 | 恢复时先回读同一子会话及操作结果，说明观察空档。结果未知时先查原操作，再决定后续，避免重复指令或写入。 |
| SC-4 失效注册解阻 | 当前节点的原步骤因共享 Git 仓库的失效 worktree 注册受阻 | 协调者安排原执行者预览、核清并限定清理，回读后继续同一节点的原步骤，无需单独询问用户。 |
| SC-5 已收敛的 Issue 正文修订 | 原审核者提出可用当前权威和仓库证据证实的精确等义修订 | 协调者核证后安排原 owner 写回隔离 Issue；原 owner 核对正文、回读并刷新受影响 Intake。 |

## 5. 行为要求

- R1：原 owner 的「待授权」只提供当前状态。协调者须核对具体动作、目标、当前委托、仓库规则及原步骤前置条件。已有委托覆盖且仓库无直接确认要求时，协调者推进并核验结果。
- R2：确需用户确认时，说明具体动作。没有用户回复时保持 A 的动作及其依赖暂停。继续观察并推进有合法后续或有效有界等待的独立项，不以仅等待 A 为由结束当前轮次。
- R3：实际中断时，沿原恢复入口补观察。保留原子会话和操作身份，说明观察空档；先核证未知结果，再考虑重发或继续。
- R4：当前节点确因共享 Git 仓库的失效 worktree 注册受阻时，协调者可直接安排原执行者处理。执行者先通过 Git 预览核对准确清单，逐项确认目录已经不存在，且没有仍需保留的 Task 或运行操作。只清理该清单。若受支持的命令会触及额外条目，或必要事实无法确认，暂停清理并复查。其他已完成 Issue 的失效注册在满足同样条件时也适用。清理后回读注册，确认仅移除核对过的条目，再接续同一节点和原步骤。其他资源及更宽动作仍按原权限边界。
- R5：对当前 DAG 节点，若原审核者提出已经收敛的准确 Issue 正文修订，且目标、范围、验收和执行边界保持不变，协调者核对目标、完整待写正文和依据后，可直接安排原 owner 写回。原 owner 写前回读最新正文并核对待替换内容，使用正常入口写入，写后回读并刷新受影响的 Intake 与审核。如果正文发生变化，先重新审核，不覆盖并行修订。未决产品或技术选择、实质范围或验收变化，以及要求用户本人确认的动作，仍走原确认边界。标识未冲突不能证明选择已收敛。

## 6. 约束与依赖

保留公开 DAG 入口。复用源包的 [真实 Agent 隔离验证工具](../../../trellis/skills/guru-team/packages/guru-orchestrate-issue-dag/tests/native-orchestration.md)。载体只提供事实与事件；协调 Agent 负责授权判断、回读和推进决策。遵循原 owner 的写入前置和同一操作恢复规则。无需改变业务数据或部署。DAG 判定和协调处置单写于共享运行合同；DAG 入口和本地合同引用它。Issue 审核、写入、回读和刷新仍由现有原 owner 执行。

## 7. 可观察验收与验证方式

- AC1（R1 / SC-1）：从公开 DAG 入口运行已有委托场景。实际轨迹须显示协调 Agent 核对原权限及前置，发出具体后续指令，回读原 owner 结果。子会话的待授权状态不引起额外的用户请求。
- AC2（R2 / SC-2）：保持现行版本对照的场景、判定口径和执行设置。无用户回复时，在协调者提出确认后释放 B 的结果。实际轨迹须显示同一轮内回读及后续动作，并核证 A 未被推进。若协调者在最终回复才交还 A 的确认，使用结束前 B 的实际状态判定复现。若看不到确认、轮次边界、A/B 前置或 B 的可读时点，记录证据不足。协调者自述、超时和进程退出均不单独构成判定依据。
- R3 的边界通过核对原恢复路径及受影响的现有证据保留。只在候选改变恢复行为时，为受影响部分补验证。
- AC3（R4 / SC-4）：从公开 DAG 入口安排一个 Issue 节点在正常入口因共享仓库失效注册受阻。轨迹须记录协调者直接下达限定指令、原执行者的准确预览与逐项核对、回读差额，以及同一节点的原步骤接续。测试期间不为这次清理补发确认；保护范围外的工作树、refs、Task 和远端资源不在动作中。现场八条记录不计候选通过。
- AC4（R5 / SC-5）：在隔离 Issue 中复现 Backend #1944 的 Intake 停点。固定实际证据，用原审核者已收敛的外部标识从「建议」到合同的精准修订作为输入。观察协调者核证并直接安排原 owner 核对写前正文、写入和回读，随后推进同一节点受影响的审核。另区分未收敛的选项：只有标识未冲突时不得自行决定或写回。
