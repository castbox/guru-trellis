# 需求歧义探索与分级确认整体需求

## 1. 来源与术语

Direct Source 为本次无 Issue 用户请求。用户明确要求：需求不明确必须确认，轻度问题由 AI 提供参考方案供简便确认；重大取舍说明选项，纯实现细节自主完成。本文件记录需求，不记录资源或执行授权。

| 来源 | 位置 | 角色与用途 |
| --- | --- | --- |
| 当前用户需求 | 当前会话关于需求歧义、轻度推荐确认及本地实现的消息 | 要求，定义目标行为 |
| 当前澄清合同 | `trellis/skills/guru-team/packages/guru-clarify-requirements/references/contract.md` 的 Questions And Convergence | 现有合同，保留逐项关闭及部分回答语义，调整提问组织 |
| 当前规划合同 | `trellis/skills/guru-team/packages/guru-author-task-plan/references/planning-body.md` 第2节 | 现有职责边界，明确技术细化不能代替需求选择 |
| 共享交互规则 | `trellis/presets/guru-team/spec/workflow/workflow-contract.md` 的 Interaction Budget | 现有合同，保留自然语言交互及独立副作用边界 |
| 兄弟模板 | 本次会话已核对的 requirement-exploration、decision-escalation | 方法参考，不整体迁入，不改变现有生命周期 |

“需求选择”影响目标、可观察行为、范围、兼容性或验收。“纯实现细节”是在既有约束内、不暗含需求决定或重大风险成本取舍的技术安排。“轻度”只降低确认成本，不免除确认。

## 2. 背景与问题

Guru 已支持证据先行、单问题循环、推荐及取舍。当前缺口是问题发现动作不够具体；严格单问题限制没有表达轻度推荐清单；Author 的技术细化规则可能被误读为自行决定需求。拥有 brainstorm 文件或完成 recorder/checker 不证明真实对话正确。

## 3. 目标与非目标

增强现有 Clarify/Author 的跨项目决策探索能力，适用于客户端、Web、后端及 CLI。通过具体例子发现歧义，按问题性质确认，回答真正影响方案及验收。

不创建平行 Skill、审批链、决策台账或授权记录。不修改 Trellis 上游、全局包或 hook。不修改业务项目，不执行项目升级；不包含 GitHub 写入或发布。此次只有一项完整能力，不将示例、验证和分发拆成独立产品范围。

## 4. 真实调用方、场景与流程

| 场景 | 前置与动作 | 处理与可观察结果 |
| --- | --- | --- |
| DEC-S1 | 用户提出简略需求，Clarify 调查已有事实 | 用正常例子与适用边界暴露不同解释，不要求用户猜仓库事实 |
| DEC-S2 | 存在轻度需求歧义 | 展示具体推荐行为及必要影响，用户可以简便接受或修正；未答时不实施依赖行为 |
| DEC-S3 | 存在影响行为、数据、兼容、架构、风险或成本的真实取舍 | 展示可行选项、推荐与代价，由用户选择 |
| DEC-S4 | 请求及约束已清楚，只有常规技术实现未定 | AI 自主研究与实现，不制造需求提问 |
| DEC-S5 | 用户只回答清单中的部分条目，或否定推荐 | 仅关闭实际解决的问题，更新需求、设计及验收，未答项保持未决 |
| DEC-S6 | Author 展开方案后发现新的需求歧义 | 回到原澄清职责处理新问题，不重新访谈已决定内容 |
| DEC-S7 | UI 调整未要求改变旧业务，设计稿未绘制旧状态 | 核对旧行为及来源，不仅凭画面缺失删除能力；真实冲突交用户确认 |

## 5. 行为要求

- DEC-R1：先调查事实与既有约束，再通过具体例子、受影响旧行为、相关历史和适用边界发现真实选择；不强制无关矩阵或额外问题。
- DEC-R2：所有尚未明确的需求选择必须确认，不因轻度、可逆或惯例而自动接受。外部系统实际行为先查证，不作为用户偏好。
- DEC-R3：轻度歧义提供明确推荐方案；同阶段且互不依赖的轻度问题可组织简短确认清单。依赖问题或重大取舍逐步询问。不得将独立条目伪装为不可分选择。
- DEC-R4：重大真实取舍提供可行选项、推荐理由、结果及必要成本风险；纯实现细节由 AI 自主完成。
- DEC-R5：推荐不是默认决定，未答不是同意，部分回答不能关闭未答项。仅暂停依赖问题的工作，独立调查可继续。既有问题生命周期及数据格式保持。
- DEC-R6：决定写回其所属需求或设计，前任务阶段保留在当前会话；恢复复用仍适用的决定。需求确认不代替独立副作用或实施激活边界。
- DEC-R7：沿用原 owner、现有公共接口与分发机制。修改 canonical 后同步工作区的 dogfood/安装投影，禁止一次性修改业务项目。
- DEC-R8：补充可执行的多轮交互验证，区分分发、结构检查与真实 Agent 行为证据，不以关键词命中判定语义正确。

## 6. 约束与依赖

Markdown 定义 AI 判断，脚本只做既定确定性动作。既有单问题方法与 Guru 轻度清单要求的衔接必须明确，不改 upstream-owned brainstorm。无公共字段、typed exit 或状态 schema 变化；必要关联入口必须同步，不能仅在新指南写规则而没有实际 consumer。

既有安装依赖完整 preset；本任务验证相关 package、分发与 drift，不承诺完整多平台发布矩阵。真实交互评测需要可用的 native Agent 执行入口；工具不可用时必须如实保留未验证项，不能以预写 transcript 冒充行为结果。

## 7. 可观察验收与验证方式

| 验收 | 对应要求 | 验证入口与预期 |
| --- | --- | --- |
| DEC-AC1 | R1、R2、R4 | 同一批正常请求包含事实可查、需求已清楚、轻度歧义及重大选择；只对真实未决需求询问，选项可执行 |
| DEC-AC2 | R3、R5 | 清单部分回答、拒绝推荐、明确接受及未答场景；逐项处理，不静默默认，不因一次确认关闭未答项 |
| DEC-AC3 | R5、R6 | 后续方案包含用户选择而非原推荐；恢复不重问有效决定，新歧义仍处理 |
| DEC-AC4 | R1、R6 | UI 例子保持未要求改变的旧业务，技术命名不掩盖需求取舍 |
| DEC-AC5 | R7 | canonical、dogfood、安装投影与引用一致，相关测试和 diff 检查通过；无公共 API/schema 无关变化 |
| DEC-AC6 | R8 | 报告真实执行的交互输入、结果及未验证边界；结构测试不被当作语义证明 |
