# 标准 Delivery 发布版对照实施与验证计划

## 1. 输入与引用

读取本批 `prd.md`、`design.md` 第3、5、6、8节，以及整体 PRD。复用 #826 的本地 CLI 样本和真实原生采集方法。按两发布 tag 的 README、preset 安装指南和实际 Fork lock 设置环境。正式分支从已固定的 `origin/main` 开始。

## 2. 有依赖顺序的步骤与文件责任

1. **冻结材料。** 实验负责人在隔离实验根准备固定业务树、三个有序样本、同一自然请求、评价规则及两侧中性标识。核对正向观察、停点、权限和六项计数。记录原样本与任何局部适配。评价标准不交执行 Agent。
2. **安装与准备。** 获取两侧发布 tag 与对应锁定 Fork，按各自发布说明构建。分别对业务副本运行匹配的 `node <fork>/packages/cli/bin/trellis.js init -y --codex --workflow guru-team --workflow-source gh:castbox/guru-trellis/trellis#<tag>`，再从对应 Guru tag 根运行 `bash trellis/presets/guru-team/scripts/bash/apply.sh --repo <副本>`。核对实际版本、来源和受管入口。通过各版原 owner 准备相同业务范围的正式 Task/Delivery。相同业务代码、数据和自然请求由一份去敏材料复制，固定业务树清单并记录各版本自己的安装文件差额。与真实 GitHub 读写相关的夹具依其实际资源和副作用边界准备。
3. **执行对照。** 两侧使用同一个可用 Codex CLI、模型及设置。先检查本机 Codex CLI 0.167.0 能用同一出入口保留足够的会话及必要独立审核事件，否则选用可记录该入口的受支持原生工具版本并同配两侧。用 `codex exec --json --cd <副本> --sandbox workspace-write -m <同一已核实模型> -` 输入同一任务材料并保留 JSONL。需要人作答时，以准确会话 ID 从支持的原生入口恢复，两侧使用相同动作许可规则。以版本自己的真实 owner 输出和待确认操作观察停点。将必要原生子审核记录与对应 invocation 链接。
4. **复核。** 在中性标识下核对阶段顺序、已做必要检查、业务输出、副作用、原失败和六项计数。固定比较范围后揭示映射。用实际源改动和记录解释归因，保留非三个专项可归因的差额。
5. **交付。** 在此 Delivery 下整理 `validation.md` 与 `validation-observations.md`。核对每项结论的观察定位与可复算性，必要时保留可复用的最小去敏输入和片段。只清理本轮对应实验实例，与证据分开保留。确认清理后仍可复核。

## 3. 验证入口、输入与预期观察

| ID | 实际入口及输入 | 预期观察与验收 |
| --- | --- | --- |
| V1 | tag 自身安装入口、固定 Fork CLI、公共 `delivery.py current --json`，两套相同业务起点 | 记录真实版本、投影和共同 Planning 起点，对应 AC1。外部依赖或安装失败按原错误保留。 |
| V2 | 原生 Codex 任务入口、三条 CLI 样本、真实 stage owner 命令和返回 | 观察 `show` 无参数、`--limit 0`、`--limit 2` 结果及存储不变。核对六项计数和适用的检查、审查及确认顺序，对应 AC2。 |
| V3 | 两侧实际记录、固定评价条件、版本 diff 与匿名评价 | 复核共同区间与差额。说明三项变更的归因边界、发布架构开销、归档及其他未到达步骤，对应 AC3。 |

实验是一组针对既定问题的观察。已有发布测试作环境与行为背景。实际结果依赖运行记录、可重算片段和正式 owner 返回。

## 4. 停止条件与适用回退点

出现不可用的匹配安装、缺失原生轨迹、未获批准的写入、合法非通过或实际环境失败时，记录阻断对象、阶段、原错误和受影响结论。可恢复的普通问题沿对应发布版原 owner 处理，保留首个失败。两侧均具备的共同区间回答对照问题后停止追加无关实验。需要合并时按本 Task 始终停在合并前的约束处理。没有正式合并证据时，将后续归档标为未到达。

## 5. Delivery Policy

full。首个 Delivery 覆盖 AC1、AC2、AC3，交付同场景对照、证据与可复核结论。按实际观察和已接受的提前停止规则核对范围。当前没有计划内后继切片。Delivery 合并后，仍由原 Completion owner 审核整个 Task 的证据和剩余责任。

## 6. Docs SSOT Plan

`no_docs_update_needed`。沿用 R826-01/02、D826-01、T826-03 的验证方法。本批新增实验记录及结论，由 Task 实施 owner 写入 Delivery 证据文件，由 Check、独立 Review 和 Completion 消费。若实际发现需要改变当前方法或产品边界，回原范围及 RDT/Architecture owner 处理。
