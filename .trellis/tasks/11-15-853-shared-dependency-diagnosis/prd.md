## 3. 目标与非目标

整体目标是确认当前原实施／影响评估 owner 对已知共享差额形成采用、适配或等待结论时，已有方法是否被实际加载并使用，及其内容是否足够。依据当前证据选择最小处理，取得适用行为证据。

完成有两条合法路径：确认消费或具体方法缺口后完成对应最小修复与行为验证；或者以足够的当前依据确认已有能力满足目标，无需追加规则。仅有诊断计划、历史原因或需求审查通过不算完成；仍需诊断时保留具体问题和下一步。

非目标：不预定新增方法文字、固定 gate、TaskCommit 准入检查、owner、阶段或 wrapper；不周期盘点全部 Task／工作树／PR／聊天，不增加协调状态、资源锁、全局 owner ledger、排队或轮询。不实施 #848/#850，不重交付历史业务适配，不重放原业务工作树、云端实验或模型请求。不展开恶意 actor、竞态压力、TOCTOU、崩溃一致性及无关 failure matrix。

## 5. 行为要求

**R1 诊断先于修复选择（SC3）。** 定位实际承担采用／等待判断的既有职责及入口，核对其到现有消费者／候选适用性正文的实际加载和使用路径。Author、Architecture 或实施职责仅在实际承担该判断时消费；不把所有相关 Skill 列为新增检查对象。不能从旧版本错误、正文存在或加长提示后的单次成功直接推定当前缺陷、所需修复或效果。

**R2 按真实线索有界调查（SC1、SC5）。** R1 调查只在已知实质变化影响当前对象／必要消费者，或具体结论缺少必要事实时展开。已有完整适用调查直接采用，只补变化或缺失事实。换 Agent、阶段、较新 SHA 和 dirty 文件数量不独立触发调查；无共享差额的工作继续原路径。

**R3 保留对象与证据身份（SC2）。** 已交付内容按实际提交／公开结果及当前相关内容判断；在途仅是观察草稿，不当作 baseline、另一方正式结果或必须采用的需求。只读判断所需差额并说明未证实边界，不新增持久快照、hash bundle 或跨任务账本。确需可复现整合时由原 owner 固定实际候选。冻结程序／旧 SDK 的成功保持原输入、依赖和环境，既有本地验证不因环境验证待补而失效。

**R4 从具体契约形成结论（SC1、SC2）。** 在原判断内核对实际适用内容：是否同一实现，两侧新增行为，共享函数签名与真实调用点，SDK／生成器与生成物配套，已有验证及组合缺口。不设固定表格、布尔维度或证明文件。同文件变化、同名测试、三方文本冲突仅是线索；无文本交集也可能要适配，重叠修改也可能等义整合。不得据此替另一任务决定 scope、实现 owner、批量能力责任或整项等待。

**R5 只保留必要依赖（SC1、SC4、SC5）。** 只有当前交付实际未满足的依赖形成先后关系，落到具体提交、接口或结果；独立部分继续。不把另一 Issue 整项 CLOSED 泛化为前置。真实 scope／时序选择回原 Clarify，技术兼容适配由原技术 owner 承担。

**R6 沿原修订与整合路径（SC4）。** 当前必须纳入的明确依赖、实际冲突、具体集成失败或用户同步请求沿 S5 处理。另一工作树草稿或未来消费者差额不自动触发 merge 最新 dev，不把 dirty 内容导成新基线。必要适配按已接受范围回原内容 owner。不得自动修改另一任务、发送跨会话指令、cherry-pick 未提交内容或接管执行。协作和 Git 副作用保持原边界。

**R7 按证据选择最小落点（SC3）。** 已有方法足够但入口未加载／判断未使用时，修正原入口引用或调用位置；已有方法已消费但具体内容不足时，只补原唯一正文的已确认缺口，例子沿原位置去敏；已有方法与当前行为已满足目标时不追加规则或入口；证据不足时继续有界诊断。仅实质修订回原受影响 owner 重新判断。不得在各 Skill 复制完整方法或把 TaskCommit／Publication 变为协调者。

**R8 聚焦验证并保持分发（SC1–SC5）。** 验证真正受影响的接口、生成链和组合，先判断原工程事实的适用性，再补必要缺口，不要求双方重跑全部测试／云端实验／模型请求。实际正文或入口修订保持唯一来源、必要引用、canonical／dogfood 及受影响平台一致，经原安装 owner 同步并定向验证；无修改不制造分发工作。无公共 API 变化不新增 schema／DTO／typed exit，真实变化须有明确迁移。示例不是用户回答、运行状态或当前通过证据。

## 6. 约束与依赖

原正常运行及诚实协作假设适用；正常 stale／mismatch、实现缺陷和兼容边界仍需处理。沿现有候选适用性、原 Check、独立完整 Review、readiness、Task Completion、Closure／Finish 和安装职责推进，不用脚本结果代替语义判断。PR／整体完成目标为 `main`，合并前等待协调器处置。

#736 的条件调用／固定基线、#822 的增量事实复用、#779 的协作边界继续适用；#747 的一般旅程方法不重复交付。相关 Issue 引用不增加整项硬前驱。#850 不由本 Task 实施，也不借此重加独立措辞或共享依赖 gate。

本项不预定公共数据、接口或持久化变更，因此当前没有预定迁移；诊断若发现必要变化，由原 owner 在既有流程内判断适用范围和兼容合同。技术材料、行为入口与验证安排由原规划／实施／审核 owner 细化，不将需求正文直接塞入行为测试 prompt。

不执行完整多平台 Release 矩阵；仅实际改动确需证明干净安装时，最多一个代表性 throwaway。正常副作用、敏感信息保护和不覆盖他人工作的约束继续有效，不写共享 journal 或无关 Task metadata。
