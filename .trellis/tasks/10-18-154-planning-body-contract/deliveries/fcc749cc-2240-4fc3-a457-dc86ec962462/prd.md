# #154 D1 规划正文合同与实际写作验证

## 1. 来源、术语与整体责任

本批需求来自 [Task 整体 PRD](../../prd.md) 与 [Direct Source #154](https://github.com/castbox/guru-trellis/issues/154)。Task 的公共 accepted_scope 是唯一整体范围；本文件展开本批，不形成第二份整体范围权威。Task、Delivery、Check、Review 等术语沿 [.trellis/spec/workflow/clear-technical-writing.md](../../../../spec/workflow/clear-technical-writing.md)。

## 2. 背景、目标与非目标

当前 Author 已拥有来源承接、来源设计矩阵、Delivery Policy 和 Docs SSOT Plan，但没有四类正文的章节、格式、适用条件、深度和裁剪骨架。原生 Task seed 是含 TBD 的初始文件；Planning chain fixture 明确只证明 transport。这些事实不足以证明规划已完整成文或原生写作已经通过。

D1 目标是全量交付四类正文合同/模板、带输入过程的完整示例、原 owners 接入，以及 V1–V7 的实际 Agent 写作/审核和定向安装证据。非目标沿整体 PRD 第6节：不新增 Skill、审批阶段、公共 DTO 或语言评分门槛；不改上游 seed/generator/hook；不重写历史归档；不自动修改业务仓；不发布软件或执行完整 Release 矩阵。

## 3. 本批起点、依赖与后续责任

这是首次 Delivery，尚无前序交付。起点为固定开发基线 main@`855f236850714edc4b78169218c09568c823f336`；PR 目标仍为 main，后续目标推进不自动改写本批内容基线。D1 覆盖整体 R1–R7 与 AC1–AC10，不把真实写作验证另留未分配切片。验证尚未执行；规划接受不能替代其结果。

依赖现有 #292 唯一 Author、#531 Task/Delivery、#250 来源与澄清、#599 清晰写作规范及 #263/#264/#265 文档 owners；当前源码已经具备这些边界。#153 的 Issue authoring 输入层是独立范围，不构成本批前置。不依赖业务方先重写简略 Issue。

D1 的实现、真实 V1–V7 与定向安装证据共同支持整体 Completion。若某个实际入口不可执行，原 Completion 必须保留对应缺口；不得仅因模板齐全、安装一致或 wrapper 通过就宣称整体完成。实际发现独立新目标时返回原 Clarify，不静默扩张本 Task。

## 4. 真实调用方、场景与流程

调用方为现有 Discovery、Clarify、Author、Wording、Architecture、Approval、实施、Check、Delivery Review 与 Completion。输入是详细、简略、无 Issue 或多来源的实际请求；状态包括全量 D1、部分/后续 Delivery、部分草稿、来源更新和恢复。

正常顺序为：Discovery 调查可查证事实 → Clarify 判断来源/范围并处理真实选择 → Author 按当前阶段加载正文合同和模板成文 → 原 Wording/Architecture/Approval 检查适用内容 → 接受后实施及原 Check/Delivery Review/Completion 实际读取必要引用。需求尚有真实缺口时回 Clarify；技术机制未定时由 Author/Architecture 设计。普通写作遗漏回最早受影响 owner。详细场景的前置、动作和观察见第6节 V1–V7，不虚构最终用户故事。

以下展开第6节各验收场景的正常调用关系；具体样例、执行入口和证据采集由 design 第8节及 implement 第3节承接。所有场景的当前状态均为待执行。

| 场景 | 调用方与前置条件 | 触发动作与处理行为 | 可观察结果 |
| --- | --- | --- | --- |
| V1 | Discovery/Clarify/Author；详细来源已区分规范要求、已约定设计、条件和例外。 | 以详细技术 Issue 进入原 Planning 链；Author 保留完整来源，编写整体 PRD、全量 D1 和实际设计，原审核核对每项承诺。 | 四类正文按适用合同成文，条件和例外未丢失；来源设计有唯一处置及具体落点，不能以编号覆盖代替。 |
| V2 | Discovery/Clarify；简略目标明确，仓库有可调查事实。 | 调查代码、调用方及现有文档；仅对剩余真实需求选择询问用户；需求明确后的技术细化交 Author/Architecture。 | 形成完整 PRD/design；调查依据和真正未决项可辨认，不编造事实或回答。无规范性来源设计时说明依据而不建空矩阵。 |
| V3 | 原 Intake owners；用户有明确请求但无 Issue。 | 从实际请求、仓库事实和必要澄清形成整体需求，再沿同一 Author 写作和审核。 | 不因缺少 Issue 降低正文深度，也不以创建或完善 Issue 代替 Planning；无来源设计时仍展开实际方案。 |
| V4 | Clarify；存在多个有明确角色的来源，且其中有真实冲突。 | 对照原承诺调查差异；由有权 owner 处置冲突；真实产品取舍由用户选择后再写作。 | 已接受内容全部保留；冲突处置有依据，建议、历史事实未升级为当前要求，较新文本未静默覆盖旧承诺。 |
| V5 | Creation/Author/Completion；存在合法切片及可读取的前序交付事实。 | 编写部分 Delivery 和后续 Delivery；读取整体范围、前序结果与当前状态，分别展开本批行为、设计差额和实施安排。 | 本批与排除项、输入、前序事实、剩余责任和整体 Completion 条件清楚；不会用复制全量 PRD 掩盖部分交付。 |
| V6 | 原来源/阶段 owner 与恢复会话；来源发生普通更新或已有部分规划，Task/Delivery 身份可由原 owner 解析。 | 重新读取当前来源并判断实际影响；仅更新受影响阶段。恢复会话通过原 Bind/Selection 读取同一切片、模板及正文必要引用。 | 新要求与历史验收不混淆，身份和历史不变；实际读取可观察，不以文件存在或旧结果替代。 |
| V7 | 原审核 owner；正常写作遗漏或原入口支持的未完成规划尚未被接受。 | 将实际草稿交原审核；识别具体缺口，返回最早受影响 owner，由 Author 修订后重审。 | 缺口不会被当作完成；最终正文补齐并保留语义，不靠篡改已接受 artifact 或预填审核结论构造成功。 |

## 5. 本批完整行为、条件与设计约束

以下直接保留当前来源的 R1–R7 正文，适用于本批全部范围。共享定义和原始证据按明确引用读取，不能把本节改写为仅有编号或摘要。来源设计的最终处置仅由 [design.md](./design.md) 维护。

### R1. 为各类规划产物建立明确的正文合同

修订现有 Author 写作合同及适用的正文骨架，补齐 Task PRD、Delivery PRD、Delivery design、Delivery implement 四类正文模板。现有 Author 必须唯一拥有这些模板，并在对应写作入口显式加载。每类模板须规定章节、顺序、格式、填写要求、适用条件和必要深度。模板还须说明如何使用来源和引用。

四类模板可以共享章节定义、填写规则和现有 STE 中文写作规范。每类模板仍须明确必要章节、差异内容及裁剪条件。可以按明确的适用方式复用同一模板，也可以组合共享内容与阶段专属内容；不要求拆成四个独立文件，不复制两套公共规则。复用不得省略 Delivery 的阶段内容和关联上下文。

| 产物 | 正文职责 |
| --- | --- |
| Task `prd.md` | 承载完整、已接受的整体需求、问题上下文及来源。保留来源中的已约定技术约束，并交由 Delivery design 承接其设计落点。 |
| Delivery `prd.md` | 完整说明本批需求、场景、范围、验收和关联上下文。明确它与整体需求、前序交付及剩余工作的关系。 |
| Delivery `design.md` | 完整说明本批要求如何落到实际系统。承接来源已有设计，展开职责、接口、数据、状态、流程和必要的技术细化。 |
| Delivery `implement.md` | 给出可执行的改动顺序、文件或模块责任、验证入口与预期观察、依赖及回退点。保留原 Delivery Policy 与 Docs SSOT Plan。 |

继续使用当前 Task/Delivery 职责。整体需求由 Task PRD 承载，当前技术方案由选定 Delivery design 承载；不新增 Task 根 design 或 implement，不建立第二套方案或实施计划权威。

简单任务可以简写正文。项目类型和复杂度决定条件章节的深度。裁剪规则必须明确，不得由 Agent 随意省略必要章节。确实不适用的内容须说明理由；适用内容必须展开。

草稿、初始文件和正常返工可以暂有缺口，但须标明具体缺口及待处理责任。各产物须在其原有接受边界前补齐当前阶段的必要内容：

- Task PRD 在 Author 返回 `scope_requirements_ready` 前完成整体需求写作，由原 Clarify 复核后执行 `accept_scope`。该步骤不要求 Delivery 方案已完成。
- Delivery PRD 在当前 requirements 阶段完成本批需求及上下文，不要求提前完成尚未开始的方案章节。
- Delivery design、implement 在 Author 返回 `plan_ready` 前完成适用内容，再进入原 Wording、Architecture 和 Approval。

空标题、TBD、笼统的“沿用原方案”及预填通过声明不能作为完成正文。非阻塞的后续观察须与尚未解决的必要问题区分，不为填写未决项而制造问题。

### R2. 明确 PRD、design 和实施计划的必要内容与格式

下表是模板必须承接的内容基线。模板须将其落实为明确章节，并标明始终适用和条件适用的内容。

| 文档 | 必须覆盖的内容 |
| --- | --- |
| PRD | 来源与术语；背景和问题；目标与非目标；角色或真实调用方；场景和业务流程；行为要求；条件、例外与失败结果；约束和依赖；可观察验收；实际未决项。 |
| design | 设计目标与需求承接；当前系统及改动边界；来源设计处置；模块和职责；接口与数据；状态及执行顺序；正常和失败流程；适用的恢复、兼容及迁移；验证设计；设计取舍和实际未决项。 |
| implement | 实施顺序与依赖；文件或模块责任；实际验证入口与预期结果；适用的回退点和停止条件；Delivery Policy；Docs SSOT Plan。 |

使用 Markdown 标题组织正文。要求、验收、场景和接口等需要逐项核对的内容，采用稳定定位及明确字段。已有来源编号可继续使用。正文中的相互引用须能定位到实际章节或条款。

场景须说明调用方、前置条件、触发动作、处理行为及可观察结果。流程存在分支、顺序或状态变化时，须将关系写清；图表用于帮助理解，不能替代必要说明。

存在真实业务角色和用户价值时，写明用户故事及验收场景。工程变更使用真实调用方和“触发条件 → 行为 → 可观察结果”，不伪造最终用户故事。

每项验收须能对应需求和验证方式。设计须让实施者理解实际改动，审核者能够核对行为、接口和约束。章节齐全、矩阵存在、编号覆盖和文件非空均不能单独证明内容充分。

### R3. 按来源充分性调查、澄清和成文

| 输入情况 | 原 owners 必须执行的行为 |
| --- | --- |
| 完整 Issue 或其他完整来源 | 保留适用原文，或作等义组织和改写，将全部已接受内容纳入 R1/R2 的对应章节。来源原结构不免除规范要求。 |
| 简略 Issue 或部分内容缺失 | 先调查可查证事实，再澄清影响需求成立的真实缺口。保留已明确内容，补齐形成完整 PRD 所需的信息。 |
| 无 Issue 的请求 | 从当前请求、仓库事实和实际澄清形成完整 PRD，遵守相同章节、格式及充分性要求。 |
| 多来源、分散讨论或来源冲突 | 区分来源角色，整合已接受内容，并解决实际冲突。不能仅因文本较新或较短而静默覆盖已有承诺。 |

Discovery 负责事实调查。Clarify 负责需求、来源角色、范围和真实选择。Author 负责正文写作与方案细化。Architecture 保持其原有判断职责。

代码、文档、调用方及历史记录能够回答的问题，先调查。涉及真实产品选择或范围取舍时，由原 Clarify 询问用户。未知事实不得写成已确认要求，也不得编造用户回答。

区分需求缺口与方案未定。需求没有明确时，先澄清。需求明确但实现机制未定时，由原 Author/Architecture 设计，不要求用户预先提供技术方案。

必要问题尚未解决时，保留具体缺口并沿原 owner 阻塞依赖工作。不得用默认值、空章节或任意假设宣称规划完成。

### R4. 在统一结构内完整承接详细需求和来源设计

正文必须保留已接受来源中的背景、场景、行为、完整条件、否定、例外、执行顺序、义务强度、约束、依赖、非目标和验收。来源中的接口、机制、职责或兼容决定已被原 owner 选为规范性约束或已接受方案时，必须保留并在 design 中给出实际落点。建议和候选仍按其原角色处理，不因包含技术细节而自动成为强制要求。

为符合正文结构和中文写作规范，可以重排章节、拆句或等义改写。每次整合和改写均须核对语义完整性。不得先将详细来源缩成摘要，再仅从摘要推导需求和设计。

区分规范性要求、已约定设计、建议、候选、历史事实和原始证据。采用来源不等于把全部评论或历史材料升级为当前要求。需要保持原样的命令、标识符、接口消息、引用及原始证据按现有写作规范处理；呈现时继续遵守脱敏规则。

存在规范性来源设计时，由 Delivery design 维护唯一来源设计处置矩阵，定位保留项、实际落点和偏离。没有规范性来源设计时，在对应章节说明依据，不创建空矩阵，也不把建议升级为规范性约束。无论是否存在来源设计，design 正文都须展开本批适用的行为、接口与执行过程，不能只写“保留”或宽泛编号。真实范围变化返回原 Clarify；Architecture 冲突和其他约束偏离由原 owner 处置。

### R5. 每个 Delivery 都完整说明本批工作及关联上下文

全量 D1、部分 Delivery、后续 Delivery 和同一 Delivery 返工均适用 R1/R2。全量 D1 不因覆盖全部要求而免除必要章节。

Delivery PRD 除本批需求和验收外，必须说明：

- 整体目标和本批独立交付目标。
- 本批覆盖的整体要求及明确不包含的工作。
- 前序交付、当前状态和本批起点；首次交付说明尚无前序交付。
- 依赖、输入、边界及未交付责任。
- 本批结果如何支持后续交付和整体 Completion。

Delivery design 必须说明本批起点和目标状态、已有能力与本批差额、实际改动，以及适用的前后交付接口、兼容关系、集成和验证安排。新会话的实施者和审核者应能通过正文及其明确引用理解当前工作。

允许复用原文和引用共享内容。引用须可解析到已接受的本地内容或明确的 canonical authority。Delivery PRD 须写清本批适用的行为、条件、约束和验收；design 须展开实际设计落点；implement 须给出本批实施与验证安排。共享定义和完整接口规格可以明确引用，各文档不重复承担彼此的正文职责。仅列来源链接、要求编号或数条摘要不能替代本批正文。引用内容在实施和审核前必须实际加载，必要的关联条件也须读取。

重复采用已接受内容不产生新的范围权威。继续使用公共 `accepted_scope`、Delivery `scope_ref/planning_root` 及原返工和 freshness 规则。来源更新由原 owner 判断实际影响，仅刷新受影响阶段。历史交付及旧验收保留其历史身份，不能与当前适用要求混淆。

### R6. 全部规划文本遵守现有 STE 中文写作原则

统一引用 #599 已建立的 `.trellis/spec/workflow/clear-technical-writing.md`。不另建语言规则副本。

正文须明确执行者、动作、对象、触发条件和结果。同一概念使用同一术语。要求、建议、事实、计划及未验证结论必须可区分。一个句子表达一个主要意思；必要的复合条件须保留完整逻辑关系。

准确性和完整性优先于简短。不得为缩短句子或篇幅删除条件、否定、例外、顺序、义务或兼容边界。现有强制规则、建议及例外保持原强度，不增加字数、句长、词表或机器评分门槛。

原写作 owner 输出前自检。原审核 owner 在各自范围内检查表达与语义。采用 STE 的中文清晰表达原则，不宣称中文符合 ASD-STE100，也不新增通用语言审核 owner 或认证。

### R7. 由原 owners 接入模板、审核和下游读取

模板及完整示例由现有 canonical Author package 唯一维护，并通过原受管分发安装。入口必须实际加载适用正文合同。原生 seed 只负责初始文件；创建脚本不判断需求含义或哪些内容可以删减。模板通过 Guru 原 Author 和受管分发接入，不修改上游生成器。

提供去敏的完整写作示例，展示来源、调查或澄清结果、按规范形成的正文、切片、设计细化及审核修订。至少包含详细技术来源和简略来源的处理，不能只提供空标题、公共 DTO 示例或缺少输入过程的理想成品。可参考 Spec Kit 和现有 Guru 需求、概要设计及详细设计实践，但不自动引入其完整门禁或业务私有正文。

原 Author、Wording、Approval、实施、Check、Delivery Review 与 Completion 在各自职责内核对章节和格式、内容充分性、来源承接及实际读取。正常遗漏必须返回最早受影响 owner。技术细化不得被误判为产品范围变化，也不得借此改变来源约束。

三份 Delivery 文档保留命中的 repo requirement/behavior、design、test 和 Architecture Baseline 的最小 canonical 引用及本轮差额。长期 Requirements/Design/Test 和 Architecture SSOT 仍由原 owners 沿 #263/#264 的 contribution/promotion 路径维护。

模板填充本身只生成选定 Task/Delivery 的规划正文，不直接修改 shared docs README/index/manifest、Architecture Baseline 或 spec projection，也不预创建空 contribution 或 ownership ledger。Author 按现有合同编写真实任务独占 Architecture contribution 或必要 ADR 候选的职责保持；RDT 贡献、共享晋升和 Bootstrap 仍由原 owners 按原合同执行。

若确需改变 public Skill I/O 或其他公开合同，必须明确迁移和 consumer 适配。不得静默改变既有语义或新增第二份范围权威。

## 6. 本批验收与实际未决项

每项 AC 的需求关系、验证方式与预期观察由以下完整来源合同约束；执行顺序、命令与文件责任由 [implement.md](./implement.md) 细化。当前无未决产品或范围选择。实际验证结果尚未产生，不预填通过。

### 6.1 验证要求

#### 6.1.1 实际 Agent 写作与审核

通过受支持的正常入口触发现有 Planning 链，让 Agent 实际调查、澄清、写作和审核。覆盖下列场景：

| 场景 | 必须观察的结果 |
| --- | --- |
| V1：详细技术 Issue | 来源同时包含需求、部分设计、条件和例外。整体 PRD 和全量 D1 均符合规范；全部已接受内容有实际正文承接。 |
| V2：简略 Issue | Agent 调查仓库事实，完成必要澄清，再形成完整 PRD 和可实施设计。未猜测缺失事实或编造回答。 |
| V3：无 Issue 请求 | 原 owners 从实际请求形成完整需求及设计，遵守同一写作规范。 |
| V4：多来源与真实冲突 | 已接受承诺完整，冲突得到处理，建议和历史事实没有被升级为要求。 |
| V5：部分及后续 Delivery | 本批正文、关联上下文、前序事实、剩余责任和整体 Completion 关系清楚，范围没有丢失或静默扩张。 |
| V6：来源更新、已有部分规划及会话恢复 | 使用当前适用来源、模板和切片；历史事实保留，只刷新受影响阶段。新会话实际读取必要引用。 |
| V7：正常写作遗漏与修订 | 将正常写作产生或原入口支持的未完成规划交给原审核，实际识别其具体缺口并沿原路径修订。最终正文补齐内容并保持语义。 |

场景可复用同一验证环境，不要求逐场景新建安装或 Task。样例覆盖简单工程变更与需要展开设计的复杂变更，以检查裁剪和深度要求。

不得由测试宿主预先写好最终文档或通过结论，再把 wrapper/schema 通过计为实际写作成功。只处理受支持的正常路径、普通遗漏、stale/mismatch 和正常恢复，不引入恶意篡改、攻击、压力或非常规故障场景。

#### 6.1.2 定向工程与安装验证

验证 canonical、dogfood、installed 和声明平台的受影响投影。核对完整匹配安装中的模板加载、引用、reapply/drift、sidecar 及用户自有内容保留。需要干净安装证明时，最多使用一个代表性 throwaway。

至少选择一个当前支持、具备实际写作和审核执行能力的平台，完成 V1–V7 的适用链路，并说明使用的入口、模板、正文、实际修订和结果。缺少必要的实际行为证据时，保留对应验收缺口，不能以文件一致或脚本通过代替。

实际 Agent 写作与审核、确定性检查、安装投影分别报告。代表平台结果不得推定其他平台的实际行为。完整多平台升级及 Release 矩阵继续由专门 Issue 承担。
