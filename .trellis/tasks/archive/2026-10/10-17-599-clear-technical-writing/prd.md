# #599 Guru Team 清晰技术写作规范

## 来源

唯一 Direct Source：https://github.com/castbox/guru-trellis/issues/599。以下完整承接当前 Issue 的要求与验收；不弱化 AC5。

## 整体责任

以 dev 为开发基线，交付规范、受管分发、入口加载和实际行为验证。保留 #57/#78 中文政策；规范不改变功能需求、兼容合同、原审核范围或公共 I/O。

## 目标

让 Guru Team 的 Agent 使用清晰、准确、一致的语言撰写文本。

建立一份基于 STE 原则的双语写作规范。通过现有 preset 分发规则。主会话和子 Agent 在输出前读取并执行规则。

## 当前依据

- 合同措辞审核只覆盖其声明的固定范围，不能替代所有文本的语言审核。
- #57 定义中文文档政策，#78 定义中文审查报告政策。本 Issue 保留这两项政策和仓库现有的中英文分工。
- 共享规则沿用 canonical preset 与 managed-spec 分发机制。语义判断继续由 AI 执行。

## 要求

### R1. 定义规范和标准来源

建立“Guru Team 清晰技术写作规范”。

中文采用 STE 的清晰表达原则。不得宣称中文符合 ASD-STE100。

英文参考一个明确版本的 ASD-STE100。编写者须核对正式来源，并记录版本、采用条款和适用边界。本 Issue 不承诺完整实施或认证 ASD-STE100。未取得或未核对的条款不得标为已采用。

每条项目规则须具有稳定编号，并标明强制或建议、适用内容和例外。建议不得作为阻塞条件。不得仅凭句长、关键词或扫描结果判断合规。

规范须覆盖：

- 一个句子表达一个主要意思。
- 操作指令明确执行者、动作和对象。
- 条件行为明确触发条件和结果。
- 同一概念使用同一术语；不同概念保留区别。
- 要求、建议、事实、计划和未验证结论使用可区分的表达。
- 中文和英文的正反例说明改写理由。

### R2. 定义内容范围和例外

规则适用于 Agent 新写或修改的全部自然语言内容：会话回复、文档、workflow、skill、prompt、代码注释、面向用户的提示、Issue 和 PR。模板中的自然语言及 Agent 编写的程序提示文本也在范围内。

仅为改善表达而改写时，命令、路径、代码标识符、schema 字段、公共 API 名称、typed exit 和精确匹配的接口消息保持字面内容。

已由功能需求授权的接口或标识符修改继续遵循原有变更与兼容合同。本规范不得阻止该修改，也不得自行授权该修改。

外部引用和用户要求原样保留的内容不因语言润色而改写。原始日志和原始证据的本体保持原样。新增的说明遵守规范。

保留原文不要求复制或公开原始记录。对外呈现继续执行现有脱敏、权限和敏感数据保护规则。脱敏后的摘录须标明省略或替换，不回写原始证据本体。

为使本规范生效而修订相冲突的现行写作指令属于范围内工作。此项工作不包含无关历史文本重写。

修改文件时，检查本次变更及理解它所需的上下文。不得因此要求重写整个文件。历史归档、旧证据和不可变版本不追溯改写。

用户明确指定的原文、格式和输出用途须保留。具体写作规则只在其适用条件成立时执行。

### R3. 保持业务语义

改写须保留业务含义、义务强度、条件、否定、例外、执行顺序和兼容边界。

准确性优先于简短。不能保持原意时，保留准确表达。Task、Delivery、Check 和 Review 是不同概念，不得合并。

术语表须区分项目用语与必须保留的公共名称。规范不得将表达偏好升级为业务要求，不得通过删减文字移除未验证边界。

### R4. 分发并加载规则

在 canonical preset 中维护唯一可复用正文，并通过现有 managed-spec 机制安装到目标仓库。本仓库 docs 记录需求、设计、验收和正文定位，不复制规则正文。

设计须列出 canonical 路径、安装路径、加载入口和直接 consumer。workflow、平台入口和 skill 引用同一正文，不重复内部规则。

受支持入口须要求 Agent 在首次生成实质文本前读取完整规范。实质文本指需求、方案、代码说明、审查结论、Issue、PR 和任务答复正文。覆盖无 Task 会话、正式 Task、task-free、独立 Git/GitHub 操作、会话恢复和子 Agent。

入口中的简短规则须约束加载期间的进度提示与缺失诊断：使用短句，明确当前动作或缺失项，不作未经验证的结论。这两类提示不以完整规范已读取为前提。完整规范读取前，不得生成实质文本，也不得宣称已执行完整规范。

子 Agent 不得假设已继承主会话上下文。设计须说明现有原生上下文注入和子 Agent 自行加载各自的适用条件，并验证实际使用的路径。规则缺失或读取失败时，只报告具体缺口并暂停受影响的实质文本生成。读取成功后继续原任务，不新增审批。

本仓库入口保留简短强制规则与定位。安装和 reapply 须保留目标仓库的用户自有指令。

同步 canonical、dogfood、installed 和声明支持的平台投影。说明已有安装如何采用规则，以及 reapply、upgrade/update 的保留与冲突处理边界。源码修改不得被描述为旧安装已经更新。

### R5. 接入现有写作与审核职责

写作 owner 在输出前自检。审核 owner 只检查其原有范围内的文本。会话回复由当前 Agent 自检。

保留 guru-review-contract-wording 的固定范围、前置条件和 typed exits。它不承担通用语言审核。

AI 判断表达是否清晰、语义是否保持。脚本只验证分发、引用、投影和已定义的机械条件。

审核按以下边界处理：

- 歧义改变执行行为、遗漏必要条件或弱化要求时，按 correctness 问题处理。
- 违反适用于当前内容的强制规则时，要求修订。
- 仅违反建议，或另一种表达同样清晰时，不作为阻塞 finding。

## 验收

| 编号 | 通过条件 |
| --- | --- |
| AC1 | R1 的标准来源、版本、采用条款和项目规则可核对。每条规则标明强制或建议、适用条件和例外。无未经证明的完整 STE 合规声明。 |
| AC2 | 规则正文只有一份 canonical 来源。完整安装后的引用均可解析。声明支持的平台投影及 R4 所列入口均有明确加载路径。 |
| AC3 | 中英文正反例覆盖指令、条件、术语、要求与建议、未验证结论。示例映射到规则编号。AI 逐例说明语义保持或修订原因。 |
| AC4 | 语言改写保留条件、否定、例外、顺序和义务强度；字面内容按 R2 保留。示例证明写作规则不会阻止已授权的功能修改，不会要求公开敏感原始记录，也不会把建议或不适用规则升级为业务要求。脱敏摘录与原始证据本体可区分。 |
| AC5 | 选定一个当前支持且具备子 Agent 能力的平台，实际验证主会话首次实质输出、会话恢复和独立子 Agent 的加载与输出。主会话覆盖无 Task 和有 Task 两种上下文。验证加载期间提示、规则缺失诊断及读取成功后的继续行为符合 R4。验证复用已有或专用测试环境，不为本次 Issue 创建无业务意义的 Task。仅文件一致不能证明行为通过。 |
| AC6 | 在匹配的完整安装中验证分发与 reapply，并执行 dogfood drift 检查。逐项处理产生的 .new/.bak。验证目标仓库用户自有指令保持原样。需要 clean 安装证明时，最多使用一个代表性 throwaway。 |
| AC7 | 完成与改动对应的 package、workflow 和全部声明平台的定向投影检查。报告规则、入口、验证方法与结果的对应关系；区分通过、失败和未验证。AC5 的最低行为验证缺失时，不得宣布本 Issue 验收通过。其他平台的实际行为不得由代表平台结果推定。 |
| AC8 | 分别报告源码、安装投影和实际行为证据。完整多平台升级与 Release 矩阵仍由专门 Issue 负责；本 Issue 不以该矩阵缺失为失败，也不宣称它已通过。 |

## 非目标

- 全仓库历史文本重写或统一改用英文。
- 完整实施或认证 ASD-STE100。
- 新增独立审批阶段、wrapper skill、语言合规证书、gate artifact 或 public DTO。
- 修改 Trellis 上游源码、全局安装或 hook 来实现写作规则。
- 自动升级业务仓库、执行完整 Release 矩阵或发布软件。



## 完成口径

AC1–AC8 全部有实际可核对证据后，整体任务才可完成。AC5 缺失时保留未完成状态；源码、投影、实际行为分别报告。完整多平台升级和 Release 矩阵由专门 Issue 承担。
