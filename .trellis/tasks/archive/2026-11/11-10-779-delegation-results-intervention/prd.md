# #779 委托后的结果承接与干预条件：整体需求

## 1. 来源与术语

| 来源 | 章节与角色 | 本 Task 用途 |
| --- | --- | --- |
| [Direct Source #779](https://github.com/castbox/guru-trellis/issues/779) | 完整正文；六项修复要求、范围与最小验收为要求；事故记录为历史证据 | 唯一外部需求来源；当前无评论补充 |
| [workflow-contract](../../spec/workflow/workflow-contract.md#phase-route) | Phase 2；现行流程约束 | 保留执行者终态、live facts、计划外候选及正式审查职责 |
| [canonical workflow](../../../trellis/workflows/guru-team/workflow.md#phase-2-execute) | Phase 2 与原 owner 路由；现行流程约束 | 保持主协调者角色、现有步骤及上游所有权 |
| [#734](https://github.com/castbox/guru-trellis/issues/734) | R3/R4；关联工作 | 理解重叠边界，不作为前置或新增验收来源 |
| 当前委托 | main 交付目标及当前专属工作树；执行约束 | 仅推进 #779，PR 发布后等待协调器处置 |

“执行者”是已受委托工作包的唯一执行 owner。“主协调者”是现有 workflow 角色。“执行事实”包括实际命令、进程、日志、产物与终态；执行事实不等同于正式 Check、独立 Review 或工作包完成判断。

## 2. 背景与问题

#779 的事故调查已发现：即使派工明确了唯一 build/device owner、完整产物核验及终态汇报，主会话仍重复追踪日志和推断进程状态，并追加过程指令。双方发生旧日志、旧 PID 或未核产物内容引起的误判；共享写入也在交接完成前启动。已核交叠差额是文档，不能据此声称产品源码被修改。

现行 Phase 2 已要求使用 worker 终态结果和 live facts，并保留主协调者对计划外候选的资格判断。缺口是委托后自主执行、结果承接、介入条件及冲突写入交接的方法没有保持清晰。未证明 Trellis 工具强制这些行为，也未证明全部重复构建由主会话指令导致。

## 3. 目标与非目标

整体目标是在现有 Guru 派工与承接约定中明确委托后的协作行为，减少同次运行的重复跟踪和未经核实的过程干预，并保留主协调者的结果判断与原正式审查。

本 Task 承担 R779-01 至 R779-06 的合同修订、实际受影响 canonical/dogfood/声明平台投影同步及必要 drift 检查。整体完成须覆盖全部要求；单个执行命令成功或一项文档修改不能替代整体验收。

非目标：#734 的消息或批次预算、规模阈值、设备矩阵、整场事故重放；新增步骤、Skill、public DTO 字段、状态、运行台账、持久 handoff、授权记录、强制汇报表、消息额度、锁或调度平台；强制换代理或结束重派；patch 上游官方 agent、Trellis runtime 或业务仓库工具。本项不自动修改或关闭 #734，不承诺成本节省比例。

## 4. 真实调用方、场景与流程

| 场景 | 调用方、前置与触发 | 处理与可观察结果 |
| --- | --- | --- |
| SC779-01 正常推进 | 执行者已接受明确工作包，运行仍正常推进 | 执行者自主等待、诊断、验证并取回产物；主会话推进互不影响的工作或有界等待，无默认同日志双重跟踪和连续过程指令 |
| SC779-02 具体介入 | 发生原 owner 决策阻塞、范围/机制变化、冲突写入、用户停止或执行者无法继续 | 主会话先核本次运行与具体缺口，再沿原 owner 处理；接管先查现有工作及可用原句柄，未知终态如实保留 |
| SC779-03 冲突写入 | 主会话需写入会影响执行者当前工作的内容 | 先请求自然边界暂停；执行者确认当前终态且暂不启动下一轮；主会话写入后通知恢复。无冲突路径继续并行；无写入需求不增加逐轮放行 |
| SC779-04 结果承接 | 执行者汇报完成、部分完成或未知终态，或已发生写入交叠 | 主协调者核对结果与当前要求，采用适用执行事实；仅针对具体缺口或失效证据补查/验证，保留正式 Check 和独立 Review |

## 5. 行为要求

### R779-01 执行者自主完成工作包

对应 SC779-01。执行者自主完成已委托工作包内的命令等待、常规环境诊断、原断言、产物取回及终态汇总。计划外范围、机制或风险变化仍按现有 discovery 合同返回主协调者；自主执行不扩张已委托范围。

### R779-02 主会话正常等待与结果层次

对应 SC779-01/04。执行者正常推进时，主会话不默认并行跟踪同一日志并连续下发 poll、继续或下一步指令。主会话可推进互不影响的工作，或按实际平台能力有界等待。日志片段、页面 PASS、命令终态、产物通过和工作包完成分别判断。

### R779-03 介入须基于具体触发与本次运行

对应 SC779-02。真实阻塞需要原 owner 决定、范围/机制变化、冲突写入需求、用户停止要求或执行者确实无法继续时，主会话介入。介入先核对本次实际运行和具体缺口，再针对缺口处理，不把猜测直接变成重启、重建或修改要求。保留必要进度查询与证据读取，不禁止主会话使用 adb。

### R779-04 最小终态汇报及原句柄承接

对应 SC779-02/04。执行者在当前对话提供最少的完成内容、实际终态、结果位置及未完成项。诊断先核对本次进程、日志和产物对应关系；未知终态如实说明。确需接管时先查现有工作并沿可用原句柄继续，不默认重新启动。正常协作不要求逐命令上报 PID、句柄或 hash。

### R779-05 冲突写入在自然边界交接

对应 SC779-03/04。存在冲突写入需求时，先请求在自然边界暂停；执行者确认当前终态且暂不启动下一轮后，主会话才写入冲突内容，完成后通知恢复。无冲突路径继续并行；没有写入需求时，执行者按原委托继续，不新增每轮等主会话放行的固定审批。已经交叠时判断实际影响、披露失效证据并补必要验证，不一律重跑。

### R779-06 原职责内核对结果并采用适用事实

对应 SC779-04。主协调者仍核对结果是否满足当前要求，识别新缺陷并交原 owner。正式 Check 和独立 Review 保持原职责。对可验证执行事实判断适用性后采用；存在具体缺口或不一致时才补查或重跑。新增要求作为明确差额处理，不用零碎消息改变隐含完成条件。

## 6. 约束与依赖

- 规则优先归入 canonical `trellis/presets/guru-team/spec/workflow/workflow-contract.md` 的 Phase 2 段。全局 workflow 仅保留必要引用；主协调者不被虚构成已有独立 implementation Skill。
- Markdown 拥有过程和语义判断；脚本只执行既有确定性安装及校验，不新增运行调度或机械审批能力。
- 受影响 canonical、dogfood 及声明平台投影通过原安装/升级 owner 同步，保留当前 Task/session 和其他执行者的内容、资源及证据。没有公共数据变化，不需要 DTO 或状态迁移。
- 本项独立于 #734。只处理诚实协作正常路径、普通过期事实及普通错误，不扩大到攻击、压力、锁或 crash 一致性协议。
- PR 与完成验证以 main 为目标。PR 发布后停止报告；合并前等待协调器具体处置。

## 7. 可观察验收与验证方式

| 验收 | 关联要求/场景 | 验证入口与预期可观察结果 |
| --- | --- | --- |
| AC779-01 合同完整且职责一致 | R779-01..06；SC779-01..04 | 只读审核修订后完整派工/承接段及原 discovery、Check、Review 关系。六项行为、触发条件、例外和交接顺序均清楚；没有新增逐轮审批、运行台账或隐含完成条件 |
| AC779-02 实际受管投影一致 | 全部要求；全部场景 | 原安装/升级 owner 同步实际受影响投影，执行必要 dogfood drift、mode 和 sidecar 检查。报告真实命令、结果及未覆盖边界；源码 parity 不声称实际 Agent 行为或业务安装已采用 |

不强制设备执行、Agent 评测框架、整场事故重放或消息计数测试。普通 Issue 的验证不扩展为完整多平台安装/升级/Release 矩阵。实际节省效果保持未验证；上述验收目前均待实施。

## 8. 实际未决项

整体需求没有待用户选择的必要问题。Delivery 原 Author/Architecture 仍需确定具体合同落点、受影响投影与最小验证安排；这些规划尚未批准，不构成实现或验收通过。
