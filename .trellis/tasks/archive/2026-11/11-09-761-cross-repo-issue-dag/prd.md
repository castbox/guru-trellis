# 跨仓 Issue DAG 编排整体需求

## 1. 来源与术语

| 来源 | 角色 | 用途 |
| --- | --- | --- |
| [Issue #761](https://github.com/castbox/guru-trellis/issues/761)，目标与行为 1–5、验收 | Direct Source，要求 | 本 Task 完整范围 |
| `trellis/skills/guru-team/packages/guru-orchestrate-issue-dag/references/dag-contract.md` | 当前行为证据 | 单仓兼容与既有调度边界 |
| `trellis/presets/guru-team/spec/workflow/issue-orchestration.md` | 既有共享合同 | 观察、解阻、权限、base、完成核证与恢复 |

节点身份是所属 repository 与 Issue 的组合。协调会话、Skill provider、节点业务仓库是不同角色。动议正式绑定集合指其当前权威中明确绑定的 Issue 集合，普通相关链接不能自动成为成员或依赖。

## 2. 背景与问题

现有 DAG 支持 provider 与业务仓库不同，但一次运行只接受一个仓库、一个已保存项目及仓内整数编号。跨仓动议无法在同一 run 表达成员及依赖，也无法为各节点选择正确项目和 base。Issue #761 的 Fizz 案例是需求背景，其中 Web 仓未登记为 Codex 项目是当时观察，不视为本次环境事实。

## 3. 目标与非目标

从任意仓库的一个协调会话显式调用公开 DAG Skill，编排用户选定或动议正式绑定的跨仓 Issue 集合，直到各节点按其业务仓流程完成。保留既有单仓调用。范围覆盖节点身份、成员解析、依赖调度、环境就绪、观察恢复和结果核证。

不完成 Fizz 业务动议，不修改其四仓业务实现。不新增调度脚本、状态库、协调 Task 或持久授权记录。不扩展恶意输入、竞态压力、锁或 crash 协议，不将普通能力交付扩大为 Release 多平台矩阵。

## 4. 真实调用方、场景与流程

| 场景 | 调用方、前置与触发 | 处理与可观察结果 |
| --- | --- | --- |
| S1 跨仓显式集合 | 用户在其他仓会话提交不同仓的 Issue 及依赖 | 规范化唯一仓库/Issue 身份，按依赖和可用槽位推进，正确创建各仓子会话 |
| S2 动议集合 | 用户指定含正式成员绑定的动议 | 回读权威成员与职责；区分总控和工程子项，形成真实依赖，不把所有链接当任务 |
| S3 环境缺口 | 某节点仓库无可用执行环境 | 先查受支持创建入口与权限；能建立则建立并回读核验，否则暂停受影响节点并给具体用户步骤；就绪后恢复原 run |
| S4 信任与 setup | 应用要求项目或 prompt/hooks 信任，或运行确需 setup | 信任由用户审阅操作；创建成功不等于信任就绪。只配置实际缺失前置的 setup |
| S5 单仓与恢复 | 既有单仓输入，或跨仓 run 已有子会话 | 单仓仍可调用；恢复同一节点/子会话和所属仓/base，避免串仓或重复创建 |

## 5. 行为要求

- **R1 / S1、S5**：节点、引用和依赖必须明确 repository 与 Issue；不同仓的同号 Issue 不冲突。发起会话和 provider 可以在其他仓。保留旧单仓输入的确定解释。
- **R2 / S2**：支持用户明确集合及动议正式绑定集合。读取各 Issue 的实际职责和验收，区分产品总控与工程交付，不凭仓库名称推导职责，不把普通相关链接升级为成员或硬依赖。
- **R3 / S1、S5**：为每个节点定位所属仓库的 Codex 项目、独立 worktree 和适用 base，执行该仓当前 workflow。PR、交付及完成核证必须绑定该节点仓库和 base，恢复保持原选择。
- **R4 / S1、S5**：一个 run 按跨仓依赖调度，复用现有并行、观察、解阻、失败策略及恢复。只有前驱完整完成才释放依赖；保留各仓操作边界，局部缺口不误伤独立可推进节点。
- **R5 / S3、S4**：缺环境时先检查当前受支持入口与权限。具备能力及操作边界时建立环境并回读验证。无权限或入口不可用时暂停受影响节点，明确仓库、缺失条件和具体用户建立步骤；就绪后继续原编排。应用信任必须由用户完成，不代理点击或将创建成功当作信任完成。setup 仅服务实际运行前置，不要求每仓新增脚本/hooks。

## 6. 约束与依赖

输入形式和兼容适配由 Delivery 规划确定。沿用 AI/Markdown 编排及原生 Codex 工具，脚本仅执行确定性事实。当前工具可能没有项目登记或信任入口；合同必须如实给出局部阻塞和受支持用户路径，不虚构 API。

公共 Skill id、typed exits 及单仓语义保持兼容，canonical 修改通过原 managed 安装 owner 同步投影。共享方法的 sequence 消费者必须保持原串行语义。本项不新增业务持久化字段或数据迁移。

## 7. 可观察验收与验证方式

| 验收 | 对应要求 | 入口、输入和预期观察 |
| --- | --- | --- |
| AC1 | R1、R3、R4 | 从不同 provider/协调仓的公开 DAG 入口提供两仓同号 Issue 及跨仓边；观察不同项目/base 的创建参数、依赖顺序和按节点仓库/base 的完成核证 |
| AC2 | R2 | 提供正式动议成员、总控及工程子项，另含普通相关链接；观察真实成员/职责承接，不扩大集合或制造循环 |
| AC3 | R5 | 通过原入口处理缺环境：有受支持创建能力、无入口/权限、需用户信任三类条件；观察真实创建/回读或具体用户步骤、局部暂停及原 run 恢复，独立节点遵守失败策略 |
| AC4 | R1、R4 | 既有单仓调用和 sequence 受影响回归保持其原观察、解阻及终点语义 |
| AC5 | R3、R5 | package/source/installed 检查及 dogfood drift；验证 matching preset 更新保留 Task/session，报告真实 App 与隔离载体边界 |

行为验证使用真实 Agent 执行公开入口及受控工具边界；静态文本/结构检查仅证明分发一致性，不能替代调度行为。生产 Fizz、真实业务合并和完整 Release 矩阵不作为本项验收。

## 8. 实际未决项

整体需求没有未决产品或范围选择。Delivery Author/Architecture 需调查当前原生项目创建、信任及 setup 能力并形成可执行合同；工具缺口按 R5 处理，不降低跨仓能力目标。
