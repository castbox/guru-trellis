# 提升正常用户旅程、阶段交接与验证有效性的 Guru 方法

## 1. 来源与术语

- Direct Source 为 [castbox/guru-trellis #747](https://github.com/castbox/guru-trellis/issues/747)。采用其交付切片、JQ-R1 至 R6、JQ-AC1 至 AC8 和 V1 至 V6。以“约束与兼容”“方案与职责”“实施顺序与知识整合”作为当前设计约束。
- #717 的审核充分性和 #735 的验证方法是当前基线。旧分支 `origin/codex/user-journey-quality` 是拆分前的历史材料。复用证据前须核对其方法版本、输入、实际入口和结论。
- 旅程是受支持调用方从真实入口到可观察结果的一组连续动作。交接不变量是已确认行为中跨阶段必须保持的业务条件。

## 2. 背景与问题

开场消息复盘发现，逐阶段通过和局部测试可以遗漏连续操作中的真实交互和阶段交接。已有案例包括局部确认后的后台任务、资源的唯一引用被提前释放、直接方法绕过菜单、替身保留同一对象和媒体输入组合过窄。历史版本与 QA 安装包未建立精确对应，不据此统计缺陷率。

## 3. 目标与非目标

D1 交付连续操作与阶段交接。D2 交付旅程验证顺序与证据有效性。先交付 D1。D2 可以从独立、来源明确的已定义正常旅程开始。两个 Delivery 各自完成相应的 JQ-R5、R6 和分发检查，整体 Completion 合并审视两个结果和仍适用的证据。

本 Task 复用当前阶段、owner、读取顺序、证据和正常场景规则。范围排除新 Skill、公共 DTO、生命周期字段、评分器、账本、固定场景数、参数矩阵、#734 的预算和并发、#736 的调用图和上下文改造、采集平台、业务修复与业务安装升级。

## 4. 真实调用方、场景与流程

| 场景 | 调用方、条件和动作 | 结果 |
| --- | --- | --- |
| JQ-S1 | Clarify 收到跨阶段操作的正常需求并从真实入口调查 | 能区分连续操作、可见结果、未决产品选择和实现细节 |
| JQ-S2 | Author 展开状态、持久化或资源交接 | 所属 design 能让 Architecture 与 Approval 判断业务条件在实际交接中能否保持 |
| JQ-S3 | 连续操作属于本批承诺，Implement 已具备运行入口和所需依赖 | 先获取本批最小完整旅程的反馈，再补有独立价值的参数覆盖 |
| JQ-S4 | Check 看到直接方法、替身或样本证据 | 确认其触达、代表性和可支持结论 |
| JQ-S5 | 独立审核收到当前候选 | 在原首读顺序内先形成源于职责 authority 的问题，再对照候选和总结 |

## 5. 行为要求

- **JQ-R1** Clarify 依当前来源和真实入口推导适用的起点、阶段、允许动作、等待期间的正常再次操作以及成功、失败、放弃的可见结果。无交互时使用真实调用方。既有行为是调查事实，真实产品歧义留在原入口，新增场景遵守原资格规则。
- **JQ-R2** Author 在已有 PRD 和 design 写明实际阶段，如局部确认、后台完成、可靠保留和最终提交。对受影响的状态或资源，写明要保持的条件、动作顺序、实际 writer/reader 和失败后归属。Architecture 与 Approval 依原职责判断条件能否成立。技术修订由技术负责人处理。范围排除通用锁、压力和 crash 协议。
- **JQ-R3** 连续操作在本批承诺内且入口与依赖就绪时，Author 在原实施验证计划安排最小完整正常旅程，Implement 先取得该结果，再补有独立价值的参数覆盖。单个函数、API 或 CLI 足以观测时采用相应层级。高风险下层可先定向验证。按风险和成本选择测试与实现顺序，设备或全链验证限于交付承诺确实需要的部分。依赖缺失时推进独立工作并说明验证影响。旅程通过后继续必要验收及受影响回归。
- **JQ-R4** 审核实际入口和可见结果，限定直接方法测试的证明层级。按当前目标比较替身与真实适配器的对象身份、异步完成、恢复、地址更新、缓存或解码语义。按真实接受范围和交付构建选择输入。容器、开发机能力和单一样本不能推出整个支持范围。工具采事实，原 owner 判断充分性。
- **JQ-R5** 在原首读顺序和隔离边界内，从当前来源或职责 authority 形成关键行为和关系问题，再与候选设计、实现、测试及总结核对。独立检查者不提前收到缺陷答案或通过叙述。人数、审核轮次、架构评估职责沿用原流程。有适用证据继续复用。
- **JQ-R6** 连续动作、阶段、不变量和验证顺序落入已有 PRD、design 或 implement 所属正文。只记录已覆盖、受影响需补验、失败及未执行的必要范围，保留历史原义。

## 6. 约束与依赖

Markdown 承载方法，原 owner 承载语义判断。机械验证承载实际运行和分发事实。公共 API、schema、typed exit、Task/Delivery 生命周期与兼容合同沿用当前基线。原工具维护入口按 local_candidate 同步受管投影。V1 至 V4 使用受支持的实际原生 Agent，输入先冻结，独立评价预期不进入被测材料。

D1 采用 Clarify、Author 及共用 review-sufficiency 的现有正文。D2 采用 quality-guidelines 的方法和实际必要引用。两批差额由原 owner 整合到 RDT 对应单元和既有 Architecture Baseline 域。本 Task 没有数据迁移或部署责任。

## 7. 可观察验收与验证方式

| 验收 | 切片与入口 | 观察 |
| --- | --- | --- |
| JQ-AC1 | D1，V1 原生 Clarify/Author 方法 | 展开上传中再编辑、局部确认后退出、恢复与最终保存。区分已确认、待确认及实现职责。 |
| JQ-AC2 | D1，V1 同一材料 | 从释放与接管关系识别引用空档，交原 owner 修订。 |
| JQ-AC3 | D2，V2/V4 原生派工与简单对照 | 入口和依赖就绪时优先最小连续旅程。单一函数或入口足够时直接用该层。 |
| JQ-AC4 | D2，V2/V3 | 区分直接粘贴和长按入口、内存同实例和反序列化、地址已知和解码可用。 |
| JQ-AC5 | D2，V3 原生审核 | H264/AAC MOV 证据不能覆盖已接受的 HEVC/PCM 范围。只要求实际接受和交付能力涉及的差异。 |
| JQ-AC6 | D1、D2，V1 至 V4 的适用部分 | 从原 authority 独立推导问题。保留原读取、资格与证据复用。 |
| JQ-AC7 | 两个切片各自 V5/V6 | 定向分发、安装/reapply 和工具同步通过。canonical 与受管投影一致，用户文件、Task/session 和 sidecar 得到检查。 |
| JQ-AC8 | D1 V1，D2 V2 至 V4 | 保存真实原生 Agent 的输入、操作、输出和缺口，原审核 owner 评价适用结果。 |

## 8. 实际未决项

当前没有待确认产品选择。真实 Agent 不可执行、provider 不完整或受管同步冲突时，保留失败与未执行范围，继续独立工作。范围变化回 Clarify。机制与基线冲突回 Architecture。
