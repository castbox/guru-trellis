## 4. 模块、职责与设计取舍

在 canonical `quality-guidelines.md` 的证据选择段补方法，覆盖交付边界、条件、实际入口、替身与样本。原 Author 实施模板直接引用同一位置。Phase 2 和原 Check/Review 保留既有读取。沿用 D1 的独立问题推导和去敏过程例子，增补手势、异步、样本和简单 API 裁剪。真实素材保持单独。Architecture 采用当前审核域，RDT 使用现有行为验证单元。

## 5. 接口与数据

使用既有 managed-spec 和 package 投影。主要输入是已确认旅程、真实可用入口和依赖，输出是原 implement 正文的验证顺序和原 reviewer 的证据结论。共用公开 I/O、路由和 Task 状态继续沿用当前合同。

## 6. 状态、顺序、正常与失败流程

Author 先确认连续操作是否属于此次承诺。若运行入口和依赖就绪，Implement 先取得一条最小完整旅程的反馈，再补有独立价值的参数覆盖。单一入口已充分时用其结果。高风险下层行为可先定向验证。依赖缺失时说明哪项结论等待继续验证，完成独立工作。保留必要验收和受影响回归。

原审核者从相关来源先提出问题，核对测试实际执行的入口及可见结果。直接方法和替身结论按证据层级限定。将真实序列化、异步完成、恢复、地址刷新、缓存和解码差异限定到当前相关表现。以已接受组合和实际交付组件选择输入。未知能力交原 owner 验证。

## 7. 恢复、兼容、迁移与集成

D2 可采用另一个来源明确的旅程。D1 证据按适用性复用。原工具同步负责同 checkout 的受管安装、原 Task/session 及 sidecar。普通装配失败保留原结果并只补缺口。没有数据迁移。

## 8. 验证设计

V2、V3 和 V4 用已有 `codex exec --ephemeral --json` 采实际记录。先运行 V2，通过原 Phase 2 派工观察真实旅程排序及局部证据。V3 从中性来源推导问题后再单独打开候选，观察目标构建、媒体输入和真实持久化证据。V4 用纯函数对照观察验证裁剪。冻结事实和评判分别位于各自目录，独立评价者核对原始记录。

V5 复用定向安装和 reapply，核对共享方法及模板投影、用户文件和 sidecar。V6 在本 checkout 运行原 `guru-upgrade-tools` local_candidate，回读 ownership、drift 和实际 native current。分发和本地采用各有证据，业务项目效果不由这些检查判断。
