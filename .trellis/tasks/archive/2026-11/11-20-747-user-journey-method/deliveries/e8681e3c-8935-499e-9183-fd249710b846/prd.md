# D2 旅程验证顺序与证据有效性

## 1. 整体来源与术语

整体范围见 [Task PRD](../../prd.md)。直接来源为 [#747](https://github.com/castbox/guru-trellis/issues/747) 的交付切片、行为要求、约束与兼容、方案与职责、验证计划和验收标准。本批承担 JQ-R3、R4、适用的 R5/R6 和 AC3–AC8。术语沿用 Task 定义。来源设计处置在本批 design 第3节。

## 2. 整体与本批目标、非目标

给原 Author、Implement 和 Check 提供选择验证顺序，以及判定实际入口、替身和样本能支撑哪些结论的具体方法。沿用最小充分证据和正常场景规则。范围排除业务应用修复、通用测试平台、固定红绿顺序及设备矩阵。

## 3. 本批起点、前序结果、依赖与剩余责任

D1 已通过 PR #888 交付连续操作、阶段交接和原独立审核方法。D2 可以从独立、来源明确、已经定义的正常旅程开始。V2 采用正常编辑草稿的既定旅程，V3/V4 分别验证证据边界和简单函数裁剪。整体完成仍由原 Completion 复核两个 Delivery。

## 4. 本批调用方、场景与流程

- JQ-S3。入口可运行且依赖已就绪时，Author/Implement 先安排并获取本批最小完整旅程的反馈。其后验证有独立价值的参数覆盖。
- JQ-S4。原 Check 核对直接方法、替身和样本实际触达的入口和输出。证据结论限于确实覆盖的行为。
- JQ-S5。独立审核先从其适用来源推导问题，再读实际候选和测试总结。

## 5. 完整行为、条件与约束

JQ-R3 只在连续操作属于交付承诺且入口及依赖就绪时使用旅程优先。单一函数、API 或 CLI 已能观察结果时用该层。高风险下层可先定向验证。设施缺失时推进独立工作并记录影响。执行顺序按实际风险和成本确定，验证完旅程仍须完成必要验收和受影响回归。

JQ-R4 根据主张检查真实入口及交接后的可见结果。直接方法仍可证明局部逻辑。只比较当前行为依赖的替身语义，如对象身份、异步完成、恢复、地址更新、缓存与解码。用目标交付构建和已接受范围选择样本，项目外工具能力和容器名不能证明编解码组合。未知范围由原负责人核实。

JQ-R5/R6 沿用原审核顺序与范围。写回已有正文，只保留已覆盖、需补验、失败与未执行的必要结论。

## 6. 本批验收、验证方式与未决项

V2 观察派工 Agent 优先真实最小旅程，并限制直接方法与替身结论。V3 观察独立 reviewer 从来源推导实际构建、HEVC/PCM、恢复、地址与解码证据缺口。V4 观察纯函数选直接单测。V5/V6 采用现有定向分发、local_candidate 安装和回读。原生输入和评价判据运行前冻结。当前没有未决产品选择。

## 7. Canonical 引用与本轮差额

使用 [行为验证需求](../../../../../docs/requirements/current/behavior-validation-method.md)、[设计](../../../../../docs/design/current/behavior-validation-method.md)、[测试](../../../../../docs/test/current/behavior-validation-method.md) 和 [审核架构域](../../../../../docs/architecture/03-domains/review-sufficiency.md)。验证选择和有效性由现有 quality-guidelines 统一维护。Review sufficiency 沿用 D1 已交付的独立问题推导。
