## 2. 背景与问题

实际使用中，审核 Issue、代码或已有能力时，Agent 经常发现少量问题后结束；用户再次要求审核，又发现另一批问题。已观察到的案例是 go-guru 两套 ORM 的评估：前轮既定 Issue 和已有回归完成后，后续在同一候选上又确认了其他缺陷。该现象不能证明存在固定 finding 数量限制，也不能把新发现直接归为修复引入的回归。

当前 Guru 已有完整范围、证据充分性和修复后覆盖等要求，但共同规则分布在多个位置：
- `guru-review-change/references/review-method.md` 组合 Check、Branch Review、Architecture、Completion 和专题 spec 的语义规则。
- Check、Branch Review 又读取该共享方法，形成共同方法与具体阶段规则之间的双向依赖。
- `workflow-contract.md#candidate-applicability-and-coverage`、`quality-guidelines.md` 及多个 Skill 合同分别定义相关规则。

这证明需要厘清共同规则的唯一 owner 和依赖方向；不预先断言全部规则已经矛盾。不同审核目的采用不同维度，不因数量或措辞不同就构成漂移。

本次核对基线为 `main@8378b8d500a974ae1c01bd0571f30149f56541b0`。可定位的现状来源为 [共享审核方法](https://github.com/castbox/guru-trellis/blob/8378b8d500a974ae1c01bd0571f30149f56541b0/trellis/skills/guru-team/packages/guru-review-change/references/review-method.md)、[候选适用与覆盖合同](https://github.com/castbox/guru-trellis/blob/8378b8d500a974ae1c01bd0571f30149f56541b0/trellis/presets/guru-team/spec/workflow/workflow-contract.md)及[专业审核与验证规范](https://github.com/castbox/guru-trellis/blob/8378b8d500a974ae1c01bd0571f30149f56541b0/trellis/presets/guru-team/spec/workflow/quality-guidelines.md)。这些链接用于定位当前差额，不把历史基线永远固定为实施 authority；实施前按当时的有效源核对差额。

## 3. 目标与非目标

建立统一的“审核充分性”SSOT，归并现有共同定义，并让适用的 Guru 审核 owner 实际执行。解决单次审核过早结束、剩余检查反复依赖用户催动的问题。

本 Issue 是一项审核合同与执行行为的收敛工作。共同规范、原定义迁出、调用接入、安装投影和真实 Agent 行为验证属于同一交付范围；不能只新增文档而保留并行定义。

Planning 在一个固定可获取的 Guru source 基线上，界定本 Issue 的共同规则和现有消费者集合，包括 Issue Clarify/Readiness/Wording、Planning Approval、独立变更审核、Check、Branch Review、Delivery Review、Completion、Architecture 及安装验证中实际承担审查的职责。逐项说明适用规则、必要接入和合法阶段特例；只改承担这些职责的内容，不把每个 semantic gate 改造成完整代码审核。

交付前核对候选相对该集合的实际变更和受影响消费者。基线后的无关新增 Skill、阶段或需求不自动进入本项；不追逐最新 SHA 或扩为所有流程的全面重写。盘点与迁移说明使用现有规划/设计/验证位置，不新增长期清单系统。

### 核心边界：只完成当前对象的审查

必须区分：
1. 审核完成：所选对象与范围已充分检查，可以完整报告发现。
2. 对象通过：满足原阶段定义的通过条件。
3. 修复或验收完成：由原修复、验证和交付流程判断。

共同审核循环为：确定当前对象与范围 → 检查适用问题 → 判断发现项和覆盖缺口 → 补充必要调查 → 输出审核结论。

- finding 可以保持未修复，独立只读审核仍可完成并完整报告。
- findings 已解决、验收完成、全部测试通过、连续若干轮零 finding，均不得成为共同的审核完成条件。
- 测试失败可以是 finding 的证据。仅在支撑当前判断需要时执行与请求权限相符的定向验证；无法执行时说明它影响哪些结论。
- 原阶段的通过、修复、验收、独立性和发布条件继续由原 owner 定义。共同规范不削弱这些门禁，也不接管其执行。
- 修复产生新候选后，由原流程或新请求发起后续审核；共同规范只定义适用覆盖如何承接，不拥有修复—复审—Delivery 的调度循环。

非目标：

不修复 go-guru ORM 或其他业务仓库的发现项；不扩展恶意输入、对抗绕过、竞态压力或无依据 fault injection；不把所有审核合并为一个 Skill；不统一各专业标准的维度数量；不接管修复、验收、Task/Delivery 生命周期或发布。

## 4. 真实调用方、场景与流程

| 场景 | 原调用方、触发与行为 | 可观察结果 |
| --- | --- | --- |
| S1 首次审查 | 原 Issue、规划/设计、实现或正式阶段审核 owner 选定对象、目的、版本，从承诺、入口和消费者形成覆盖 | 完成必要调查并报告全部成立 findings 和覆盖结论 |
| S2 分散问题及同根因多入口 | 当前范围发现多个问题或共享转换/状态/契约问题，沿真实机制检查相关入口 | 不按 finding 数或报告长度早停，不无限扩展 |
| S3 finding 未修复与测试失败 | 独立只读审核在受审候选上确认缺陷或失败测试 | 可以完成当前审核并完整报告，不自行修复或推进 Delivery |
| S4 正确对象与合法差异 | 适用覆盖已完成且无新证据/影响 | 不制造误报、不固定轮数，结束本次审核 |
| S5 必要证据缺口 | 必要对象不可访问或来源/执行证据不足 | 明确已查/剩余、具体阻塞和影响，不宣称完整；保持原前置停止与出口 |
| S6 后继候选 | 原流程或新请求发起新候选审核，检查完整增量及影响 | 保留有效原覆盖，补齐失效/缺失；影响无法界定则完成必要完整审查 |

共同循环与修复调度边界由第3节定义，具体义务见第5节；场景不是另一个阶段调度器。

## 5. 行为要求

### 1. 从对象与依据形成覆盖

在当前选定对象、目的和版本范围内，从有效来源承诺、实际入口、必要消费者及适用专业标准形成检查单元，交叉核对覆盖清单本身是否遗漏。不能只从现有实现或测试反推完整性，也不能以逐文件读取、章节齐全或维度字段齐全代替行为与关系覆盖。

检查单元按真实对象和复杂度裁剪，不强制通用表格，不穷举无依据的输入组合。必要未变消费者是证据范围，不自动扩大 accepted scope。检查对象是请求选定的范围和可识别的必要关系，不要求证明所有未知缺陷均不存在，也不以全文读取量或覆盖百分比代替语义判断。

### 2. 按剩余覆盖推进

允许分批调查和阶段性汇报，但发现一批问题、达到某个输出数量或回复篇幅限制不能成为隐含停止条件。已确认发现不得因报告长度被丢弃。

原审核 owner 继续完成未查范围，并在上下文或执行约束下沿原职责承接。真实访问、权威或执行缺口阻止充分审查时，报告已覆盖部分、剩余部分、具体阻塞及影响，不宣称完整审核。具体退出或继续执行沿各 owner 已声明的合同；“部分完成”是报告中的事实描述，不因此新增 `partial` 或其他公共出口。原 owner 明确要求前置阻断时，保留该停止条件并说明未审范围。

剩余检查得到支撑结论所需的覆盖后结束本次审核；没有新证据或新影响，不因“也许还能找到问题”反复扫描同一范围，不强制固定轮数、连续零 finding 或另派审核者。合并同根因发现时保留各触发条件和影响，不能通过归并丢弃已确认问题。

### 3. 检查有依据的同类影响

发现转换、状态处理或契约承接问题后，检查本次范围内共享该机制的适用入口和消费者。扩展由真实机制关联支撑，不因“可能还有问题”无限扩大范围，不新增特性或无依据的防御场景。

### 4. 完成发现判断与当前结论

对已发现候选完成必要调查、证据核对、适用性与影响判断。报告完整的成立 findings、覆盖结论及影响结论的未决证据；未成立候选仅在解释重要争议或结论局限所必需时说明。共同规范不要求逐条输出全部被排除候选、完整候选历史或每次搜索。原 owner 已有的必要记录义务继续沿其当前合同执行。

审核完成必须有当前范围及适用问题已充分检查的依据，完整报告发现，并明确证据缺口及其影响。存在妨碍充分性结论的缺口时如实表达部分完成或阻塞。不得以 finding 数量、零结果、Agent 共识、命令通过或扫描通过替代判断。

### 5. 后续候选的覆盖承接

后续审核由原 owner 检查先前覆盖的实际适用性，审查新候选的完整增量及受影响路径，保留仍有效的证据，补齐失效或缺失部分；影响无法界定时完成所需的完整审查。不得仅看修复点，也不得无条件换 Agent 从零重扫。

该规则只约束一次后续审核如何工作，不要求当前调用等待修复、不跨多个 Delivery 自行推进。

### SSOT 归属与迁移

- 统一 SSOT 定义共同的覆盖形成、推进、补查、结束、局限表达及后续覆盖承接义务。先核对现有定义，已由唯一源充分定义的规则直接引用；只有实际重复、冲突或缺失部分才迁移、归并或补充。每条规则只有一个可编辑权威，不要求把所有专题正文塞入同一文件。
- 需求、概要/详细设计、Go-Guru 实现等正确性标准保留在原专业标准；共同 SSOT 不复制其正文。
- 原 Skill 保留自己的入口、输入、审核对象、执行顺序、独立性要求、阶段特例、通过条件、typed exits、恢复和副作用。
- 检索充分性、测试有效性、因果结论等已有专题规则仍由原 SSOT 维护，共同规范准确引用；workflow 只负责调用和出口消费。
- 迁移时逐条区分重复定义、真实冲突、合法特例与历史规则，将共同定义迁出后删除旧正文并改为引用。不能只增加新规范并约定其“优先”，长期保留多份可编辑定义。
- 共同规范不依赖某个具体阶段的私有 artifact、recorder 或出口；理顺当前共享方法与阶段合同的依赖方向。判断现有 `review-method.md` 是否仍有独立组合职责，保留有职责的薄组合或撤出重复内容。
- 物理位置和分发方式由实际消费者决定。Guru preset 当前不捆绑独立维护的 `guru-ai-guides` 专业 Skill；不得将其独立调用隐式绑定到目标项目必须安装 `.trellis/`。本 Issue 在 Guru 侧完成共同规范的加载、专业证据消费及 provider/目标仓库分离，明确外部独立调用的兼容边界；不把外部 Skill 接入声明为已经落地，也不以另一个仓库的未来修改替代本项应完成的 Guru 职责。本项不授权跨仓库修改或批量升级业务项目。
- 保持既有公共 I/O、schema 和出口语义；确有破坏性调整时遵循现有显式迁移合同。
- 覆盖进度优先留在当前会话或原有必要结果中，不新增长期审核台账、评分器、digest 链、用户授权记录或无直接 consumer 的公共字段。
- 不新增“审核充分性审核”运行时 Skill、审批链或平行 gate，由原审核 owner 直接应用共同规范并负责结论。

## 7. 可观察验收与验证方式

**AC1**. 给出当前规则与消费者的迁移说明：每条共同规则有唯一源；旧定义已迁出；阶段差异和专题标准仍有明确 owner；引用与读取方向清楚，没有共同规则与具体阶段内部实现的循环依赖。
**AC2**. 对已界定消费者证明其加载与引用接入；按实际审核职责选取不同调用语义的代表性正常入口执行 Agent 行为验证，说明代表性依据及未覆盖边界。字段、命令或名称相同不能单独证明等价；不要求每个 owner 重走完整 Task/Delivery 链。保持 Issue、文档、实现、正式阶段与独立只读审核的原边界及出口。
**AC3**. 执行真实 Agent 行为评估。验收方在执行前确定每个案例的范围、已知应发现问题、合法对照和必要证据缺口，并据此核对 Agent 的实际调查、finding 与完成表述；预期答案由验收方持有，不向 Agent 注入指定 findings、预填当前语义判断或使用生产入口之外的纠偏提示。复用现有 eval 与观察能力，不新建长期审核运行平台。案例覆盖：
   - Issue、代码及规划/设计类对象均有代表性案例。
   - 多个分散问题：不在发现少量问题后提前宣称完整结束。
   - 同根因多入口：检查有依据的相关影响。
   - finding 未修复、测试存在失败：仍可充分完成当前只读审查并完整报告，不自行修复或推进 Delivery。
   - 正确实现及已约定合法差异：不为继续找问题制造误报。
   - 必要范围不可访问或证据不足：准确说明缺口及其影响，不伪造完整结论。
   - 后续新候选：审查增量和影响，保留仍有效覆盖，不要求跨 Delivery 等待，也不无条件从零重审。
   - 已充分覆盖且没有新的证据或影响：能够结束当前审核，不为了固定轮数或追求继续发现而无限补查。

   保留足以复核对象、实际入口、Agent 行为和结论的最小观察证据，并沿原 eval 结果位置承接；这不是每次业务审核都新增的持久化要求。
**AC4**. 在同一案例和可比的入口、工具及模型条件下，分别观察变更前后的遗漏、误报、提前结束和重复调查，保留首次实际结果及必要条件差异。验收逐项判断案例要求，不把单轮问题数量或统计改善替代行为正确性；不新增通用召回率门槛，也不以测试套件全绿作为业务审核完成条件。不能用 Markdown 引用存在、schema 合法、runtime 测试通过或人工编写的理想对话代替 Agent 行为证据；不承诺任意审核一次发现全部缺陷。
**AC5**. 按本 Issue 的变更面验证 canonical/dogfood/installed、声明平台投影及适用 reapply/drift；明确真实行为验证、机械检查和未验证安装边界。普通 Issue 不承担完整多平台 installer/Release Gate 矩阵，也不批量更新业务仓库。

上述验证用于验收本 Issue 的实现，不进入每次业务审核内部循环。
