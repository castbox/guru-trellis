“验收切面”是 Issue 自身交付边界内实际调用方可观察的合同结果；“支撑证据”是判断该结果所需的验证，不自动成为另一交付目标或验收层。Task 对整体来源负责，Delivery 只承接选定范围。来源中的规范性条件、否定、例外、顺序和来源角色均保留。

## 2. 背景与问题

当前规范已有必要性、主目标优先和删除扩张要求，但没有充分定义责任边界停止条件、结果与证明方法分类、创建前全部入口精简及后续各轮去重。历史案例中两个主要目标对应九条混合验收，目标归属本身不能过滤测试过程和重复义务。最早可确认偏差在待创建正文及原审核，不据此断言具体 Agent 未读规则。

Create Issue 执行器只提交原文并追加 marker；确定性字节一致性不能承担自然语言审核。修复必须落在共享 Markdown 规则和原 AI owner，不将语义判断放进脚本。

## 3. 目标与非目标

目标是在所有受支持的 Agent 创建入口首次写入 GitHub 前，以及后续任意审核输出和每次正文写回前，保证验收合理、精简、范围适当且不重复。交付止于本 Issue 可独立验证的权责边界，不沿调用链外推。

承担共享内容／验证规范、原 owner 的必要引用及原门禁行为、实际受影响 workflow／平台入口、去敏教学示例、现有 Skill eval 和受管采用。公共 API、typed exit、DTO、schema 和运行状态不变。

不恢复 Wording、扫描器或新阶段；不设固定验收数量、测试层级或每层必测；不新增持久映射、证明表或账本；不让 Create Issue 改写正文；不承担边界外系统联合交付；不取消合法技术承诺及必要补证；不重做全部生命周期；不执行完整多平台安装或发布矩阵。

## 4. 真实调用方、场景与流程

- **S1 创建：**任意受支持入口的 Agent 面对新写、用户提供、复制、拆分或续接的草稿，先由 Clarify 形成合理精简正文，经原 Readiness／Create Issue 门禁，再首次创建。Task、阶段和 Issue-only 不豁免。未通过时回原 owner 修订，不先创建后补救。
- **S2 持续审核／修订：**原写作及审核 owner（含需求、方案、Architecture、Approval、Planning、Check、独立 Review、Branch／Delivery Review、Completion）在当前有效需求和证据上判断。更换 Agent、workflow／standalone、恢复会话、输入来源均不豁免。多余义务在本轮输出前被删除，不先形成阻塞再交下轮撤销；正文写回前检查完整候选。
- **S3 合法技术交付：**组件在自身对外合同处验收；消费者接入与业务 E2E 由对应责任方承担。现有充分证据复用，只补自身明确承诺尚未证明的条件。
- **S4 真实遗漏／联合交付：**原范围内遗漏、缺陷或证据失效仍定向修复；有效需求确实包含接入或承诺必须由集成证明时，保留对应验证，并说明具体承诺与现有证据缺口。
- **S5 采用：**原安装 owner 同步受影响 canonical／dogfood／声明平台投影，保留用户修改、Task/session 与原 sidecar 恢复。

## 5. 行为要求

**R1（S1–S4）责任边界与结果：**确定目标、消费者、边界和边界外责任后，在边界内选最外沿有效切面。多个入口只覆盖必要差异。API、CLI、workflow、文档、代码、配置、协议和数据状态均可作为交付对象，不要求最终用户界面或生产效果。不能以粗糙结果省略明确承诺，也不能以内部观察手段否定合法技术结果。

**R2（S1/S2）验收分类与删除：**候选验收对应已确认目标，区分结果、证据和无依据扩张。删除无目标、仅复述过程或重复条目；判断删除后哪个目标或必要承诺无法确认。数量服从独立判断价值，不规定一目标一条，也不将多义务塞入一条冒充精简。替换实现检查只辅助识别偶然细节，不推翻规范性技术约束。

**R3（S3/S4）禁止外推：**不得因调用方或最终用途，或以防御性推断、完整性偏好、“确保万无一失”、泛化风险追加消费方集成、E2E、生产采用及联合验收。消费者视角用于确定合同，不意味着运行真实消费者。消费方尚未接入、无 E2E 或未上线本身不阻塞提供方完成。不能改名为保护、风险、Finding、强制 follow-up 或后续 gate。只有当前有效承诺确需集成时才安排最小验证；缺少依据时删除，不反复要求扩张确认。必要替身仅隔离边界外依赖，不制造被测组件本应产生的结果。

**R4（S1–S4）最小充分证据：**单元、集成、端到端和联合验收是可选方法，不是固定层级。最外沿有效证据已覆盖时不逐层复制。明确内部承诺尚未被证明时只补定向检查，不另建验收层。额外验证须有独立缺陷检测价值，不能以惯例、测试数量或覆盖率新增义务。对象、条件、路径和结论仍适用的证据复用，阶段或 reviewer 变化不自动重跑。原 owner 独立判断适用性和充分性。

**R5（S1）首次写入前：**所有正常受支持创建入口路由既有 Create Issue 及必需前序；用户创建意图、现成草稿、既有 pass 或“先记录”不能代替最终正文适用审核。不合规先回原 owner 修订，未通过不得创建；实质变化刷新直接受影响判断。已实际成功创建的输出丢失恢复同一对象，不重复创建。执行器保持原文，AI 原门禁承担语义检查。

**R6（S2）任意轮次持续约束：**新增、恢复或强化义务先核对有效来源、支持场景、权责、已有验收及证据；说明当前承诺或真实缺陷、实际覆盖缺口及最小补充必要性，不新建证明表。设计、测试及审核记录不能自行取得需求权威。不成立的候选在本轮输出前删除，不形成阻塞或返工；正文写回前核完整正文及受影响安排。多余义务连同派生测试、Finding、依赖和 gate 删除，不搬到其他阶段或改名恢复。真实范围变更回 Clarify，原始承诺修复不自动扩张验收。清楚合法且未受影响的结论继续复用。

**R7（S5）唯一来源与分发：**Issue-specific 方法由 issue-content 独占；跨阶段验证必要性、边界、去重和复用由 quality-guidelines 原小节承载，原审核经现有共同规范与引用使用。只调整必要引用和原行为，不复制第二套规则，不新增语义脚本或阶段。受管副本通过原安装 owner 同步并按实际差额验证。

## 7. 可观察验收与验证方式

**AC1（R1–R6；S1–S4）：**复用现有 Issue 入口、教学示例与 Skill eval 的最小正常场景集：两目标草稿混入可归属目标的测试过程、无依据扩张、重复层级及跨界 E2E，同时含合法技术承诺、已充分覆盖证据、一个真实遗漏和确需集成的明确承诺。原 Clarify／Readiness／Create Issue 在首次创建动作前先修订并审核最终正文；未通过时没有创建写入。普通与真正不同的 Issue-only／现成草稿／已有 Task 或阶段内路由被覆盖，等价入口复用路由证据。后续独立或恢复审核拒绝新增、重复或改名恢复义务及其阻塞后果，每次写回前正文仍合理精简；真实遗漏能定向修复。核实际正文、动作顺序和回程，不以条数、预填 pass、扫描或退出标签代替语义行为。

**AC2（R7；S5）：**共享规则、原 owner 引用及受影响 canonical／dogfood／声明平台投影一致，通过适用原安装／工具更新与 drift／sidecar 定向验证；不执行完整多平台安装或发布矩阵。教学、静态、原生 Agent 与安装采用结果分别说明，未覆盖项如实保留。整体完成需原 Task Completion 判断 AC1/AC2 的当前证据，不能以分发成功替代行为效果。
