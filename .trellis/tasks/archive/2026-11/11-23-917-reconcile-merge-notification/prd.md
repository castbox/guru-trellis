# 修复并行 PR 合并通知触发无依据的 Reconcile

## 1. 来源与术语

| 来源 | 定位与角色 | 用途 |
| --- | --- | --- |
| [Guru Trellis #917](https://github.com/castbox/guru-trellis/issues/917) | Direct Source，整体需求。见「问题」「期望行为」「验收」 | 界定两个受影响的通知入口和临时仓库验收边界。 |
| [#917 审核评论](https://github.com/castbox/guru-trellis/issues/917#issuecomment-7100737709) | 有效讨论 | 确认 #567 的触发规则继续有效。 |
| [Guru Trellis #567](https://github.com/castbox/guru-trellis/issues/567) | 约定约束。见「Reconcile 只按实际需要触发」 | 保留固定候选、原阶段负责人和既有整合入口。 |
| [Backend #2179](https://github.com/castbox/ai-chat-roleplay-backend/issues/2179)、[PR #2183](https://github.com/castbox/ai-chat-roleplay-backend/pull/2183)、[整合提交](https://github.com/castbox/ai-chat-roleplay-backend/commit/2578adb25c0f840531ec53f172fc2ffa9b0bcf69) | 历史事实和原始证据 | 说明通知、基底前进和同路径变化如何进入一次无实际阻塞记录的整合。 |

固定候选是当前阶段已选定的 Delivery 内容及其审查对象。目标分支及其最新提交是独立事实。Reconcile 是原阶段负责人在有触发依据时调用的既有基底整合流程。

## 2. 背景与问题

Backend #2179 执行时收到 PR #2183 已合并的通知。执行者因目标分支前进以及 Runtime、Architecture 文件路径重叠，废弃原审核前置并创建整合提交。原记录未给出实际冲突、需要承接的依赖、必需检查发现的集成失败或服务端更新要求。此前另一次执行有明确同步授权，其基底差额为归档和 Fizz 测试。两次执行的授权条件不同。

当前协调合同的派发模板和同仓其他 PR 合并后的处理条款默认要求整合。现行 workflow 的「Fixed content and actual integration」把整合限定在 #567 已定义的实际触发条件。

## 3. 目标与非目标

修复协调派发和执行会话处理合并通知时的误触发。整体完成要求两个入口继续原阶段，并证明原 Reconcile 在真实冲突场景仍可调用。来源业务仓仅用于取证。冲突验收止于调用原 Reconcile，后续解冲突、重审与交付接续由既有流程承接。

## 4. 真实调用方、场景与流程

| 场景 | 前置与触发 | 可观察结果 |
| --- | --- | --- |
| S1 协调派发 | 当前 Task 有固定候选。协调会话收到同仓 PR 合并通知，用户要求关注合并并在必要时同步。 | 下发的指令保留同步条件和已核对的事实。执行会话可以继续原阶段。 |
| S2 执行会话 | 当前 Delivery 正在审核。执行会话直接收到合并通知，或在接回工作时看到该通知。目标已前进，当前工作无依赖变化或实际阻塞。 | 原阶段负责人核对当前适用事实。固定候选和仍适用的审核证据可供原审核继续使用。 |
| S3 实际冲突 | 正常提交使候选与目标在同一位置产生 Git 内容冲突。 | 原阶段负责人指出具体冲突，选定一次目标提交，调用原 Reconcile 入口。 |

## 5. 行为要求

- **R1 派发。** 协调者原样保留用户给出的同步条件和已核对的事实。关注合并或「必要时同步」按原条件执行。
- **R2 接收。** 执行会话收到通知或接回工作时，由原阶段负责人按当前入口核对适用事实。如果仅有合并通知、目标 SHA 变化或路径重叠，保留固定候选和仍适用的证据，继续原步骤。
- **R3 触发。** 如果发生实际合并冲突、必需检查发现具体集成失败、原 Merge 负责人确认服务端要求更新分支、当前工作明确需要纳入依赖或需求，或者用户明确要求同步，则按原入口选定该次目标并进入 Reconcile。等同于「必要时同步」的指令仍受已给条件约束。

## 6. 约束与依赖

现行 #567 固定内容和实际集成规则继续有效。协调会话传递事实和条件，原阶段负责人负责判断证据适用性。原 Reconcile 负责固定目标及后续整合。交付目标为 castbox/guru-trellis 的 origin/main。开发起点为 main 的固定提交 8604558695dfd9d8ea2181406a87ece70d9eea63。

## 7. 可观察验收与验证方式

| 验收 | 入口与输入 | 预期结果 |
| --- | --- | --- |
| AC1 对应 S1、R1 | 在临时仓库用正常提交推进目标分支。协调会话收到通知时，当前 Delivery 无依赖变化和实际阻塞。 | 观察实际派发。同步条件及已核对事实得到保留，派发没有要求追赶新 SHA。 |
| AC2 对应 S2、R2 | 使用同类无阻塞变化，在固定候选审核途中向执行会话直接提供通知。 | 观察执行会话继续原审核。候选及仍适用的证据保留，调用记录没有 Reconcile。 |
| AC3 对应 S3、R3 | 在临时仓库以正常分支提交制造实际 Git 冲突。 | 原阶段负责人指出冲突，固定目标提交，并产生原 Reconcile 入口的实际调用。此处是验收终点。 |

为三个场景保留可重跑的起始提交、通知输入、实际派发及调用结果。Git 检查用于建立场景事实，Agent 轨迹用于判断派发和阶段决策。
