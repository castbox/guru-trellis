## 2. 整体与本批目标、非目标

同仓 PR 合并通知曾导致 #2179 在缺少实际触发证据时中断原审核并创建整合提交。本批交付完整的通知处理修复。协调派发保留同步条件和事实，执行会话继续原步骤或在实际触发时调用原 Reconcile。冲突场景的验收终点是调用。来源业务仓和本单之外的后续整合流程保持其原有负责人。

## 3. 本批起点、前序结果、依赖与剩余责任

D1 没有前序 Delivery。内容范围的开发起点为 main@8604558695dfd9d8ea2181406a87ece70d9eea63。PR 目标为 castbox/guru-trellis 的 origin/main。依赖 #567 已交付的固定候选合同、协调派发入口、执行会话的当前阶段入口和原 Reconcile。成功交付本切片即覆盖整体需求。Task Completion 仍由原负责人核对实际交付和三个验收结果。

## 4. 本批调用方、场景与流程

- **S1 协调派发。** 同仓 PR 合并后，协调会话处理通知和用户「必要时同步」的指令。目标已前进，当前 Delivery 无依赖变化及实际阻塞。协调者将原条件和已经核对的事实交给执行会话。派发保留原步骤。
- **S2 直接通知或接回。** 执行会话在固定候选审核中收到通知，或接回该工作。原阶段负责人重读当前适用事实。单独的通知、目标 SHA 变化或路径重叠不足以触发整合。保留当前固定候选和仍适用的证据，继续原审核。
- **S3 实际冲突。** Git 对固定候选与目标提交报告内容冲突。原阶段负责人指出具体阻塞，固定本次目标提交，调用原 Reconcile。

## 5. 完整行为、条件与约束

协调者原样传递用户条件和已核对事实。「关注合并」及「必要时同步」按其条件执行。执行会话按原阶段入口核对事实。出现实际合并冲突、必需检查发现具体集成失败、原 Merge 负责人确认服务端要求更新、当前任务明确需要纳入依赖或需求，或者用户明确请求同步时，才进入原 Reconcile。真实触发时固定一次目标。原候选、阶段和仍适用证据继续由各自负责人维护。仅因 SHA 或路径变化，不作废证据、不新增检查义务、不进入整合。

## 6. 本批验收、验证方式与未决项

| 验收 | 输入与入口 | 预期行为 |
| --- | --- | --- |
| AC1 / S1 | 在临时仓库提交无依赖变化、无实际阻塞的目标推进。向协调入口提供合并通知和原条件。 | 实际派发保留用户条件和已有事实，没有要求追赶目标 SHA。 |
| AC2 / S2 | 同类目标推进。直接向执行会话的在途审核入口提供通知。 | 原审核继续，候选和适用证据仍可读取。调用轨迹中没有 Reconcile。 |
| AC3 / S3 | 以正常分支提交在同一位置制造真实 Git 冲突。 | 原负责人指出冲突，选定目标提交，实际调用原 Reconcile 入口。到此结束该场景。 |

保留可重跑的起始提交、通知、实际派发和调用结果。实际 Agent 行为验证和安装投影检查分别报告。当前没有未解决的需求选择。
