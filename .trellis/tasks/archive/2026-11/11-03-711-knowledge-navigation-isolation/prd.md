## 5. 行为要求

以下八条沿 Direct Source 原顺序，分别编号 R711-01..08。全部条件、例外及原 owner 边界均为 accepted scope；具体布局交后续规划论证。

本节的“根入口”指需求、设计、测试和架构知识体系的入口，例如 `docs/{requirements,design,test,architecture}/README.md`；不禁止维护仓库安装说明 README。知识单元按稳定能力或职责划分，不按任务、Issue 或文档层机械等同；不同文件若共同修改同一能力或关系，仍按真实语义重叠处理。

1. 根入口保持稳定，保留知识体系的稳定身份、适用范围、状态、真实版本引用、历史边界，以及知识组织和查找方法。普通任务新增或修改独立主题时，不再为逐项登记而修改根入口、递增无关的共享全局版本或追加合并历史。入口自身的身份、适用状态、位置、查找合同或必要关系实际变化时，仍由原维护 owner 完成对应修改；不删除真实公共 API 版本及其兼容语义，也不强制普通任务为无关变更创建新版本。该要求覆盖真实维护链上的共享导航，不能将逐项登记转移到 `current/README.md`、共享 index/manifest、生成后仍需各 PR 提交的索引，或另一个统一登记文件。Planning 须列出当前读取者和写入者，逐一说明采用新合同后的读取与写入路径。
2. 按稳定能力或职责划分当前知识单元及必要导航。语义独立单元的日常正文和导航维护使用互不竞争的文件路径；修改既有能力时更新原完整正文及其必要关系，不以每个 Issue 另建一份 current 正文代替整合。若两个任务必须共同修改同一有效关系，该关系属于真实重叠范围，由原 owner 整合，不能为满足路径隔离而复制关系或拆散必要语义。
3. 同步调整读取端。Agent 能从稳定入口，通过目录、稳定标识和限定搜索定位适用的完整正文及必要 R/D/T、Architecture 关系。发现入口必须区分经原 owner 晋升的 current、accepted target、未晋升 contribution、历史及被替代内容；不能因文件存在或搜索命中就将候选视为当前定义。不能依赖根入口枚举全部单元，也不能把搜索排序、日期或更大版本当作语义 authority。新增、修改、改名、替换或删除知识单元时，由原 owner 同步维护受影响的稳定引用及必要关系；不为这些动作恢复全局逐项登记。
4. 保持现有 RDT 与 Architecture 维护职责、隔离贡献、候选 Check、final integration、最终 Check 和 Review 边界。任务贡献仍是候选或历史来源，不能直接冒充共享 current；晋升后的普通读取不需要回放贡献链来拼接完整定义。
5. 两个任务修改同一能力、正文或必要关系时，原 AI owner 必须识别并整合真实语义冲突，保留双方仍有效的条件。正常 Git 自动合并可以继续使用，但文本合并成功不能证明语义一致；原 owner 仍须审核组合后的完整定义及受影响消费者。不得在未判断有效范围时只取一侧，也不得绕过审核制造“无冲突”。
6. 公共规则同时覆盖 RDT 和适用的 Architecture 导航；调查其真实共享写入点，仅修改与上述目标有关的合同和消费者。不得将其扩大为所有代码或业务冲突的自动解决框架。
7. 给出已有项目可执行的迁移与兼容合同：旧入口及完整正文、稳定引用、未迁移范围、进行中任务的阶段适用版本、切换条件、失败恢复和旧路径退出。区分“安装新规则”与“项目文档完成迁移”：未满足切换条件时，保留明确可读的原 authority，标明未迁移范围，不宣称已获得无共享索引写入的效果；满足条件后，新任务采用新写入合同，不继续双写旧共享索引。在途任务保留适用版本；最终集成触及已迁移单元时，沿原 owner 的真实目标重读和整合路径处理，不把旧读取兼容解释为继续写旧索引。历史快照与原始证据保持原含义。
8. 将改动落实到 canonical Skill/spec 及必要 workflow/preset 消费方，同步 dogfood、实际安装副本和声明平台投影。说明已有项目的采用步骤；源码分发一致不等于业务仓库已完成迁移。公共 API 若需破坏性修改，使用明确版本和迁移合同。

具体目录布局和是否需要确定性辅助工具由 Planning 结合当前消费者论证。不以生成一个仍需各 PR 提交的共享索引文件作为消除竞争写入的证明。脚本仅执行确定性动作和校验；知识适用性、替代关系及整合充分性继续由 AI 判断。


## 6. 约束与依赖

## 7. 可观察验收与验证方式

下列项目按原顺序编号 AC711-01..08，覆盖 R711-01..08 与 S711-01..07。Planning 在实施前固定样本、必答事实、必要关系及实际入口；验收只定义预期，不预填通过。

A、B 都须从未包含对方贡献的同一基线独立形成候选，再验证两种合并顺序；不能先合入 A、让 B 改写共享入口后宣称不存在竞争。这里验证独立分支的组合，不增加同时运行进程的压力或竞态测试。

- Planning 在实施前固定正常样本、必答事实、必要关系和实际读写入口。旧新对照保持相同主题、完整来源语义、必答事实、必要约束及等价任务操作；允许目录布局、导航形式及对应读写指令随方案变化，不要求两种结构逐字节相同。实际 Agent 对照保持模型版本、工具权限及任务起点条件一致，各自从正常入口执行，不预载另一方案的答案或操作过程。保留旧结构的首次冲突证据；不以减少样本内容、提前整合另一任务或强制串行改写来取得通过。
- 在待测方案各自的同一干净基线上启动两个正常任务，分别新增语义独立的知识单元，完成各自正常文档维护和晋升；固定候选后分别验证 A→B 与 B→A 的合并，均不因共享导航、全局版本或合并历史产生冲突，双方有效知识和必要关系均保留。核对完整变更文件集合，证明冲突点未转移到下一级索引或共享 metadata。
- 通过正式安装入口执行实际 Agent 的读取与写入：在未预置另一方案答案的等价起点，按现有原 owner 完成新增主题、修改既有单元及晋升，观察其实际修改文件，证明不再要求全局逐项登记。合并后能发现两个新增主题、读取完整适用正文并保留稳定标识、必要跨层追踪及来源。至少一个样本同时含 current、未晋升 contribution 和历史定义，验证 Agent 不混用状态、不形成第二 current authority。RDT 与受影响的 Architecture 导航均须有对应样本或明确的不受影响依据。
- 两个任务分别修改同一能力，验证原维护流程能识别真实差异并保留仍有效的条件；不以消除 Git 冲突代替语义一致性。
- 使用已有文档的代表性样本验证迁移，样本可以来自 Guru 本仓库或去敏临时仓库，不修改业务仓库。覆盖切换条件未满足与已满足两种状态，以及一个在途任务的最终集成；旧引用仍可解释，当前查询可正确定位，未迁移范围明确，新任务和合法集成不会恢复旧索引双写。改名、替换或删除单元的样本核对仍有效的引用与关系，不要求重写不可变历史快照。
- 验证 canonical、dogfood、安装包、声明平台投影、reapply 与 drift；按现有质量合同执行最小可靠验证集。实际 Agent 样本可以复用同一代表性安装；需要 clean throwaway 时最多执行一个。完整多平台安装/升级/Release 矩阵由其专门 owner 承担，未覆盖范围单独报告。
- 实际 Agent 样本采用与待测基线匹配的公开入口和 Check 合同。若本项改变原 owner 的公开调用，须同步调用说明、输入示例和定向真实入口验证。既有验证结果仅在仍适用的范围内复用；受改动影响的部分须重新验证。
