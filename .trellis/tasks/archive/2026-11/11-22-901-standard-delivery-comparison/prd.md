# 对照验证标准 Delivery 流程的减负效果

## 1. 来源与术语

| 来源 | 角色 | 用途 |
| --- | --- | --- |
| [#901 正文](https://github.com/castbox/guru-trellis/issues/901) | 直接需求 | 确定本 Task 的目标、对照方法和验收边界。 |
| [#901 审核评论](https://github.com/castbox/guru-trellis/issues/901#issuecomment-7078991310) | 审核背景 | 确认 #826 提供方法，历史事故统计只提供背景。 |
| [#736](https://github.com/castbox/guru-trellis/issues/736) AC9 | 要求 | 明确共同口径、实际工作量和失败保留。 |
| [#826](https://github.com/castbox/guru-trellis/issues/826) R3、R4 和 AC3 | 已约定方法 | 复用真实 Agent 对照、匿名评价和最小证据保留。 |

共同区间指两边从同一起点实际完成、且有同等行为和结果证据的区间。发布版本整体差额指两个版本之间观察到的差额。单项归因需要对应改动与实际读取、调用或阶段交接的证据。

## 2. 背景与问题

v0.7.0-guru.9 包含 #793 的条件资格判定、#792 的按步读取和 #794 的提交后独立完整审核。既有测试与发布验证提供局部证据。#901 要求测出这三项变化进入同一标准 Delivery 后的实际工作量，并核对必要检查是否都得到执行。

## 3. 目标与非目标

完成一个代表性标准 Delivery 的改前与改后对照，交付逐项可复核的结果。报告改善、退化、归因依据和未验证边界，并说明观测结果是否支持另立架构减负项。身份解析与发布入口的后续实现分别归 #899 和 #900。其他发布变化只用于解释版本间差额。

## 4. 真实调用方、场景与流程

**S1 标准 Delivery 对照。** 实验负责人先为两侧固定同一任务材料、起点、终点、必要行为和计数口径。两侧真实 Agent 从受支持的入口执行各自匹配的 workflow 和工具。场景须能观察资格判定触发、按步读取及 Check 与独立审查的交接。两侧以同一可核验 Delivery 结果为目标。评价者依据固定规则核对实际读取、工具记录、结果和副作用，先作匿名评价，再解明版本对应关系。

**S2 提前停止。** 若任一侧发生环境阻碍、装配失败或合法非通过，保留原始记录和实际停点。评价者只对两侧均已观察到的同一区间给出差额，并标明未到达环节。新尝试保留与原运行的关系。

## 5. 行为要求

- **R1 冻结对照。** 执行前记录共同任务材料、起止、必要检查和计数规则。优先使用 v0.7.0-guru.8 和 v0.7.0-guru.9。若安装或环境限制需要替代版本，说明理由、实际版本和可比边界。
- **R2 采集真实工作量。** 从两边的实际运行记录统计必读流程字节、runtime 调用、输入装配失败、语义审查、测试重跑和用户确认次数。预先说明分段、重复读取和测试首次执行与重跑的计法。保留失败及合法非通过，并复核必要检查与副作用边界。
- **R3 复核并解释差额。** 提供逐项比较及证据定位。区分版本整体差额与 #793、#792、#794 各自能够归因的变化。报告实际可观察的发布阶段架构资格开销。场景到达归档时单独报告归档观察，否则注明未到达。历史事故统计仅供背景。

## 6. 约束与依赖

实验采用独立项目副本、相同任务材料和中性标识。优先保持模型和运行设置一致，记录影响比较的实际差异。执行 Agent 接收普通任务及指定方法。评价标准、预期答案和另一侧输出由评价方保管。每侧记录实际 workflow、工具版本及原生入口。Git 和 GitHub 写入遵循原流程的副作用边界。保留支持复核的最小材料、记录和结果，按项目规则处理敏感数据与授权信息。

## 7. 可观察验收与验证方式

- **AC1（S1／R1）** 复查事前材料及两侧原生执行记录，能确认共同起止、任务输入、计数规则、实际版本和必要行为。使用替代版本时，可核对替代原因及可比区间。
- **AC2（S1、S2／R2）** 从实际读取与调用记录能追溯六项计数，辨认重读、测试重跑、原始失败及合法非通过，并核对必要检查和实际副作用。任一侧提前结束时，只有共同实测段进入差额计算。
- **AC3（S1、S2／R3）** 报告给出两侧逐项观察、改善与退化、可归因证据和未验证区间，标明发布阶段架构资格及归档的实际观察边界，并说明是否有证据支持另立架构减负项。

## 8. 实际未决项

整体范围无待决定的产品选择。Delivery 规划负责选择具体场景，固定共同停点和计数细则，并核验两侧安装及原生运行入口。实验结论等待真实运行。
