# 〈Task 标题〉整体需求

写作前实际加载 [共享正文合同](../references/planning-body.md)。按下列顺序用实际内容替换填写提示；始终/条件及裁剪规则由共享合同第3节定义。本模板只写整体需求，不创建 Task 根方案或实施计划。

## 1. 来源与术语

填写来源表：稳定标识、可解析 locator、章节/条款、角色（要求/约定设计/建议/候选/历史/证据）、本 Task 用途。写明 Direct Source 或无 Issue 的实际请求；解释影响理解的术语。必要引用按共享合同第2节实际读取。

## 2. 背景与问题

填写当前行为、期望行为、具体差额和影响。事实给出可查位置；历史案例保持历史身份，不从个案扩出其他功能。

## 3. 目标与非目标

填写整体目标、承担范围、明确排除项及整体完成责任。保留来源的非目标，不用候选技术方案限制需求。

## 4. 真实调用方、场景与流程

按场景 ID 填写：调用方、前置条件、触发动作、处理行为、可观察结果。分支/顺序/状态变化写清关系；真实业务角色存在时补用户故事，工程变更按真实调用方写。

## 5. 行为要求

按稳定要求 ID 展开行为、完整条件、否定、例外、执行顺序和失败结果，关联场景及来源。来源已约定技术约束在此保留，由选定 Delivery design 第3节给出唯一处置和具体落点；这里不另建矩阵。

## 6. 约束与依赖

填写适用的接口、机制、兼容、运行和 owner 约束，以及外部输入/依赖和缺失影响。技术实现未定时交原 Author/Architecture，不能伪装成产品问题。条件项无关时写明理由。

## 7. 可观察验收与验证方式

按 AC ID 填写：对应要求/场景、验证入口与输入、预期可观察结果、适用证据边界。这里定义验收，不写未经执行的通过结论。

## 8. 实际未决项

填写具体问题、原处理 owner、影响和停点。没有必要未决问题时如实说明；非阻塞后续观察单列。`scope_requirements_ready` 前补齐本阶段必要内容，再由原 Clarify 审查并 `accept_scope`。
