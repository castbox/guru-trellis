## Purpose-specific Planning 3.0 migration

Planning task impact requires schema_version=3.0 and planning_purpose. Read
references/contract.md's Planning 3.0 section. Candidate assessment consumes
current call-local design_facts/constraint_refs or the current design_locator;
it never requires an unwritten contribution, projects promotion_state, or
claims reviewed_candidate. Its current router returns only to Author
solution_planning. Final assessment consumes Wording-current design_locator
and actual task-local contribution/necessary ADR; current returns directly to
Approval. The first result is never reused as the second result.

All seven planning exits bind the same purpose. Sync goes through the thin
sync router back to this original owner and preserves the original purpose;
bootstrap/repair current reruns fresh task impact for that purpose. Conflict or
contract gap returns through the planning router to Author's corresponding
conflict profile; fitness regression and blocked retain their original meaning.
No new Architecture owner or lifecycle stage is introduced.

Old task-impact planning 2.0 input fails closed; interrupted old planning fresh
re-enters Author. Bootstrap and repair retain their fixed contracts. Nonplanning task impact and
promotion select 4.0 / Delivery 2.0 under MIGRATION-600. Historical schemas are validation assets only, never a planning
fallback. MIGRATION-292 defines the matching workflow/preset update boundary.

## Delivery Architecture projection

Nonplanning development stages select delivery_task_impact_sync (schema_version
delivery-2.0; Planning retains delivery-1.0 and purpose-bound 3.0 semantics), carrying the exact opaque DeliveryKey and public planning_root
in addition to this owner's original stage authorities. Read the selected
Delivery's three planning documents and the Task's overall scope separately.
The installed public API validates key/relationship and planning_root; the
semantic owner result binds both fields and its exact public input. Independent
assessment, required concerns, contribution, ADR, project checks and promotion
remain under this original Architecture owner and contract. No second judgment
or public Planning writer is added. Whole-task acceptance_finish may have no
current Delivery and retains task_impact_sync; other development invocations
without an explicit key are rejected. Delivery exits carry key/root to the
original route; source_profile=delivery_task_impact_sync distinguishes them.
Old Task development inputs require the pinned old complete installation.

Delivery stage recovery uses `delivery_promotion`, `delivery_repair`, or
`delivery_bootstrap_foundation` with the explicit original DeliveryKey and
planning_root. These profiles execute the same baseline owner algorithms and
return the original stage identity; promotion specifically selects phase2.
Whole-task/global bootstrap, promotion and
repair retain their existing profiles and never infer a Delivery from private state.

`sync_required` has the sole workflow consumer
`guru-architecture-baseline-sync-router`. It uses only the closed DTO shape and
sync_kind to project the exact Task or Delivery promotion/repair/impact entry
to this same owner. It performs no second semantic assessment and infers no identity.
