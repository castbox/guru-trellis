# 分散来源与局部修订：真实过程的去敏教学示例

本例取自一次已执行的 Issue 创建及后续正文修订。已省略本机路径、仓库、Issue、Task、创建标记和调用 digest，将三个历史工作项替换为“清晰写作规则来源”“历史摘要优化来源”和“历史归档维护来源”。公开规范路径、命令与技术条件保留。它展示实际输入、普通遗漏、原审核及修订关系，不是当前需求、用户答复或可复用通过结果。内容标准仍只由[共同规范](../../../references/issue-content.md)定义。

## 实际输入与来源角色

初稿是工程规则验证正文，要求四个原 owner 读取同一内容与语言规范，保持创建、修订、只读和回读边界。随后选定评论要求局部增加两个历史需求写作样例及验收，并保留既有用途、非目标和有效加载条件。

评论的必要内容包括：历史摘要优化需求的同轮重复对象只读算一次、同次相同不可变树复用、变化后重算、无跨进程持久缓存及摘要字节兼容；历史归档维护需求的原身份和历史、人工历史归档与正式 Finish 的区别、同次恢复不额外推进 generation，以及不创建替代任务或空 Delivery。评论还提出装饰图标建议，该建议没有成为内容要求。历史工作项已经完成，不是这次重新实现产品功能的责任，其旧结果也不证明这次验证通过。

Agent 实际读取已有完整正文、选定评论和两个历史需求的完整来源。这里没有编造用户回答，也没有把历史或建议升级为必须实现的新功能。

## 实际普通遗漏与原审核

未完成追加稿把缺陷来源写成“批量读取同轮重复 blob；摘要可以复用”，只用进程数下降验收；功能来源只写“恢复人工归档任务，保留身份与历史”和能够续接。它尚未通过或成为已接受正文。

原 Wording 阅读完整标题、正文及来源后，实际返回 `blocked`。它指出摘要复用的条件、变化后重算、字节兼容和正式链路证据边界被删减；归档恢复的适用对象、路径、身份及 generation 约束也缺失。扫描和文件存在没有替代这次语义判断。

完整正文审核还发现本轮局部追加范围外的既有缺口：初稿仅写语言规范读取失败，没有说明共同内容规范不可读时如何恢复。原审核保留其对完整性结论的阻塞，没有直接扩写核心段。最终修订范围包括两个样例和对应验收，以及这句必要恢复行为；无关内容保持。

原 Clarify 据此补齐正文，沿原正文写入、live reread 和 `refresh_context` 返回。回读正文与实际修订 payload 相同；修订使用既有对象，没有调用创建或建立替代任务。

## 实际最终正文的去敏整理

标题：规范加载的 Issue 创建与修订

## 用途与边界

本 Issue 是验证任务的真实 Issue 写作、审核、创建与修订验证对象。它不要求重新实现已完成的清晰写作规则来源，也不创建 Task、branch 或 worktree。清晰写作规则来源只提供已确认的工程规则来源，不作为当前缺陷声明。

## 本轮行为

执行创建、修订和原审核的 Agent，在生成或审核实质文本前，完整读取安装的 `.trellis/guru-team/skills/packages/guru-clarify-requirements/references/issue-content.md` 与 `.trellis/spec/workflow/clear-technical-writing.md`。创建和修订采用同一内容基线。

如果语言规范缺失或读取失败，Agent 仅报告具体缺口并暂停依赖正文。恢复后，Agent 完整读取，再继续同一请求，不新增审批。共同内容规范不可读时，Agent 沿原安装或对应 owner 恢复后再继续，不猜测正文。短句、常用词和主动语态保持建议性质；命令、路径、标识符和必要来源语义保持。

Clarify 负责调查、来源角色、草稿写作或既有正文整理。Wording 检查清楚表达与语义保持。Readiness 检查完整性和可观察验收。Create Issue 核对最终已审草稿，沿原创建及回读路径执行。正文修订沿原 Clarify 写入、回读和上下文刷新，不调用创建动作。

只读审核、讨论和状态查询不自动写正文。修订时保留此前仍有效要求；必要已确认内容进入正文，建议与历史保持其来源角色。局部修改检查完整正文的跨段影响，语言检查限本轮文本与必要上下文；范围外缺口不静默扩写，影响完整性结论时保留阻塞。

## 可观察验收

1. 从简略请求调查现有文件，形成正文；未编造用户回答或新产品要求。
2. 四个原 owner 实际读取同一内容和语言规范，并完成各自原门禁。
3. 创建结果回读的完整标题、正文与已审草稿一致；创建 marker 按原合同保留。
4. 后续同对象正文修订保留有效条件，整合选定评论中的已确认必要内容；写后回读与精确 payload 一致，刷新后审核完整实际正文。
5. 只读审核保持正文不变。验证结束后关闭本对象，保留正文与讨论供验证任务核查。

本文列出本轮可观察验收；实际创建、修订及规范暂缺结果由验证任务的唯一 Test 分开记录，不以正文或历史来源宣称当前行为通过。规则来源是本仓当前安装正文及清晰写作规则来源的 R2–R5；无未决产品选择，技术细化不要求用户提前设计。

## 历史需求写作样例

以下两段由本轮选定评论要求整理，只验证来源承诺的完整表达。历史归档维护来源与历史摘要优化来源均为已完成的历史来源，不是当前产品待办，也不据此改代码、建立恢复数据或再次跑原性能矩阵。

### 缺陷来源：历史摘要优化

该历史需求解决 Reconcile 树摘要逐对象进程和同次调用重复计算。修复约束是：同轮相同 blob OID 只读取并计算一次，仍按原索引路径顺序组装同样的摘要字节；同次调用只复用相同不可变树的计算，保留两份输入各自的结构、身份和关联校验。可变索引或候选内容变化后必须重新计算，不新增跨进程持久缓存。采用能结束的批量传输，不能重新引入双向管道互等。

原普通文件、可执行文件、链接、空/二进制文件、特殊路径、重复对象及未初始化 gitlink 合同保持；不要求本地子模块对象或远端访问。原正常合并、冲突解决和提交后恢复仍走原 owner 路径，优化不替代语义门禁。

样例验收须同时表达摘要字节兼容、同轮重复对象只读算一次、同次相同不可变树复用及变更重算，并指明代表性无冲突正式 candidate→reconciliation→record→check→invoke 链。历史 100 对象抽样不是完整链路基准，进程数下降也不单独证明完整性能和资源目标通过；原设计阶段固定目标与正式链路重复测量的责任保持。本文不宣称重新执行或取得这些旧基准结果。

### 功能来源：历史归档维护

该历史功能允许用户继续仅作人工历史保留、没有当前正式 Completion/Closure/Finish 结果且没有待恢复收尾事务的旧归档。AI 先读取明确选定归档、来源、历史和当前责任，再由原独立维护入口处理。保留原 TaskId、来源、accepted scope、规划、提交和交付历史；同次操作重试或结果恢复不额外推进 generation，不重复导入历史。

正式 Finish 归档继续走原 Reactivate；未完成 Closure/Finish 或旧 Finalizer 残留回原事务或既定人工处置。不得补造完成/seal，不创建替代 TaskId，也不为仅补证据创建空 Delivery。真实新实现切片仍按正常 Delivery 路径；当前范围变化回原 Clarify，旧 gate 不作当前 pass。

写集限选定任务和必要绑定/恢复状态，保留原始归档及无关内容。依赖缺失、来源过期、身份不唯一或工具不兼容时，暂停依赖写入及成功声明，说明具体缺口、原 owner 和恢复入口，不扩张其它任务维护。配对 CLI/Core 的 source、构建和公共 API 须真实匹配，版本号相同或 Issue CLOSED 不代替依赖证明。

样例验收须能核对目标自身原生 continuation 与下一实际 owner 续接相同 TaskId/公共结果 generation；工具可用、转换、历史保留、会话续接和业务完成分开说明。本文仅验证这些条件被保留，不实际操作任何旧任务或业务数据。

本轮新增验收：两个样例的条件、否定、例外、职责及证据边界在最终正文可读；局部修订后的完整正文经原审核检查，必要评论不只留在评论。装饰图标仍是未采用的建议，未成为内容要求。
