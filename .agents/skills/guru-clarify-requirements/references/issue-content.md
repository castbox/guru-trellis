# Issue 内容编写规范

## 1. 使用与唯一来源

本文件是 Issue 创建与修订共同的内容规范，由原 `guru-clarify-requirements` 维护。运行时完整读取 `.trellis/guru-team/skills/packages/guru-clarify-requirements/references/issue-content.md`；原受管 package 分发同时提供完整安装包和声明平台的可读投影。入口、示例和 README 只定位本文件，不另维护内容标准。

创建、修订及原审核 owner 在生成或审核实质文本前，还须完整读取 `.trellis/spec/workflow/clear-technical-writing.md`。语言规则仅由该文件定义。它是采用 STE 部分原则的项目中文清晰写作规范，不是 ASD-STE100 中文版，也不证明中文符合 ASD-STE100 或取得认证。文件缺失或读取失败时，只报告具体缺口，暂停依赖的实质文本；恢复并完整读取后继续原请求，不新增审批。共同内容规范不可读时，沿原安装或 owner 恢复后继续，不猜测正文。

来源处理实际加载原 Author [规划正文合同第2节](../../guru-author-task-plan/references/planning-body.md#2-从来源到正文)及必要关联条件，只复用其完整读取、来源角色、语义保留与必要引用规则。该节是这些规则的唯一公共来源；其 Planning 章节、模板和接受边界不变成 Issue 格式要求。

在采用本规范的受支持入口中，所有由 Agent 创建的 Issue 都须在首次 GitHub 创建写入前满足本规范。草稿由用户提供、从旧材料复制、拆分或续接，以及 Issue-only、已有 Task 或阶段内创建，均使用原 Clarify／Readiness／Create Issue 路径，不豁免最终正文审核。第4节的持续约束适用于后续每轮相关审核和每次正文写回。

本规范不改变现有 scope authority、Skill Interface、typed exits、确认、freshness、写入或恢复合同。独立操作与 workflow 使用同一内容基线。普通状态查询、只读审核、需求讨论和过程评论不自动触发正文写入。也不要求所有简略 Issue 先改写成完整 Issue 才能进入 Planning；正文整理适用于用户实际请求的创建或完善，原 Author 对简略来源的调查、澄清及 PRD 写作保持。

## 2. 原 Clarify 的正文整理

1. 先完整读取当前请求、现有标题和正文、相关评论及必要仓库事实。按原来源规则判断哪些内容仍有效，区分已确认要求、约定设计、建议、历史事实、原始证据和未决问题。仓库可回答的问题先调查，不猜测缺失事实，不编造用户回答。
2. 从有效来源确定交付目标、实际消费者、本 Issue 自身可交付且可独立验证的权责边界，以及边界外由谁承担什么。按第3节在该边界内选择最外沿有效观察切面，再区分交付结果、支撑证据和无依据扩张；不能只将现有条目映射到目标后照搬。
3. 检查表达是否充分前，先判断要求是否必要。新增要求、机制和验证义务须服务原始需求、受支持场景、实际消费者及当前结果。必要性判断须能回答：省去该项后，哪个受支持场景中的哪项原始需求无法完成。业务结果必要，不代表承载它的整套机制都必要；分别判断所需结果和机制。文档、实现、测试或审核记录不能自行取得新增需求的权威。
4. 不因防御性推断、风险厌恶、完整性偏好或未来想象扩张职责、字段、状态、控制机制和验收。发现无依据或已排除的内容时，删除该要求及其派生的验收、测试、Finding、依赖、后续任务和放行条件；不改名或转移到其他阶段，也不把它变成确认问题。原始需求明确要求的安全、权限、敏感数据保护和真实兼容责任仍须保留。
5. 对影响需求成立的真实选择，沿原 Clarify 流程处理。必要问题未解决时，说明具体缺口及其阻塞的结论，不宣称正文已完善。需求已清楚而实现机制未定时，留给原规划 owner，不要求提交者先完成技术设计。形成最终草稿或完整修订正文时，保留此前仍有效的已确认需求，整合本轮明确变更。替换、撤回或范围调整由原 Clarify 处理；某项要求本轮没有重述，不能据此删除。已有明确接口、机制、职责、顺序和兼容承诺按其来源角色保留，不以“以后再设计”删去。
6. 按第3节将必要已确认内容组织到最终正文。评论与会话承载讨论和历史，但内容已经出现在那里，不是省略正文的理由。共享定义或详细接口规格可以准确引用；本 Issue 的行为、条件、约束及验收仍须在正文说明，不能只写链接或“见讨论”。
7. 输出前按第4节对照完整来源自检标题与正文，核对必要性、来源角色、完整规则、验收及旧承诺与本轮变更是否一致。简短而完整的原正文可以保留，不为形式重写。

草稿更新沿原 `proposed_draft_update` 和上下文刷新。已有 Issue 沿原 `issue_body_edit`、精确 payload、repo-bound GitHub 写入、live reread 和 `refresh_context`。普通澄清讨论仍可使用原 `issue_comment`；它不代替用户请求完善时的最终正文整理。修订不调用创建动作，不产生重复 Issue。新 Issue 只从经原审核的最终草稿进入 `guru-create-issue`，不隐含 Task、branch 或 worktree 创建。

## 3. 适用内容、深度与裁剪

标题明确本 Issue 要解决的问题或交付行为。正文先连续说明触发条件、执行者、核心行为和可观察结果，再展开必要例外与技术约束。同一规则保持一个完整定义，不能靠新增摘要掩盖正文中的规则分散。以下适用内容按真实需求组织，不规定统一章节或目录顺序：

| 内容 | 读者应能理解什么 |
| --- | --- |
| 背景与问题 | 当前现象、已有能力、缺口及其影响；区分事实与待验证判断 |
| 目标与范围 | 本 Issue 承担什么，不承担什么；已有正确能力如何复用 |
| 真实场景 | 用户或调用方、前置条件、触发动作、处理行为和可观察结果 |
| 行为要求 | 已确认行为及适用条件、否定、例外、失败结果和执行顺序 |
| 约束、依赖与来源 | 影响交付的约束、依赖及准确来源；已约定技术承诺与候选方案的角色 |
| 验收与验证 | 从什么入口、用什么输入观察什么结果；不得把预定验证写成通过 |
| 实际未决项 | 具体缺口、影响和原处理 owner；确实没有时如实说明 |

简单 Issue 可以短写、合并章节，裁剪不能丢失适用内容。不强制空章节、无关的 N/A、统一用户故事、Given/When/Then 或优先级格式。Bug 以现象、期望和正常复现场景为主；工程变更说明真实调用方及“触发条件 → 行为 → 可观察结果”；存在真实业务角色和价值时可以采用用户故事。

复杂度决定展开深度。有真实分支、失败或恢复时写清条件和结果；有规范性技术来源时保持其承诺。没有相应行为时不为填表制造接口、状态或故障要求。技术细化未定不自动成为产品需求缺口。

### 验收切面与必要结果

验收止于本 Issue 自身的权责边界，不沿调用链继续外推。在该边界内选择实际调用方通过约定入口、输入和可观察结果足以判断交付的最外沿有效切面。组件 Issue 在组件对外合同处验收，完整业务链路 Issue 在其承担的业务结果处验收。多个实际入口只补必要差异，不为每个内部层次另建验收。

结果型验收不要求最终用户界面、真实消费方接入、生产采用或 E2E。交付对象可以是 API、CLI、workflow、文档、代码、配置、协议或数据状态；不能因观察手段偏内部而排除合法技术成果。消费者视角用于确定合同，不意味着必须运行真实消费者。当前有效需求确实包含联合交付，或自身明确承诺必须由集成证明时，保留对应最小验证；具体必要性、禁止外推及证据去重按下述共用方法判断。

根据有效需求、实际消费者和自身承诺，判断可观察结果覆盖哪些必要责任层。组件或服务合同、调用方或界面合同、跨组件业务结果以及发布或环境结果可以组合，不能按标题词强制唯一分类。组件责任不自动包含调用方接入、整站联调或整体部署；调用方责任不能以替身成功冒充被调用组件或完整链路通过。

验收定义 Issue 需要观察的交付结果，验证证据证明该结果，服务版本部署、共享 test 环境部署和目标环境运行验证属于相应的部署、环境或发布责任。普通 Issue 不默认逐 Issue 部署共享 test 环境；业务对象中的“发布模板”“发布配置”“同步配置”等操作不因名称自动成为服务部署。有效需求明确要求真实联调、共享环境或指定目标环境，或者只有该环境才能判断承诺时，正文保留该结果、必要环境条件和归属。此时不能用最小验证删除承诺，也不能用部署或共享环境通过替代未覆盖的组件合同。

验收场景集合也按独立风险收敛。每个场景对应一个独立的可观察结果或风险；一个场景可以包含判断该结果所需的多个条件、输入和例外。同一行为不得因创建、复审、验证方法或阶段不同拆成多个重复场景。补充测试方法、工程检查或一致性验证不自动成为新的行为场景；其他入口或阶段只在存在必要差异时增加场景。

将每条候选对应到已确认目标，并分清其用途：

- **交付结果：**说明从什么入口、用什么输入观察什么结果，足以判断目标及必要承诺是否完成。保留有效来源的行为、失败、安全、兼容和规范性技术承诺，不能用粗糙结果掩盖其中缺口。
- **支撑证据：**为上述结果提供证明的工程验证，不自动成为独立目标或平行验收层。由原实施、测试与审核职责选择、承接或复用，不将预定验证写成通过。
- **无依据或重复义务：**删除没有目标归属、仅复述过程或重复证明同一结果的条目及其派生义务。归属目标本身不证明条目必要。

逐条检查：删除该条后，哪个目标或必要承诺将无法判定完成？没有独立判断价值时合并或删除。不设置固定条数，也不默认一个目标对应一条验收；不能把多条义务塞进一条冒充精简。“替换实现后是否仍成立”只辅助识别偶然细节，不推翻规范性技术来源。验收不逐项复述功能规则，不因完整性偏好追加固定样本数、设备数、测试方法或完整矩阵。验收深度须与本项成果一致；后续实施或发布准备不提前成为需求发布条件。

实际读取同一 Guru provider 的 `quality-guidelines.md#test-and-validation-value`，执行其责任边界、停止外推、最小充分证据、去重与复用方法。源码位置为 `trellis/presets/guru-team/spec/workflow/quality-guidelines.md`，安装位置为 `.trellis/spec/workflow/quality-guidelines.md`。这些跨阶段验证规则只由该节定义，本文件不另设测试层级或证明表。

## 4. 完整审核与局部修订

创建审核面向最终标题和草稿正文。修订的内容完整性审核面向修改后的完整标题、正文及必要来源上下文，不能只审新增段落。审核者先独立连续阅读正文，还原适用场景、主要行为、可观察结果和必要例外，再按第2、3节反查完整来源、真实入口、消费者及验收，同时识别多余要求与必要遗漏。基本行为须能从正文理解，不能依赖作者在会话中补充解释。核对改动的跨段影响及此前仍有效的要求；发现既有入口不自动新增交付项，完成原始目标所需的真实适配也不能因精简而省略。

首次创建写入前，原 owner 必须确认最终完整正文的验收合理精简。现成草稿、上游通过、创建意图或“先记录以后完善”不能替代本次适用判断。不合规先沿原 owner 回程修订，未修订通过不得创建，也不得靠创建后的正文编辑或审核评论补救。草稿实质变化只刷新直接受影响的原判断。Create Issue 执行器保持原样提交；已经实际成功创建但输出丢失时，沿原恢复路径找回同一对象，不重复创建。

从草稿到后续每轮审核，本规范持续约束相关原写作与审核 owner，包括需求／方案、Planning、Architecture、Approval、Check、独立 Review、Branch／Delivery Review 和 Completion。workflow／standalone、Task 是否存在、换 Agent、恢复会话及输入来源均不产生豁免。每轮拟新增、恢复或强化义务时，先按第3节所指共用方法核对有效来源、受支持场景、权责、已有验收和仍适用证据；不成立的候选在本轮输出前删除，不先形成阻塞、返工、风险、强制 follow-up 或放行条件再交下轮撤销。设计、测试与审核记录不能自行授权扩张。真实原范围遗漏、缺陷或失效证据仍由原 owner 定向修复，真正范围变化返回原 Clarify。

每次将修订正文写回 GitHub 前，原 owner 检查最终完整正文及受影响的规划、验证安排；未满足时先在草稿修订，不先写回再补救。已删除的多余义务不能在评论、其他章节或后续阶段以改名方式恢复。无依据义务及派生测试、Finding、依赖和 gate 一并删除，不转移给后续阶段；有效且未受影响的判断和证据继续复用。

修订的语言检查只覆盖本轮新写或修改文本及理解它所需的上下文。适用语言规则按唯一语言规范执行；无关历史段落不因个人表达偏好被强制重写。短句、常用词和主动语态是建议，同样清楚准确的表达可以保留，不能仅靠句长、词数或建议差异阻塞。

局部修订先界定本轮修改范围。原审核发现本轮普通遗漏或跨段不一致时，交原受影响 owner 修订，并按原重新进入审核的规则执行。如果发现范围外既有缺口，说明缺什么及其对本轮结论的影响，不静默扩写。如果该缺口影响正文完整性判断，保留该判断的阻塞，不宣称正文完整合规；真实范围选择由原 Clarify 处理。

## 5. 原 owner 的使用

| 原 owner | 在原职责内实际使用本规范 |
| --- | --- |
| Clarify | 按第2、3节形成边界内必要结果，按第4节在原自检及正文写回前审核完整候选；判断意图、来源角色、范围和真实选择。显式只读措辞请求使用 standalone_wording_review；正常需求审核不增加独立门禁 |
| Readiness | 按第2–4节在原十维内核对完整正文的权责边界、目标与结果、证据重复及必要承诺；普通缺口经原 `clarify_requirements` 或适用 existing-Issue 补充出口返回原 owner，不自行改写 |
| Create Issue | 按第2–4节在原创建语义门禁、首次 provider 创建写入前确认最终草稿满足本规范，前序结果仍适用，待写内容与已审核稿一致；不合规沿原 `refresh_review` 回 Sync/Intake 及原责任方，修订通过前不得创建。执行器不裁剪正文；创建后沿原路径回读核对实际标题和正文 |

每个 owner 实际读取当前正文及必要来源，不能凭上游的通过代替自己的判断。各 owner 保留原入口、出口、确认及恢复，不新增通用审核人或平行门禁。章节齐全、关键词覆盖、文件存在、记录器或校验器通过都不能证明内容充分；脚本仅检查分发、引用、投影和既定机械条件。

## 6. 过程示例与证据边界

[简略工程请求](../examples/issue-content/brief/process.md)、[详细缺陷来源](../examples/issue-content/detailed/process.md)、[分散来源与局部修订](../examples/issue-content/revision/process.md)和[验收边界与证据去重](../examples/issue-content/acceptance-boundary/process.md)用于教学。既有示例中的 Wording 执行属于退役前实际历史，当前路径由本节前述 owner 承接。示例分别标明实际观察、去敏整理及情境假设；它们不是当前要求、用户回答或验收证据。当前任务若要求真实 Agent 写作、审核发现遗漏、创建或修订回读，须通过其正常入口执行并单独报告。分发测试与示例存在不能代替这些结果。
