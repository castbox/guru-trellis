# Issue 内容编写规范

## 1. 使用与唯一来源

本文件是 Issue 创建与修订共同的内容规范，由原 `guru-clarify-requirements` 维护。运行时完整读取 `.trellis/guru-team/skills/packages/guru-clarify-requirements/references/issue-content.md`；原受管 package 分发同时提供完整安装包和声明平台的可读投影。入口、示例和 README 只定位本文件，不另维护内容标准。

创建、修订及原审核 owner 在生成或审核实质文本前，还须完整读取 `.trellis/spec/workflow/clear-technical-writing.md`。语言规则仅由该文件定义。它是采用 STE 部分原则的项目中文清晰写作规范，不是 ASD-STE100 中文版，也不证明中文符合 ASD-STE100 或取得认证。文件缺失或读取失败时，只报告具体缺口，暂停依赖的实质文本；恢复并完整读取后继续原请求，不新增审批。共同内容规范不可读时，沿原安装或 owner 恢复后继续，不猜测正文。

来源处理实际加载原 Author [规划正文合同第2节](../../guru-author-task-plan/references/planning-body.md#2-从来源到正文)及必要关联条件，只复用其完整读取、来源角色、语义保留与必要引用规则。该节是这些规则的唯一公共来源；其 Planning 章节、模板和接受边界不变成 Issue 格式要求。

本规范不改变现有 scope authority、Skill Interface、typed exits、确认、freshness、写入或恢复合同。独立操作与 workflow 使用同一内容基线。普通状态查询、只读审核、需求讨论和过程评论不自动触发正文写入。也不要求所有简略 Issue 先改写成完整 Issue 才能进入 Planning；正文整理适用于用户实际请求的创建或完善，原 Author 对简略来源的调查、澄清及 PRD 写作保持。

## 2. 原 Clarify 的正文整理

1. 先完整读取当前请求、现有标题和正文、相关评论及必要仓库事实。按原来源规则判断哪些内容仍有效，区分已确认要求、约定设计、建议、历史事实、原始证据和未决问题。仓库可回答的问题先调查，不猜测缺失事实，不编造用户回答。
2. 对影响需求成立的真实选择，沿原 Clarify 流程处理。必要问题未解决时，说明具体缺口及其阻塞的结论，不宣称正文已完善。需求已清楚而实现机制未定时，留给原规划 owner，不要求提交者先完成技术设计。
3. 形成最终草稿或完整修订正文时，保留此前仍有效的已确认需求，整合本轮明确变更。替换、撤回或范围调整由原 Clarify 处理；某项要求本轮没有重述，不能据此删除。已有明确接口、机制、职责、顺序和兼容承诺按其来源角色保留，不以“以后再设计”删去。
4. 将必要已确认内容写入最终正文。评论与会话承载讨论和历史，但内容已经出现在那里，不是省略正文的理由。共享定义或详细接口规格可以准确引用；本 Issue 的行为、条件、约束及验收仍须在正文说明，不能只写链接或“见讨论”。
5. 输出前对照完整来源自检标题与正文：范围、条件和验收是否对应，来源角色是否保留，旧承诺与本轮变更是否一致。简短而完整的原正文可以保留，不为形式重写。

草稿更新沿原 `proposed_draft_update` 和上下文刷新。已有 Issue 沿原 `issue_body_edit`、精确 payload、repo-bound GitHub 写入、live reread 和 `refresh_context`。普通澄清讨论仍可使用原 `issue_comment`；它不代替用户请求完善时的最终正文整理。修订不调用创建动作，不产生重复 Issue。新 Issue 只从经原审核的最终草稿进入 `guru-create-issue`，不隐含 Task、branch 或 worktree 创建。

## 3. 适用内容、深度与裁剪

标题明确本 Issue 要解决的问题或交付行为。正文按真实需求组织以下适用内容，不规定统一章节或顺序：

| 内容 | 读者应能理解什么 |
| --- | --- |
| 背景与问题 | 当前现象、已有能力、缺口及其影响；区分事实与待验证判断 |
| 目标与范围 | 本 Issue 承担什么，不承担什么；已有正确能力如何复用 |
| 真实场景 | 用户或调用方、前置条件、触发动作、处理行为和可观察结果 |
| 行为要求 | 已确认行为及适用条件、否定、例外、失败结果和执行顺序 |
| 约束、依赖与来源 | 影响交付的约束、依赖及准确来源；已约定技术承诺与候选方案的角色 |
| 验收与验证 | 从什么入口、用什么输入观察什么结果；不得把预定验证写成通过 |
| 实际未决项 | 具体缺口、影响和原处理 owner；确实没有时如实说明 |

简单 Issue 可以短写、合并章节，裁剪不能丢失适用内容。不强制空章节、无关的 N/A、统一用户故事、Given/When/Then 或优先级格式。Bug 以现象、期望和正常复现场景为主；工程变更说明真实调用方及“触发条件 → 行为 → 可观察结果”；存在真实业务角色和价值时可以采用用户故事。

复杂度决定展开深度。有真实分支、失败或恢复时写清条件和结果；有规范性技术来源时保持其承诺。没有相应行为时不为填表制造接口、状态或故障要求。技术细化未定不自动成为产品需求缺口。

## 4. 完整审核与局部修订

创建审核面向最终标题和草稿正文。修订的内容完整性审核面向修改后的完整标题、正文及必要来源上下文，不能只审新增段落；须核对改动的跨段影响及此前仍有效的要求。

修订的语言检查只覆盖本轮新写或修改文本及理解它所需的上下文。适用语言规则按唯一语言规范执行；无关历史段落不因个人表达偏好被强制重写。短句、常用词和主动语态是建议，同样清楚准确的表达可以保留，不能仅靠句长、词数或建议差异阻塞。

局部修订先界定本轮修改范围。原审核发现本轮普通遗漏或跨段不一致时，交原受影响 owner 修订，并按原重新进入审核的规则执行。如果发现范围外既有缺口，说明缺什么及其对本轮结论的影响，不静默扩写。如果该缺口影响正文完整性判断，保留该判断的阻塞，不宣称正文完整合规；真实范围选择由原 Clarify 处理。

## 5. 四个原 owner 的使用

| 原 owner | 在原职责内实际使用本规范 |
| --- | --- |
| Clarify | 写草稿、修订正文并自检；判断意图、来源角色、范围、必要内容及真实选择 |
| Wording | 检查清楚表达、术语一致，以及重排和改写后的完整语义；保持原完整 title/body scan。必要评论是 AI 阅读的来源，不声称被 scanner 扫描 |
| Readiness | 在原十维审核内判断需求完整性、范围、独立交付单位和可观察验收；普通遗漏返回原受影响 owner |
| Create Issue | 在原创建语义门禁确认最终草稿满足本规范、前序结果仍适用、待写内容与已审核草稿一致；发现遗漏沿原 `refresh_review` 回 Sync/Intake 及原责任方。创建后沿原路径回读核对实际标题和正文 |

每个 owner 实际读取当前正文及必要来源，不能凭上游的通过代替自己的判断。四者保留原入口、出口、确认及恢复，不新增通用审核人或平行门禁。章节齐全、关键词覆盖、文件存在、记录器或校验器通过都不能证明内容充分；脚本仅检查分发、引用、投影和既定机械条件。
