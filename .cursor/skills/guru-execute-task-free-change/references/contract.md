# Task-Free Change Execution Contract

This semantic Skill owns execution location, bounded editing, targeted checks,
and execution-time scope/risk evolution. Before the first candidate write and
on continuation, read the actual execution directory, repository/common-dir,
registered primary/linked topology, branch/HEAD, full dirty/untracked diff,
unresolved conflicts, and current real binding and candidate ownership. A
path, branch name or another chat's Task inventory is not Task identity.
Branch protection is outside this local execution decision.

A suitable writable position is a registered linked worktree in this repository
on a non-base working branch, with no unresolved conflicts and a scope,
candidate and current binding compatible with this request. The primary
checkout is not a bounded-edit location, even on a non-base branch; a linked
checkout on the base branch or detached HEAD is also unsuitable. Keep the
primary checkout on its base ref; normal base synchronization remains with
`guru-sync-base`. Never switch/create a work branch or detach there to make a
location suitable. Any explicit primary-ref exception is a separate exact Git
operation, not this edit route's fallback.

Reuse an appropriate linked candidate after reviewing its real ownership and
complete diff. If none is available or evidence is insufficient, return
`location_required` before writing. This same owner consumes that interaction:
show the exact repository, base/ref/HEAD, new branch, absolute linked path and
creation effects; consume the applicable current-dialogue authorization for
that action before authenticated `git worktree add`. Re-enter here in the
selected directory, reread live facts, and repeat suitability before any edit.
No authorization or unavailable location means no dependent write. Use explicit
isolated cwd for commands and absolute isolated paths for file tools, output
and artifacts. Read-only work does not acquire resources.

Task-free location acquisition uses ordinary Git facts and operations. It does
not invoke Task APIs, Task-specific checkout checks, creation/activation/session
binding or acquisition wrappers; it creates no TaskId, TaskBranchBinding,
`task.json`, created DTO, task-free ledger or persistent checkout mapping.
Actual current-chat formal binding returns to its existing owner; a stale or
conflicting binding stops without deleting or replacing it. Other chats'
Tasks in the same common-dir are inventory, not this chat's binding.

Preserve unrelated dirty/untracked content and all existing candidates and
worktrees. Existing primary edits stay there: first review ownership and the
complete diff. Carryover requires a separately displayed exact source, target,
diff and action under its own applicable authorization. Never automatically
stash, move, overwrite, reset, delete, mix into commits or fall back to primary
writes. Credentials and ignored/uncommitted inputs are not inherited by a new
worktree; use an explicitly established safe read-only source or current-process
environment. Missing input blocks only its dependent action.

Continuation uses the current request, host conversation and freshly read
binding/topology/diff. Same-scope retries retain their current mode and selection
origin while rerunning suitability. New-chat recovery requires an explicit
bounded request and live candidate facts; insufficient scope or origin cannot
be guessed from names, old results or a cache. Return the applicable bounded
interaction/stop rather than creating a Task to restore context. The Guru
workflow caller, not this package or upstream code, owns consumption of
`trellis-continue:no_current_task` into this route.

The owner forms a candidate-only set before its pre-write decision and invokes
`guru-qualify-normal-scenario:task_free_pre_write`. A candidate contains only a
stable ref, observed behavior, current code/test locator, and the minimum live
reread locator; it carries no scenario class, decision, severity, route, or
authorization. Newly discovered behavior/scope/risk candidates use
`task_free_evolution` before this owner decides whether bounded execution
remains suitable. `classified` and `mechanism_revision_required` return to this
owner, `scope_confirmation_required` routes to `guru-clarify-requirements`, and
`blocked` stops. A rejected classification cannot cause a question, negative
test, edit, or expansion route. This package writes and rereads no qualification
result, report, locator, or checkpoint.

The AI Review Gate must bind both sides of execution. `pre_write_review` records
why the selected checkout is suitable or why another route is required.
`completed` additionally requires `completion_evidence` containing the actual
edited paths, targeted checks with concise report summaries, a passed
`post_write_review`, and explicit unverified boundaries. Its public DTO exposes
only those edited paths, summarized check results, and unverified boundaries
needed by the workflow completion response; commands, review narrative, and
complete execution evidence remain private.

The completion response is bounded to actual edited paths, local targeted checks
and explicit unverified boundaries. It does not claim artifact deployment,
capability enablement, consumer adoption or original-request end-to-end acceptance.
When changing status/gate logic, consume the original qualification's protected
object, invariant, minimum migration and operation applicability. Missing switch
evidence restricts only the transition or claim that needs it; do not generalize
one migration gate into all interfaces or all delivery being unavailable. Retain
independently established contract, source and deployment facts as such, while
keeping this result's own claim at the local-edit layer.

For those status/gate changes, identify the supported entry points in the
selected targets that dispatch the affected operation, then trace their actual
callers, argument parsing, dispatch and outer guards. Do not select only the
application helper because existing tests call it. A correct helper does not
establish that a CLI or other supported entry permits the same call. Before
declaring the local edit complete, check the requested availability through the
affected supported entries after writing, and check that the qualified
transition still requires its evidence. If current tests reach only a lower
function, use the minimum actual entry checks needed by the request and source.
Keep unchanged consumers in this review; do not manufacture a full state matrix
or an obligation for changes that do not affect status/gate behavior.

`reselect_mode` and `explicit_choice_required` are post-write routes. Each
requires `evolution_evidence` for a real partial edit: actual edited paths, the
new scope/risk fact, `stop_after_detection=true`, remaining target writes not
performed, and applicable targeted checks. Deterministic record/check/invoke
commands validate identity, bounded edited/remaining target membership, and
structure only; they never decide suitability, expansion
significance, scope, risk, edit completion, check adequacy, or route.

Same-scope active-task work returns `resume_active_task`; potential expansion
returns `scope_change`. An unrelated location, unresolved dirty overlap,
unsuitable topology, or insufficient position evidence returns
`location_required`. Automatic task-free expansion returns `reselect_mode`; explicit task-free expansion returns
`explicit_choice_required`. The two interaction exits self-reenter without
persisting the user's answer or authorization.

The public handoff is deliberately minimal. Review narrative, Git status,
target snapshots, check transcripts, and authorization remain private or
dialogue-local. Missing, stale, multiple, unknown, or unmapped results fail
closed.

On automatic expansion, stop remaining target writes immediately and retain the
actual partial diff before returning `reselect_mode` to the selector. Explicit
expansion similarly stops and returns `explicit_choice_required` to this owner
for narrowing or standard Intake. Neither return silently creates or binds a
Task. Narrowing preserves the candidate and reruns pre-write suitability;
standard selection enters the existing Intake/acquisition owners.

Formal Task acquisition retains its clean-checkout invariant. A suitable clean
linked position may be reused by that owner after its own review. If this
candidate contains partial edits, the original Intake/acquisition owner selects
a clean linked position and separately reviews any exact carryover action and
its authorization. Until then preserve the candidate and stop dependent actions.
Use live source/target diffs and host continuation to avoid repeating completed
carryover; do not introduce a transfer ledger, empty Task or relaxed global
clean check. Commit, push, PR, merge, release, install and cleanup each retain
their original owner and independent operation boundary.
