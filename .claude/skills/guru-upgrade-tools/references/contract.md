# One checkout tools maintenance

`judgment_mode=semantic`; standalone only. This owner installs tools, not Task
conversion, historical closeout, business completion, session restoration or
base integration. The complete successor canonical source and its managed
runtime execute every command. `--root` is repository selection context, never
a request to run the old target dispatcher. A platform discovery copy is not
self-contained. Existing `guru-upgrade-installation` full Plan2 inputs and
recovery retain their original meaning; this Skill does not call them.

## Entry selection

The AI selects this owner when the actual request updates tools, workflow,
Skills or managed projections in one existing checkout while preserving all
Task/session state. Source-repository dogfood synchronization can use this
same entry under its existing source and write-set requirements.

Ordinary full preset apply/reapply keeps its current-only Task inventory
precondition. Its `upstream_delivery_migration_required` diagnostic describes
that invocation's inventory; it neither requires a tools-only request to
convert unrelated history nor establishes this owner's prerequisites. Read the
actual goal, target and available maintenance capability before choosing this
entry. A full installation/migration request stays with its original owner;
missing tools-only prerequisites stop here without falling back to migration.
The script diagnostic never chooses that semantic route. Selected single-Task
conversion or historical maintenance remains with `guru-maintain-legacy-task`.

## Version and unfinished-operation prerequisites

After selecting the target version, resolve it to a complete Guru commit and
read that commit's own Fork source lock. Obtain the CLI and Core packages from
that exact locked source and verify the existing package/source checks. This
applies to formal releases and explicitly selected unpublished candidates.
Unpublished `main` is not a default stable release. Version labels alone do not
establish this source pair; isolated `local_candidate` retains its declared
formal-source-lock limitation.

Before preparing or writing a new operation, inspect relevant unfinished
upgrade transactions in the selected checkout and any shared paths the proposed
write set touches. Return an existing transaction to its original owning Skill
and matching source pair. Use its original input, frozen plan, recovery reference
and backups under that owner's recovery contract. The original owner means the
Skill and operation, not the original chat or Agent; another Agent may recover
from the complete original inputs. Preserve later business work. Do not edit
old checkpoints, refresh rollback anchors, or assume every unfinished operation
must roll back. If legal resume or rollback is unavailable, that original owner
handles the concrete case before an overlapping new operation can proceed.

## Forward behavior

1. Read the selected public profile. For `install`, bind `source_ref` to the
   actual source HEAD and explicitly select `source_locked` or isolated
   development `local_candidate`. Obtain matching installed CLI/Core package
   roots, actual byte identities and public maintenance API1.0. The runtime
   transport imports the public package main `maintenance` namespace only;
   missing APIs are before-write prerequisites, never an automatic Plan2 or
   old-runtime fallback. `source_locked` also requires the reviewed formal
   Guru/Fork source lock. Same version numbers are insufficient.
2. Resolve explicit `checkout` exactly. When omitted, use the original shared
   Sync resolver: explicit `base_branch`, configured base scalar, configured
   candidate list (default dev, develop, main, master), then remote symbolic
   default. Select a branch before locating its unique registered checkout.
   Missing/ambiguous/prunable checkout stops; do not skip a preferred branch
   to find an easier checkout. Selection never fetches, fast-forwards, creates
   or switches a branch/worktree, nor invokes Task Identity/Reconcile.
   Identify registered peers through the Git common directory and inspect the
   actual shared paths before freezing this one-checkout write set. Common-dir
   membership alone does not prohibit ordinary parallel work. Preserve every
   original observation key/value. New registered peers must be physically
   isolated from the actual frozen tool destinations; new keys alone do not
   fail the preservation check and never enlarge the operation's backup/write/delete set.
3. Read current upstream tools inspection, old Guru manifest/source hashes,
   actual managed edits, user config/spec/platform choice, and pointer layout.
   `preview.sh --root CONTEXT --input INPUT --upstream-source SOURCE_JSON`
   is read-only. It does not parse old Tasks as current authority. Unknown
   owned preimages require explicit preserve/replace; missing historical hashes
   come from the old exact source, never the successor. Do not retire upstream
   `trellis-*` assets under an old overbroad Guru receipt. A physically shared
   whole-.trellis tools alias cannot satisfy a single-checkout install and
   stops before any write. Ordinary dirty business work is allowed.
4. Author `private-prepare` in memory or an external private temporary file:
   actual `upstream_source`, exact `tools_input` accepted by public
   `prepareToolsInstallation`, selected platforms and per-path Guru decisions.
   For Guru workflow install use exact canonical content, template guru-team,
   its reviewed custom provider and `ownership=custom`; never label it bundled
   native. `preserve` requires AI to establish that the existing workflow is
   compatible with the actual current owner graph; preserving incompatible
   workflow bytes cannot establish success. Public file decisions retain
   official required/skip/user-edit rules. Require the actual public
   `getMaintenanceContract.tools_custom_instruction` capability to declare
   `path=AGENTS.md,action=custom`. Supply exactly one AGENTS decision with
   `action=custom`, the actual original `source` snapshot (or null), and reviewed
   `content` as its base. To update upstream template text, explicitly review and
   supply that base; do not silently convert preserve/replace or copy the updater.
   The prepare owner copies this input and uses the original installer's pure
   renderer to update only its Guru block before calling public prepare once.
   Call `prepare.sh`; its receipt contains `result.plan`, the single frozen public
   operation ID and public/Guru/pointer facts. The returned public plan is not
   changed. Validate its AGENTS target is renderer-idempotent; an old block left
   by `update.skip` stops before writes. Missing capability, missing or duplicate
   AGENTS decisions also stop before writes. The public writer owns the final
   content/mode, guard and candidate; the later preset is byte-idempotent.
   Core template hashes retain their Core baseline meaning. Preparation creates no target
   checkpoint. Keep this plan for the same invocation; do not prepare another
   operation to recover a partial one.

## Managed manifest preimage

[original conflict contract](../../guru-reconcile-task-base/references/contract.md#managed-manifest-conflict-continuation).
Establish that it represents the actual prior installation and retain its raw
bytes, source/provenance and managed hashes. It is only the working inventory
preimage. A parseable old manifest does not prove that the merge is resolved.

Use the complete combined canonical source and this owner's existing
preview/prepare/invoke sequence. Inspect relevant unfinished operations first.
Judge each actual managed difference as preserve or replace against its real
preimage; missing historical hashes require the exact original source. Keep
ordinary workflow, AGENTS, public maintenance API, platform and pointer rules.
Prepare once, retain the returned frozen plan and recover the same operation
when necessary. Do not edit the old manifest to make differences disappear.

The original installer generates the final manifest and projections. Verify
both sides' canonical changes in that installed result, run the actual target
resolver, installed/native/drift and sidecar/mode checks, then return to the
original conflict-resolution step for final staging and resolved execution.
Tools success remains an installation fact, not Check or full Review.

Dirty combined canonical may use only the original isolated `local_candidate`
boundary with `unverified=[formal_fork_source_lock]`. After a real clean
canonical commit exists, formal adoption is a new original `source_locked`
operation using its matching Fork. Never change the old plan/ref or relabel
local-candidate evidence. Existing in-flight operations retain their fixed
complete provider; this contract clarification changes no public I/O, parser,
manifest field or recovery family. Existing installations adopt it through the
complete matching tools update and actual target validation.

## AI Review Gate and write boundary

Review the exact source, selected checkout, public tools/workflow and Guru

platforms, all conflicts/sidecars and source-lock limitation. Confirm that no
Task/planning/archive/workspace/public session/private control, peer tools or

and fixed plan actually implement the requested tools-only change. Native
checks and schema validation are facts, not this judgment.

Present the exact target, source, command and write/deletion set. Obtain
current-dialogue confirmation only for this actual write or a real unresolved
choice. Do not serialize authorization, a review transcript, a pass flag or a
reviewer identity. Mapped same-operation recovery within an already confirmed
write set proceeds without another permission request. Changed scope or source
returns to this gate before any new write.

## Deterministic execution and target evidence

Call `invoke.sh --root CONTEXT --input INPUT --plan FROZEN_PLAN` using the
source launcher. It freezes the original Guru asset/pointer preimages and
public operation ref in Git-private recovery before either owner writes.
Public `applyMaintenance` installs only its reviewed template/workflow set.
The original Guru installer retires only exact old Guru-owned assets and the
old manifest, then performs real staged current installation. It generates
its own current manifest; this owner never fabricates one. Current ordinary
validators remain current-only. Preserve unknown local edits; essential
package conflicts and any unresolved `.new`/`.bak` block success.

The tools-only installer uses the original immutable managed Python cache and
checkout-local `.trellis/.runtime/guru-team/python/active.json` override for
both primary and linked checkout. The selected target resolver reads it first;
original gitdir/common fallback still supports ordinary installs. Common and
peer pointer bytes stay unchanged. The source runtime is not evidence that the
target can execute: read the public tools postvalidation, run the real target's
own resolver plus installed package validation and its actual native entry.
Verify that peer checkout tools and common/peer pointers remain unchanged.
A direct old Task must diagnose maintenance_required and route to the separate
maintenance owner, not appear valid/current. A valid current target must enter
its original next owner. Do not convert data to make tools validation pass.

After checking actual native and preservation facts, return `tools_upgraded`
only when target tools are usable and all required conflicts are resolved.
The exit does not claim old Task migration or Completion. In development mode
`unverified=[formal_fork_source_lock]` is mandatory and tells the result
consumer that this is local-candidate proof only. Real business installation,
external acceptance and release matrices remain separate evidence.

## Same-operation resume and rollback

`resume_required` projects only `profile=resume,recovery_ref` to this same
owner. Use that exact ref in the target checkout, from the unchanged source.
Read its private phase/failure and public recovery facts. AGENTS input composition
occurs only before initial public prepare; resume/recover/rollback consume the original
frozen plan and never reproject targets or edit an existing checkpoint. Resume uses the
original public plan/operation ID and original Guru preimages; it never expands
backups, accepts a replacement plan, replays a completed public write, or
imports later business work into rollback eligibility. Complete output loss
is recovered by the same reference and actual checks. A source/path/runtime
mismatch or later owned edit stops for review. Apply the unfinished-operation
prerequisites above before any overlapping new operation. Sidecar reconciliation
must be an explicit reviewed canonical resolution; it cannot silently refresh
backups.

Rollback is a separately reviewed bounded write. Read the fixed original
preimages and current Task/session compatibility through the public owner.
First validate Guru owned-path freshness without restoring it, then call the
public `rollbackMaintenance`. That API checks actual Task2/session3 versus old
reader capability before its restore. Incompatibility leaves both halves
untouched; never restore Guru first and discover the incompatibility afterward.
Only a successful public rollback allows exact original Guru assets/pointer
restoration. Neither owner resets Git nor deletes branches, newer Task work,
business files, remote PRs or historical evidence. Run the old target native
smoke and check its restored runtime before reporting `rolled_back`; retain a
concrete unresolved gap instead of claiming success if that smoke is missing.
The original recovery is the only rollback consumer of the retained private
preimages; rollback does not create a new anchor or future authorization.

## Frozen-source recovery of schema1.0 operations

`recover_frozen_source` is an explicit additive profile for existing schema1.0
operations, including the operation blocked in #766. Read the original failure,
phase, target, source and frozen public pair/plan/ref and preimages. Establish
that the repaired complete executor source is applicable to this peer-growth
repair. The original `cp.source` remains the complete logical asset source;
its HEAD/tree token and root binding still must match. Existing `resume` and
`rollback` remain same-source profiles and do not gain implicit cross-source
fallback.

Invoke from the complete repaired source with the original identity
`{profile: recover_frozen_source, action: resume|rollback, recovery_ref: original}`
and the original target as `--root`. Do not supply a new plan/source override,
prepare another operation, edit the old checkpoint, refresh its peer snapshot
or backups, or incorporate later owned/business edits. The current repaired
engine loads the installation helper and preset assets from the original
logical package. Its sibling helper dependency is loaded from that same source;
a prior import cache cannot choose different asset code. Source mismatch,
owned mismatch and changed original peer values still block.

The current engine follows the original recorded phases. `preset` means the
original preset action is still pending and may continue the original installer
with its original public recovery reference. Existing projected files are not
proof of `complete`. At `complete`, recovery validates without installing again.
Public work already completed is recovered by the public owner; there is no
new prepare or operation. Rollback still checks public compatibility before
restoring original Guru preimages. Verify the target's own resolver, installed
runtime and native entry, and peer preservation independently. A tool result
does not establish Task or Delivery success.

### Explicit normally retired peer locations

Before using `retired_peer_roots`, read the original peer owner's real terminal
exit and exact checkout location, then judge whether that normal retirement is
applicable to this recovery. Directory or observation absence alone is not that
judgment. Missing owner evidence returns to this same semantic owner for the
concrete evidence gap; do not infer success or automatically select roots.

Only `recover_frozen_source` additionally accepts optional
`retired_peer_roots: string[]`. Omission and `[]` retain the original preservation
check. A nonempty list names the finite, reviewed absolute retired checkout
locations. Runtime verifies each location is not the target, has the original
checkout-local active pointer marker in the frozen observation, is absent from
all Git worktree registrations including prunable records, and has no filesystem
entry of its own. Reuse the original peer parser with its default #759 filter
unchanged; a complete-registration read is only for this object check.

For those exact locations, retire only original local active/selection-v3 and
installed/source runtime observations. Do not skip a path prefix or common/gitdir
state. In this nonempty explicit mode, other original file observations that
current enumeration no longer lists are reread from their original paths and
must retain the same state. Uncovered runtime observations missing from current
enumeration still block. Same-source profiles gain no exception. Pass the same
call-local roots through the original engine's before/after preservation checks;
never rewrite `cp.public`, peer observations, plan or preimages.

When that engine returns a retry requirement, this profile emits
`frozen_recovery_required` with the same profile/action/ref. Its sole consumer
is this owner at `recover_frozen_source`; keep `action=rollback` on rollback
retry. If the caller actually provided `retired_peer_roots`, include that same
value in the retry, including `[]`; otherwise omit the field. The existing
presence-select projection copies it only when present. Read and review the new
failure before re-entry. Success and permanent
blocking retain the original independent output contracts. No checkpoint
fields, data conversion or backup migration are added.

This owner retains compatibility until the existing schema1.0 operations have
reached a terminal state and their original recovery retention responsibility
has ended. Removal then requires an explicit migration by this owner; this
change adds no transaction scanner, automatic API retirement or general
migration framework. The complete support and adoption boundary is in
`trellis/presets/guru-team/MIGRATION-769.md`.

## Public output consumers

- `tools_upgraded`: result stop consumes installed_version for actual target
  status, recovery_ref for this owner's optional rollback, and unverified for
  the formal-source boundary. No Task/session inventory or digest crosses it.
- `resume_required`: same owner consumes only profile and recovery_ref.
- `frozen_recovery_required`: this same owner consumes profile, action and
  recovery_ref through the explicit frozen-source input; the projection removes
  exit_id, preserves the original action, and copies retired_peer_roots only
  when that field is present.
- `rolled_back`: result stop consumes the actually restored installation version.
- `blocked`: result stop consumes the concrete missing prerequisite/conflict.

These are independent output schemas. No stop enters Task Completion, normal
Finish or another install. Unknown/multiple/unmapped exits stop. Private plan,
preimages and public operation details belong only to this same-owner recovery;
no downstream Skill reads or deletes them.
