# 连续旅程、阶段交接与证据边界

先读 [source 全文](source.md)。本例是教学推演，所有处理和结果均为示意，没有执行真实 Agent、设备或测试。它不能作为当前用户回答、当前方案批准或本批验收通过的证据。实际行为观察须另用中性材料，经受支持入口执行并独立评价；不要把本例的问题答案送给被观察 Agent。

## Clarify：沿连续动作发现真实选择

从 source 第1节已确认的最终提交结果，先反查主表单持有已确认内容、附件就绪等普通保存前提，再展开“进入编辑页 → 选择媒体 → 后台处理期间再次编辑 → 局部确认 → 主表单退出提示 → 返回编辑稿 → 最终保存”的正常旅程。各段结果分别是编辑器可见内容、表单持有选择、未保存提示、可恢复内容和最终提交结果。局部确认不向服务器提交；普通保存前提满足后，须观察服务器收到的文本内容与已确认附件一致。后台任务完成与这些 UI 动作有各自含义，不能因为局部确认成功便认定上传、可靠保留或保存成功。

同样沿真实入口检查“长按文本区域 → 菜单出现 → 粘贴 → 文本可见”，以及“选择媒体 → 返回编辑页 → 继续输入”。这些场景已有明确要求，不必重新问是否需要菜单或焦点。处理中再次操作、确认后退出和重新打开属于本例明确支持的普通操作，不需要制造异常并发压力来发现问题。

source 第3节的未确认关闭行为有两个真实解释。Clarify 应说明它对再次打开的可见结果和来源保留责任的影响，提出有依据的建议并取得真实选择。在答案到来前，保留这一缺口，不编造一次回答；可继续不依赖该选择的调查，并保留已局部确认、普通保存前提满足后的最终提交路径及观察。writer/reader 的转移代码与原生库裁剪方式属于技术方案，不能要求用户提供实现。

## Author：在所属正文解释交接条件

PRD 保留已确认的阶段行为、普通最终保存结果与真实未决选择。design 说明编辑器、表单和后台任务各自在什么时候持有来源、读取结果、转移和清理，并说明主表单如何将同一已确认内容的文本与附件交给服务器。此例需要的条件是：被有效编辑稿或表单引用的来源持续可用；仍有接收方的后台结果不能在持有者变化后丢失；最终保存前的未保存判断涵盖已局部确认但仍在处理的媒体。

source 第2节的初稿先释放编辑器的唯一引用，之后才交给表单。两步之间清理条件已成立。原设计审核据此要求 Author 修订交接顺序或持有机制，使新接收方建立引用后才释放原持有方；不要用“结果对象还在内存”代替来源可用的证明。Architecture 在自己的 authority-first 顺序内评估这一机制，Approval 判断其是否足够实施。无需新增锁、crash 协议或第二次架构评估。

后台任务复用也要沿真实接收关系核对：重新确认后的候选由谁接收原 Future 的完成结果，谁继续观察后续状态，失败或放弃后谁清理。只检查旧候选清理不覆盖新候选完成。将必要结论写在 design 的实际交接处，不另建持有者台账。

## Implement：先获得完整旅程反馈，再补有价值的差异

入口和相关依赖可运行后，先执行一条能经过选择、局部确认、返回和最终保存的最小正常旅程，尽早暴露页面接线和交接缺口。分别观察局部确认没有向服务器提交，以及普通保存前提满足后服务器收到的文本内容与已确认附件一致。之后补等待中再次编辑、退出提示和恢复等尚未覆盖的独立行为，不先重复大量等价文件尺寸。高风险的引用转移或任务回调可先用便宜模块测试验证；完整旅程通过也不能替代剩余必要验收。

如果真实上传环境不可用，继续验证独立的文本菜单和本地交接，但明确上传后续状态仍未验证。不要把环境装配失败解释为产品失败，也不要把替身成功提升为真实环境通过。

## Check：按声明行为核对证据

| 当前证据 | 可以支持的局部结论 | 仍须补足的具体问题 |
| --- | --- | --- |
| 直接调用 paste 后文本正确 | paste 方法的文本逻辑 | 长按是否真正唤起菜单，菜单是否连接该动作 |
| 选择回调返回媒体 | 回调的数据处理 | 回到编辑页后的焦点和继续输入结果 |
| confirm 方法返回选择 | 方法内的结果转换 | 页面释放来源与表单接收的实际顺序 |
| 替身返回同一实例时刷新通过 | 同实例路径 | 真实反序列化新对象、刷新地址后的合并与展示 |
| URL 已存在，缓存中旧帧可见 | 地址或旧缓存存在 | 下一帧实际解码后能否显示，失败帧如何影响当前已确认行为 |
| H264/AAC MOV 样本通过 | 该输入在该构建上的能力 | 已确认接受范围是否含其他编码，交付依赖是否具有所需能力 |

这些差异只要求证明当前声明的行为。无需每条单测跑全链，也不能从未知的 HEVC/PCM 能力直接承诺支持或删除既有支持要求。按来源核实范围和实际交付组件，再安排有独立价值的输入。

原独立审核 owner 应先从自身 authority 推导上述类型的问题，再看候选及实施总结。派工只提供当前对象、必要来源和声明范围，不预置“这里必有引用 bug”或“全部通过”的答案。保留正式读取顺序和仍适用的证据；不因为另一个执行者接手就重复全部实验。

## 简单函数对照与结果保存

source 第4节的 trim 纯函数可用直接单测观察输入输出，覆盖两端空白、中间内容保持和空字符串等有独立意义的条件。没有 UI 或资源交接，便不追加设备、媒体或持久化旅程。是否先写测试由明确行为、风险与成本决定。

必要场景写在 PRD，交接条件与机制写在 design，验证顺序与实际结果写在 implement 或原验证位置。区分已覆盖、失败、受改动影响需补验和未执行的范围；不复制原始日志，不新增评分、证明账本或固定场景数。本教学例不证明实际模型执行改进，更不证明真实 QA 缺陷率下降。
